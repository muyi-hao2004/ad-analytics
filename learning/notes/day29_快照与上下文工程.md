# day29 快照（Snapshot）与上下文工程

> 承接 day27/28，讲"快照"这个通用高频模式。它到处用得到，因为解决了"LLM 无状态 + 怕数据大"这个通用难题。

## 一、快照是什么

**把"当下的状态"压缩成一份 LLM 能读懂的精简结构化数据，作为每次对话的"起点背景"。**

| 关键词 | 含义 |
|---|---|
| 当下状态 | 不是历史/全量，是"此刻"的关键信息 |
| 压缩 | 原始数据太大太细，只留结论和可索引骨架 |
| 起点背景 | 喂给 LLM 的"开场白"，让它先知道发生了什么 |

## 二、为什么到处用得到

LLM 两个天生毛病：**无状态**（不记东西）、**怕大怕细**（数据喂多 token 爆炸还读错）。

快照同时治这两个毛病：**"别把整个数据库塞给 LLM，先把关键结论压成简报给它。"**

同一思想在不同场景的叫法：

| 场景 | 快照叫什么 | 压缩了什么 |
|---|---|---|
| 我的 Agent | snapshot | 每日报表的派生指标结论 |
| 智能客服 | 用户画像/订单摘要 | 用户历史、当前订单 |
| 代码助手 | 项目上下文摘要 | 文件树、关键代码 |
| 智能运维 | 系统状态快照 | CPU/告警/日志摘要 |
| 金融分析 | 行情简报 | 今日指数、持仓盈亏 |

## 三、快照设计三原则（我的代码已踩对）

1. **只给结论，不给过程**
   - 给"D7 ROI = 0.65"（结论），不给"让 LLM 自己拿 installs/revenue 算"（过程）。
   - 因为 LLM 算数容易错，派生指标代码算好，LLM 只读结论。
   - 对应"硬口径走代码、软经验走 LLM"。

2. **给骨架 + 按需查细节**
   - 快照只给 top 20 骨架，细节靠工具 `get_metric()` 按需查。
   - 快照 = "目录"，细节靠 Function Calling 取。

3. **快照是"会变部分"，放后面**
   - 呼应 day28 缓存：快照每天变，放固定前缀之后，别破坏缓存。

## 四、快照背后的三个通用模式

快照其实是三个更底层概念的合体：

1. **上下文工程（Context Engineering）**：决定"喂什么、不喂什么、怎么喂"。2024 后 Agent 最火概念。
2. **摘要/压缩（Summarization）**：大信息压成小信息，RAG 重写查询/压缩文档同款思想。
3. **状态管理（State Management）**：快照是"对话开始时的状态"，配合多轮状态更新= Agent 记忆系统。LangGraph 的 `state` 就是它。

## 五、完整数据流（我的项目）

```
数仓事实表（大、细、会变）
  → 压缩（只留结论+骨架）
快照 snapshot（小、精、结构化）
  → 组装进 messages（固定前缀之后）
LLM 读快照 → 理解现状 → 决定查什么/做什么
  → 需要细节时 → 工具按需查真实数据
```

**注意**：发给 LLM 的不是"原始数仓数据"，是"精简快照"。原始表太大太细、让 LLM 自己算指标容易错。

## 六、每日自动决策闭环

```python
def daily_auto_analysis():
    snapshot = build_snapshot()               # ① 算今天数据快照
    messages = [
        {"role": "system", "content": SYSTEM_PROMPT},  # ② 固定
        {"role": "system", "content": tools_str},      # ③ 固定（缓存命中点）
        {"role": "user", "content": snapshot},         # ④ 会变
        {"role": "user", "content": FIXED_QUERY},      # ⑤ 固定问题
    ]
    decision = run_llm_loop(messages)          # ⑥ 多轮查数→决策
    apply_decision(decision)                   # ⑦ 代码落地决策（不是 LLM 自己改）
```

每天变化的只有 `snapshot`，其余固定。

## 一句话总结

快照 = "把当前状态压缩成 LLM 能读懂的简报，作为对话起点"。它通用，因为解决"LLM 无状态 + 怕数据大"；背后对应上下文工程、摘要压缩、状态管理三个底层模式。
