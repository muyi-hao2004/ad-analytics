# 调度与消息队列

本篇覆盖：Airflow 的定位与核心概念（DAG / Operator / Task / Scheduler / Executor / Webserver / Triggerer）、调度周期与依赖写法、backfill 补数、调度器分容器部署的原因。
消息部分包括消息队列存在的理由、Kafka 的 Topic / Partition / Offset / Consumer Group 模型与投递语义、Kafka 与 Spark Streaming / Flink 的配合方式。
缓存部分包括 Redis 在数据链路中的缓存、分布式锁、去重、限流等典型用途。

主线是一条数据管道的三层骨架：**调度层（Airflow）决定什么时候跑、按什么顺序跑；传输层（Kafka）决定数据怎么在系统间流动；缓存与协调层（Redis）解决热点读取、并发互斥和重复处理。**

## 一、Airflow 是什么

### 1.1 它解决什么问题

一条数据管道是一串有先后关系的步骤：

```
拉取渠道数据 → 清洗 → 归因 → 算指标 → 写库 → 跑 Agent 分析 → 出报表
```

需要回答四个问题：

| 问题 | 没有调度器时 | Airflow 的答案 |
|---|---|---|
| 谁每天 8 点自动跑 | 人肉执行，或写一堆 crontab | `schedule_interval` 定时触发 |
| 步骤之间的依赖谁保证 | 靠脚本里 `sleep` 或手动串联 | DAG 的依赖边，上游成功才跑下游 |
| 某步挂了怎么办 | 不知道，或整体重来 | 自动重试 + 状态记录 + 从失败处续跑 |
| 怎么知道昨天跑没跑成功 | 翻日志 | Web UI 可视化 + 告警 |

一句话定义：**Airflow 是一个用 Python 代码描述工作流、按时间与依赖触发、并记录每一次执行状态的调度编排平台。**

它替代的是 crontab，但比 crontab 多了三样东西：**依赖管理、状态管理、可视化与重跑能力**。crontab 只能"到点执行一个命令"，不知道上游有没有成功，也没有地方记录"这次跑失败了几次"。

### 1.2 边界：它不是 ETL 工具

| 误解 | 事实 |
|---|---|
| Airflow 能做数据清洗 | 不做。清洗逻辑写在业务代码的 Python / SQL 里，Airflow 只负责调用 |
| Airflow 能存数据 | 不能。它只存任务的**元数据与状态**（在元数据库里） |
| Airflow 能传输大数据 | 不能。任务之间传大数据要靠共享存储（HDFS / S3 / 数据库），XCom 只适合小数据 |

准确说法：**Airflow 是"调度编排器"（orchestrator），不是"数据处理引擎"（engine）。** 数据在 Spark / SQL / Python 里算，Airflow 只负责按下按钮和检查结果。

## 二、核心概念

### 2.1 五个基础概念

| 概念 | 是什么 | 类比 |
|---|---|---|
| **DAG** | 有向无环图，一条业务管道的定义（代码文件） | 一份总流程图 |
| **Task** | 图中的一个节点，一个具体步骤 | 流程图里的一个框 |
| **Operator** | 决定 Task 执行什么动作的模板类 | 框里写的动作类型 |
| **Dependency** | Task 之间的先后关系 | 框之间的箭头 |
| **DagRun** | DAG 的一次运行实例，带一个逻辑日期 | 某天那趟执行 |

"有向无环"是关键约束：**有方向（A 必须在 B 前）、无环（不能绕回自己）**。有环就意味着任务永远等不到开始条件，调度器会直接拒绝加载。

常见 Operator：

| Operator | 用途 |
|---|---|
| `PythonOperator` | 执行一个 Python 函数（最常用） |
| `BashOperator` | 执行 shell 命令 |
| `SQLExecuteQueryOperator` | 执行 SQL |
| `SparkSubmitOperator` | 提交 Spark 作业 |
| `FileSensor` / `SqlSensor` | 等待文件出现 / 等待 SQL 有结果 |
| `EmptyOperator` | 占位、聚合分支（不做事，只用来汇合依赖） |

### 2.2 运行时角色

**Airflow 本质 = 一组后台进程 + 一个写 DAG 用的 Python 库。**

| 角色 | 是什么 | 职责 | 启动方式 |
|---|---|---|---|
| **Scheduler** | 进程 | 大脑。扫描 DAG 文件、按时间表创建 DagRun、根据依赖把 Task 标记为可执行、交给 Executor | `airflow scheduler` |
| **Executor** | 配置项 / 组件 | 决定"任务在哪里、以什么方式执行"，本身不做调度决策 | 配置文件 `executor = ...` |
| **Worker** | 进程 | 真正执行任务代码的进程，CeleryExecutor / KubernetesExecutor 下才需要独立部署 | `airflow worker` |
| **Webserver** | 进程 | 提供 Web UI：看 DAG、看状态、看日志、手动触发、清除任务 | `airflow webserver` |
| **Triggerer** | 进程 | 运行 deferrable operator（可延迟的传感器），用 asyncio 事件循环等待外部条件，**等待期间不占用 Worker 槽位** | `airflow triggerer` |
| **Metadata DB** | 数据库 | 存 DAG 结构、DagRun、TaskInstance 状态、连接、变量、日志索引 | Postgres / MySQL |
| **DAG 文件目录** | 文件系统 | Scheduler 定期扫描（默认 30 秒）解析 DAG 定义 | `dags/` |

几个容易混淆的点：

**① Scheduler 与 Executor 的分工。**
Scheduler 决定"**该不该跑**"（时间到了吗、上游成功了吗、并发满了吗）；Executor 决定"**在哪跑、怎么跑**"（本机多进程、发到 Celery 队列、起 K8s Pod）。两者解耦的意义是：**换 Executor 就能独立扩展执行能力，调度逻辑不用动。**

**② Triggerer 解决的是"空等"问题。**
传统 Sensor 会一直占着一个 Worker 槽位轮询（poke），等 6 小时就浪费 6 小时的槽位。deferrable operator 把等待交给 Triggerer 的单个事件循环，条件满足后再唤醒任务重新排队。**大量长等待任务（等文件、等上游表分区）场景下，Triggerer 能显著提升集群吞吐。**

**③ 代码里的 DAG 是"类"，运维启动的是"进程"。**
`from airflow import DAG` 拿到的是一个 Python 类；`airflow scheduler` 启动的是一个长期运行的服务。前者是定义，后者是执行。

### 2.3 Executor 类型

| Executor | 任务跑在哪 | 是否需要独立 Worker | 并行 | 适用 |
|---|---|---|---|---|
| `SequentialExecutor` | 本机，一次一个 | 否 | 无 | 本地调试；SQLite 元数据库只支持它 |
| `LocalExecutor` | 本机，多进程 | 否 | 有（受 CPU 限制） | 单机生产、中小规模 |
| `CeleryExecutor` | 多台机器，经 Redis / RabbitMQ 分发 | 是 | 强，可水平扩展 | 生产集群 |
| `KubernetesExecutor` | 每个任务一个 Pod | 否（Pod 即 Worker） | 强，隔离性好 | 云原生环境 |

一个实践结论：**从 SQLite 换到 Postgres 的同时，必须把 SequentialExecutor 换成 LocalExecutor**，否则并行能力仍然是零。SQLite 不支持多连接并发写，这是它只能配 SequentialExecutor 的根本原因。

### 2.4 最小 DAG

```python
from airflow import DAG
from airflow.operators.python import PythonOperator
from datetime import datetime, timedelta

default_args = {
    "owner": "data",
    "retries": 2,                          # 失败重试 2 次
    "retry_delay": timedelta(minutes=5),   # 间隔 5 分钟
}

def load_data(**context): ...
def clean_data(**context): ...

with DAG(
    dag_id="ad_daily_pipeline",
    default_args=default_args,
    start_date=datetime(2026, 10, 1),
    schedule="0 8 * * *",      # 每天 8 点（Airflow 2.4+ 推荐 schedule）
    catchup=False,             # 不自动补跑历史
    tags=["ad", "daily"],
) as dag:
    load = PythonOperator(task_id="load", python_callable=load_data)
    clean = PythonOperator(task_id="clean", python_callable=clean_data)

    load >> clean              # 依赖：load 成功后才跑 clean
```

DAG 文件的六段结构：**导入 → 定义函数 → 默认参数 → 创建 DAG 对象 → 定义 Task → 定义依赖**。这个顺序不是强制的，但按它写最不容易乱。

### 2.5 关键参数

| 参数 | 含义 | 注意 |
|---|---|---|
| `dag_id` | DAG 唯一标识 | 改名等于新建一个 DAG，历史记录不继承 |
| `start_date` | 从哪天开始产生 DagRun | 配合 catchup 决定是否回填，**不要写成 `datetime.now()`** |
| `schedule` / `schedule_interval` | 调度周期，cron 或 timedelta | 2.4 起 `schedule` 为新参数，`schedule_interval` 仍兼容但已标记弃用 |
| `catchup` | 是否自动补跑 `start_date` 到现在的所有周期 | 默认 True，容易一次性触发大量历史运行 |
| `max_active_runs` | 同一 DAG 最多几个 DagRun 并行 | 防止补数时把集群打满 |
| `retries` / `retry_delay` | 重试次数与间隔 | 放在 `default_args` 里对全部 Task 生效 |
| `retry_exponential_backoff` | 重试间隔指数增长 | 适合应对外部 API 限流 |
| `execution_timeout` | 单任务最长执行时间 | 防止挂死任务永久占用槽位 |
| `sla` | 超时告警 | 只告警，不杀任务 |
| `concurrency` / `max_active_tasks` | 并发上限 | 保护下游数据库连接数 |

### 2.6 常用进阶组件

| 组件 | 解决什么 | 用法与注意 |
|---|---|---|
| **Variables** | 全局配置：密码、文件路径、邮箱、开关 | `Variable.get("mysql_password")`；改配置不用改代码；敏感信息应放 Secret Backend 而非明文 |
| **Connections** | 外部系统的结构化连接信息（host / port / user / password） | 与 Hook 配合：`MySqlHook(mysql_conn_id="ad_mysql")`；密码不落在代码里，多个 DAG 共用 |
| **Sensors** | 等某个条件满足再往下跑 | `FileSensor` 等文件落地、`SqlSensor` 等上游分区产出；`poke_interval` 是检查间隔，`timeout` 是最长等待；长等待应使用 deferrable 模式交给 Triggerer |
| **TaskGroup** | 把相关任务打包成一组，UI 可折叠 | 按"数据准备 / 指标计算 / 输出"分组；只影响组织与展示，不改变依赖关系 |
| **BranchPythonOperator** | 按条件选择走哪条分支 | 函数返回下游 `task_id`；未选中的分支标记为 skipped，汇合处要用 `none_failed` 或 `all_done` 触发规则 |
| **Pools** | 限制某类任务的并发槽位 | 保护下游数据库连接数、限制外部 API 调用并发，避免补数时打满资源 |
| **XCom** | 任务间传小数据 | 只传路径、行数、状态标志；传 DataFrame 会撑爆元数据库 |

这些组件的共同点是：**把"配置"和"代码"分离，把"等待"和"执行"分离。** Variables / Connections 让环境差异不进代码，Sensors / Triggerer 让等待不占资源，Pools 让并发可控。

## 三、调度周期与依赖

### 3.1 cron 表达式

格式：**分 时 日 月 周**（五段）。

| 表达式 | 含义 |
|---|---|
| `0 2 * * *` | 每天 2:00 |
| `0 8 * * *` | 每天 8:00 |
| `*/10 * * * *` | 每 10 分钟 |
| `0 */2 * * *` | 每 2 小时整点 |
| `0 9 * * 1` | 每周一 9:00 |
| `0 0 1 * *` | 每月 1 日 0:00 |
| `@daily` | 等价 `0 0 * * *` |
| `@hourly` | 等价 `0 * * * *` |
| `None` | 不自动调度，只能手动触发 |

记忆规则：`*` 任意值，`*/n` 每 n 个单位，`a,b` 枚举，`a-b` 范围。

注意 Airflow 的 cron 按**UTC** 解释（除非显式设置 `timezone`），国内业务要换算成 UTC+8，例如"每天北京时间 8 点"应写 `0 0 * * *` + `timezone="Asia/Shanghai"`，或直接写 `0 8 * * *` 但把 DAG 时区设为上海。时区错了会导致数据窗口整体偏移 8 小时，是补数时最常见的坑之一。

### 3.2 任务依赖写法

```python
# 顺序：A → B → C
a >> b >> c
a.set_downstream(b)          # 等价写法

# 并行：A 完成后 B、C 同时跑
a >> [b, c]

# 汇合：B、C 都完成后才跑 D
[b, c] >> d

# 混合：A → (B, C) → D
a >> [b, c] >> d

# 反向：C 依赖 B，B 依赖 A
c << b << a

# 跨 DAG 依赖（2.4+ 的 Dataset / Asset 机制）
dag_b = DAG(..., schedule=[dataset_a])   # A 产出数据后触发 B
```

`>>` 的本质是建立 **Task 之间的上下游关系**，调度器据此判断"上游全部 success 才把下游置为 scheduled"。默认触发规则是 `all_success`，可以改：

| trigger_rule | 含义 |
|---|---|
| `all_success` | 全部上游成功（默认） |
| `all_failed` | 全部上游失败 |
| `all_done` | 全部上游结束，不管成败（常用于收尾、发通知） |
| `one_success` | 任一上游成功 |
| `one_failed` | 任一上游失败（常用于告警） |
| `none_failed` | 没有失败（允许 skipped） |

### 3.3 任务之间怎么传数据

**Airflow 的每个 Task 可能跑在不同进程、不同机器上，不能共享内存变量。**

| 方式 | 适用 | 限制 |
|---|---|---|
| **XCom** | 传小数据：路径、行数、状态标志 | 存在元数据库里，传 DataFrame 会撑爆 DB |
| **共享存储**（推荐） | 传大数据：中间结果写 Parquet / 临时表，下游读路径 | 需要约定路径规范与清理策略 |
| **外部系统** | 上游写 Redis / MySQL，下游读 | 多一层依赖，但解耦彻底 |

生产标准做法是第二种：**每个 Task 把结果落成文件（Parquet）或表分区，XCom 只传路径。** 这样任务可以独立重跑，不依赖上游是否还在内存里。

### 3.4 Context 与模板

给函数加 `**context` 就能拿到运行时信息：

| 变量 | 含义 | 用途 |
|---|---|---|
| `ds` | 逻辑日期字符串 `2026-10-01` | 拼分区路径、传 SQL 参数 |
| `ds_nodash` | `20261001` | 拼文件名 |
| `ts` | ISO 时间戳 | 日志、审计 |
| `data_interval_start` / `end` | 本次运行对应的数据窗口 | 增量抽取的边界 |
| `task_instance` | 当前任务实例 | `xcom_push` / `xcom_pull` |
| `dag_run` | 当前 DagRun | 读取 `conf` 里的手动参数 |

模板写法：`bash_command="python job.py --dt {{ ds }}"`，Airflow 会在运行时渲染。

**关键认知：`ds` 是"逻辑日期"，不是"当前时间"。** 补跑 9 月 1 日的数据时，`ds` 仍然是 `2026-09-01`，任务才能写到正确的分区。所有任务都必须用 `ds` 而不是 `datetime.now()`，这是幂等的前提。

## 四、backfill 补数

### 4.1 catchup 与 backfill 的区别

| | catchup | backfill |
|---|---|---|
| 触发方式 | DAG 配置项，调度器自动创建遗漏的 DagRun | 命令行 / UI 手动指定日期范围 |
| 范围 | `start_date` 到现在 | 任意指定区间 |
| 适用 | 新部署、停机后补齐 | 修历史数据、重算某段 |
| 风险 | 一次性创建大量运行，压垮集群 | 忘记通知下游，导致上下游数据不一致 |

```bash
# 补 9 月整月
airflow dags backfill \
  --start-date 2026-09-01 \
  --end-date 2026-09-30 \
  ad_daily_pipeline

# 只重跑某一天（先 clear 再让调度器重跑）
airflow tasks clear ad_daily_pipeline -t clean -s 2026-09-15 -e 2026-09-15
```

### 4.2 补数必须满足的三个条件

| 条件 | 为什么 |
|---|---|
| **任务幂等** | 补数本质是重跑，非幂等会写重复数据（分区覆盖写、先删后插） |
| **按逻辑日期取数** | 用 `ds` 拼分区，不能用"今天"；否则补历史会写错分区 |
| **下游一起补** | 重跑 DWD 某天，DWS / ADS 对应分区必须重算，否则口径断裂 |

### 4.3 补数的工程细节

- **限流**：补 90 天会瞬间创建 90 个 DagRun，设 `max_active_runs=3`、`max_active_tasks` 限制并发，否则会把 YARN 队列或源库连接打满。
- **顺序**：按日期从早到晚补，避免下游读到"未来的数据"再被覆盖。
- **回刷窗口**：转化回传有延迟，补数时要带上 lookback（如每次重算 `[T-7, T]`），让迟到的数据被吸收。
- **通知**：补数会改变已经发出去的报表数字，必须通知使用方，否则会出现"昨天的日报今天变了"的信任问题。
- **监控**：补数期间单独看失败率，批量重跑容易集中暴露上游接口限流、锁冲突。

## 五、为什么调度器要分容器部署

### 5.1 单机部署的问题

Airflow 不是"一个程序"，而是 **scheduler + webserver + triggerer + 元数据库 + （可选）worker** 的组合。全塞进一个进程或一台机器会出四类问题：

| 问题 | 表现 |
|---|---|
| 故障扩散 | webserver 内存泄漏或 scheduler 卡死，互相拖累，一起重启 |
| 资源争抢 | webserver 处理大量日志请求时抢走 scheduler 的 CPU，调度延迟抖动 |
| 扩展不独立 | 想加调度吞吐只能整机复制，web 和 scheduler 被迫同比例扩容 |
| 依赖冲突 | 不同角色对 Python 包、系统库的版本要求不同，装在一起互相污染 |

### 5.2 容器化的收益

```
┌─────────────┐  ┌─────────────┐  ┌─────────────┐
│  postgres   │  │  scheduler  │  │  webserver  │
│  元数据库    │  │  调度大脑    │  │  UI + API   │
└─────────────┘  └─────────────┘  └─────────────┘
                 ┌─────────────┐
                 │  triggerer  │
                 │  延迟任务    │
                 └─────────────┘
       共享：dags 卷、logs 卷、airflow.cfg
```

| 收益 | 说明 |
|---|---|
| 进程隔离 | 单个容器崩溃不影响其他角色，重启粒度小 |
| 独立扩缩容 | scheduler 压力大就多加一个（需配 HA），webserver 前面挂负载均衡 |
| 环境一致 | 镜像固定了 Python 版本与依赖，开发机和服务器行为一致 |
| 依赖隔离 | 每个角色可以用不同镜像、不同资源限制 |
| 滚动升级 | 先换 webserver 再换 scheduler，减少停机 |
| 可复现 | `docker-compose.yaml` 就是完整的环境定义，换机器一条命令拉起 |

### 5.3 一个真实的部署约束

Windows 上直接 `pip install apache-airflow` 后启动会失败，原因是 Airflow 依赖 Unix 专有模块（如 `pwd`、`fcntl`、`os.fork`），Windows 没有对应实现。这不是配置问题，是平台不兼容。

标准解法是 **Docker 容器化**：容器内是 Linux 用户态，与宿主机是 Windows 无关。

本项目的落地形态：

| 项 | 配置 |
|---|---|
| 镜像 | `apache/airflow:2.10.5-python3.12` |
| 元数据库 | PostgreSQL（`postgresql+psycopg2://airflow:airflow@postgres/airflow`） |
| Executor | `LocalExecutor`（支持同机多进程并行） |
| 容器 | postgres / scheduler / webserver / triggerer 四个 |
| 共享 | `dags/`、`logs/`、`plugins/` 挂载到各容器 |
| 权限 | `user: "50000:0"` + `AIRFLOW_UID=50000`，避免挂载目录属主错误 |

### 5.4 从 SQLite 升级到 Postgres 的四步

| 步骤 | 改动 | 原因 |
|---|---|---|
| 1 | `SequentialExecutor` → `LocalExecutor` | SQLite 只支持串行，换库后才能并行 |
| 2 | 连接串改为 `postgresql+psycopg2://...` | 元数据落到独立数据库 |
| 3 | 新增 postgres 服务 + healthcheck + 数据卷 | 元数据必须持久化，容器重启不丢状态 |
| 4 | scheduler / webserver / triggerer 的 `depends_on` 加 `condition: service_healthy` | 数据库没就绪就启动，会因建表失败而崩溃循环 |

### 5.5 部署期高频故障

| 现象 | 根因 | 处理 |
|---|---|---|
| 镜像拉取超时 | Docker Hub 直连不稳定 | 换国内镜像源 |
| `pip install` 报权限错误 | 官方镜像默认 root，Airflow 禁止 root 装包 | 切到 `USER airflow` |
| 元数据丢失 | SQLite 文件没挂到共享卷 | 改共享卷，或直接升级 Postgres |
| 挂载目录 Permission denied | 容器内 UID 与宿主机目录属主不一致 | 指定 `AIRFLOW_UID` 与 `user` |
| 任务卡在某一网络请求 | 下游服务无响应，客户端无超时 | 给 HTTP 客户端加 `timeout` + `max_retries`，避免单任务拖死整个 DAG |
| 调度延迟越来越大 | DAG 文件解析慢、元数据库膨胀 | 减少顶层代码、清理历史、加 scheduler 资源 |

最后一条值得展开：**任何外部调用都必须设超时。** 一个没有超时的 `requests.post` 可以让 Task 挂几小时，占着槽位不放，最终表现为"Airflow 卡住了"，实际是下游服务的问题。加上 `timeout=60, max_retries=2` 之后，任务失败会快速进入重试或失败状态，不会阻塞整条链路。

## 六、为什么需要消息队列

### 6.1 四个动机

| 动机 | 说明 | 例子 |
|---|---|---|
| **解耦** | 生产者不需要知道有几个消费者、消费者是谁 | 埋点服务只管发事件，推荐、风控、数仓各自订阅 |
| **削峰** | 上游瞬时流量写进队列缓冲，下游按自己的能力消费 | 大促期间订单峰值 10 万/秒，下游只能处理 2 万/秒 |
| **异步** | 主流程不等下游完成，直接返回 | 下单成功后异步发积分、发短信、写数仓 |
| **缓冲与背压** | 下游故障时不丢数据，恢复后继续消费 | 数仓集群维护 2 小时，消息在 Kafka 里保留 7 天 |

### 6.2 没有队列会怎样

```
同步直连：
埋点服务 → 数仓 API（挂了）→ 埋点服务报错 → 用户端请求失败
         → 风控服务（慢）→ 埋点服务被拖慢 → 全站雪崩
```

```
加队列：
埋点服务 → Kafka（快速写入，几毫秒）→ 数仓 / 风控 / 推荐各自消费
             ↑ 下游挂了也不影响上游，消息留在队列里
```

**消息队列把"同步调用"变成了"异步事件"，把"点对点"变成了"一对多广播"。**

## 七、Kafka

### 7.1 定位

LinkedIn 开发、后捐给 Apache 的分布式流平台。Java / Scala 编写，但使用者不需要会 Java——用 Python 的 `confluent-kafka` / `kafka-python` 客户端连接即可。

它解决的核心问题是：**海量数据流如何可靠、可回放地分发给多个下游。**

### 7.2 核心概念

| 概念 | 是什么 | 关键点 |
|---|---|---|
| **Producer** | 生产者，写数据的一方 | 决定分区策略（按 key 哈希 / 轮询）、`acks` 级别 |
| **Consumer** | 消费者，读数据的一方 | 自己维护 offset，主动拉取（pull） |
| **Broker** | Kafka 服务器节点 | 多个 Broker 组成集群，每个 Partition 有一个 Leader |
| **Topic** | 消息的逻辑分类，像一个频道 | 逻辑概念，由多个 Partition 组成 |
| **Partition** | Topic 的物理分片，**有序追加日志** | 并行度的单位；顺序只在分区内保证 |
| **Offset** | 每条消息在 Partition 内的单调递增编号 | 消费者的"书签"，提交 offset 即表示"读到这了" |
| **Consumer Group** | 一组共同消费一个 Topic 的消费者 | 组内分摊，组间广播 |
| **Replica** | Partition 的副本 | Leader 读写，Follower 同步；ISR 是"跟得上的副本集合" |

### 7.3 物理结构

```
Topic: ad_events（3 个 Partition，副本数 2）

Partition 0:  [0][1][2][3][4][5] ...   ← 只追加，不修改
Partition 1:  [0][1][2][3] ...
Partition 2:  [0][1][2][3][4] ...

每个 Partition 在磁盘上就是一组 segment 文件：
  /kafka-logs/ad_events-0/00000000000000000000.log
  /kafka-logs/ad_events-0/00000000000000012345.log
  /kafka-logs/ad_events-0/00000000000000012345.index
```

顺序写的追加日志是 Kafka 高吞吐的根本原因：**磁盘顺序写接近内存速度，且完全避免了随机寻址**。消息不因为被消费而删除，只按时间或大小过期（`retention.ms` / `retention.bytes`），所以能反复回放。

### 7.4 三个区别于普通队列的特性

**① 可回放。**
消息被消费后不会删除，Consumer 只移动自己的 offset。消费者挂了重启，从上次提交的 offset 继续读；想重算，把 offset 重置到 3 天前即可。这是 Kafka 能同时服务实时和离线重算的原因。

**② 一条消息可以被多个消费组各读一遍。**

```
                 ┌→ Consumer Group A（数仓）：consumer1 读 P0/P1，consumer2 读 P2
Topic ───────────┤
                 └→ Consumer Group B（风控）：consumer3 读全部 3 个分区
```

- **组间广播**：不同 Group 各自维护 offset，互不影响，都拿到全量。
- **组内分摊**：同一 Group 内，一个 Partition 只能分给一个 Consumer，实现并行消费。

推论：**Partition 数决定了消费并行度的上限。** 3 个分区最多被 3 个消费者有效消费，第 4 个会空闲。所以分区数要按"峰值消费能力"预估，但也不能太多（增加元数据、Rebalance 开销、文件句柄）。

**③ 分区 + 副本。**
Partition 提供并行与水平扩展，Replica 提供容错。写入时 Producer 可配 `acks`：

| acks | 含义 | 可靠性 | 延迟 |
|---|---|---|---|
| `0` | 不等确认，发出去就算成功 | 最低，Broker 挂了就丢 | 最低 |
| `1` | Leader 写入成功即返回 | 中，Leader 挂且未同步会丢 | 中 |
| `all` / `-1` | ISR 中所有副本都写入才返回 | 最高 | 最高 |

配 `acks=all` + `min.insync.replicas=2`，才能保证"至少两个副本有数据"，单 Broker 故障不丢。

### 7.5 顺序性与 Rebalance

**顺序性只在单个 Partition 内保证。** 跨 Partition 没有全局顺序。

需要"同一订单的事件按序处理"，就把 `order_id` 作为消息 key，Kafka 用 `hash(key) % partitions` 路由，同一订单永远进同一分区，从而保序。代价是可能出现数据倾斜（大 key 撑爆一个分区）。

**Rebalance**：Consumer Group 成员变化（新增、宕机、超时）时，重新分配 Partition 的过程。Rebalance 期间整个组暂停消费（Stop-The-World），频繁 Rebalance 会造成消费延迟抖动。缓解手段：合理设置 `session.timeout.ms`、`max.poll.interval.ms`，避免单批处理时间超过 poll 间隔；用静态成员（`group.instance.id`）减少滚动重启引发的 Rebalance。

### 7.6 投递语义

| 语义 | 怎么实现 | 风险 |
|---|---|---|
| At-most-once | 先提交 offset 再处理 | 处理失败会丢消息 |
| At-least-once | 先处理再提交 offset | 可能重复，**默认且最常用** |
| Exactly-once | 幂等 Producer + 事务，或下游幂等去重 | 实现复杂，跨系统难保证 |

工程上的务实做法：**Kafka 保证 at-least-once，业务侧用幂等消费兜底**（按消息唯一 ID 去重、按分区覆盖写、upsert）。追求端到端 exactly-once 通常要配合支持事务的存储（如 Flink + 两阶段提交 Sink）。

### 7.7 Kafka vs Redis 队列

| | Redis List / Stream | Kafka |
|---|---|---|
| 定位 | 轻量任务队列、缓存 | 海量数据流管道 |
| 吞吐 | 高（十万级/秒） | 极高（百万级/秒） |
| 消费后消息 | List 弹出即消失 | 保留，可回放 |
| 多消费者 | 一条被一个消费者抢走 | 多消费组各读一份 |
| 顺序 | 列表内有序 | 分区内有序 |
| 持久化 | 内存为主，RDB/AOF | 磁盘顺序写，多副本 |
| 适用 | Celery 任务分发、简单异步 | 日志、埋点、实时计算、CDC |

选型口诀：**任务是"要被执行一次"的，用 Redis / RabbitMQ；数据是"要被多个下游各读一遍"的，用 Kafka。**

## 八、Kafka 与流式计算配合

### 8.1 批处理 vs 流处理

| | 批处理 | 流处理 |
|---|---|---|
| 代表 | Spark SQL、Hive、MapReduce | Spark Streaming、Flink |
| 触发 | 定时（每天 / 每小时） | 持续运行，事件到达即处理 |
| 延迟 | 分钟到小时 | 秒级到毫秒级 |
| 数据边界 | 有界（一个分区、一段时间） | 无界（永远在增长的数据流） |
| 场景 | 日报、历史回溯、全量重算 | 实时监控、实时告警、实时 ROI 看板 |

### 8.2 Spark Streaming 的微批模型

Spark Streaming 把无界流切成小批：

```
Kafka 流 → 每 1 秒切一批 → 当成一个小 DataFrame → 用批处理 API 计算 → 输出
```

- 本质是**微批（micro-batch）**，最小延迟通常在几百毫秒到秒级。
- API 与批处理几乎一致（Structured Streaming 就是 `readStream` 替代 `read`），学习成本低。
- 用 `checkpointLocation` 记录进度，故障恢复后从 checkpoint 继续。

```python
df = (spark.readStream
      .format("kafka")
      .option("kafka.bootstrap.servers", "localhost:9092")
      .option("subscribe", "ad_events")
      .load())

query = (df.selectExpr("CAST(value AS STRING)")
          .writeStream
          .format("parquet")
          .option("checkpointLocation", "/checkpoints/ad_events")
          .option("path", "/warehouse/ods_ad_events")
          .start())
```

关键点：**checkpoint 里存的是 offset**。Spark 把"读到哪个 offset"和"输出写到哪"绑定在一起，配合幂等 Sink 实现端到端一致性。

### 8.3 Flink 的定位

Flink 是**原生流处理**：一条消息到达就处理，不做微批，延迟可到毫秒级；同时用 checkpoint 屏障（barrier）做分布式快照，配合两阶段提交 Sink 实现 exactly-once。

| | Spark Streaming | Flink |
|---|---|---|
| 模型 | 微批 | 原生流（批是流的特例） |
| 延迟 | 秒级 | 毫秒级 |
| 状态管理 | 有，相对简单 | 强（Keyed State、State Backend） |
| 事件时间 / 乱序 | 支持 watermark | 支持更完善 |
| 生态 | 与 Spark 批处理统一 | 流批一体，CDC 场景强 |

选型：**已有 Spark 体系、延迟要求秒级 → Structured Streaming；要求毫秒级、复杂事件时间语义、CDC 入湖 → Flink。**

### 8.4 典型链路

```
客户端埋点
   ↓ HTTP / SDK
埋点服务（Producer）
   ↓
Kafka Topic: ad_events（按 device_id 分区保序）
   ↓                    ↘
Spark Streaming          Flink
（秒级聚合，写 Parquet）   （毫秒级告警，写 Redis/ClickHouse）
   ↓
ODS / DWD 分区
   ↓ Airflow 调度离线任务
DWS / ADS
   ↓
BI 看板 / Agent 查询
```

**Kafka 在这条链路里是"实时层的入口 + 离线层的缓冲"**：同一份数据既被实时任务消费，也被落盘后由离线任务重算，这就是 Lambda 架构的基本形态；只用流处理一条链路同时服务实时和历史的，叫 Kappa 架构。

## 九、Redis 在数据链路里的用途

### 9.1 是什么

REmote DIctionary Server，内存 key-value 数据库。数据放内存，读写延迟在微秒到毫秒级，常同时充当**缓存**和**轻量消息队列**。

### 9.2 为什么快

| 原因 | 说明 |
|---|---|
| 数据在内存 | 内存随机读写比磁盘快几个数量级，省掉了磁盘寻址 |
| 单线程执行命令 | 没有锁竞争、没有线程切换、没有上下文切换开销 |
| IO 多路复用 | epoll 单线程管理大量连接，不是"一个连接一个线程" |
| 高效数据结构 | SDS、跳表、压缩列表、哈希表，操作多为 O(1) 或 O(log n) |
| 协议简单 | RESP 协议解析开销极低 |

**"单线程为什么还快"是高频题**：瓶颈在内存带宽和网络，不在 CPU；单线程反而消除了锁和上下文切换。Redis 6.0 之后网络读写用了多线程（IO threads），但**命令执行仍然是单线程**，所以不存在并发写冲突。

### 9.3 持久化

| 方式 | 机制 | 优点 | 缺点 |
|---|---|---|---|
| **RDB** | 定期 fork 子进程，把内存快照写成二进制文件 | 文件小、恢复快、适合备份 | 两次快照之间的数据会丢 |
| **AOF** | 追加每条写命令到日志，重启时重放 | 丢数据少（可 `appendfsync everysec`） | 文件大、恢复慢 |
| **混合**（4.0+） | RDB 快照 + 增量 AOF | 兼顾恢复速度与数据安全 | 配置略复杂 |

### 9.4 数据链路中的五类用途

#### ① 缓存：挡住热点读

```python
def get_campaign(campaign_id):
    key = f"dim:campaign:{campaign_id}"
    val = redis.get(key)
    if val:
        return json.loads(val)          # 命中，不走数据库
    row = mysql.query("SELECT * FROM dim_campaign WHERE id=%s", campaign_id)
    redis.setex(key, 300 + random.randint(0, 60), json.dumps(row))  # TTL + 随机抖动
    return row
```

这是 **Cache-Aside（旁路缓存）**：读时先查缓存，未命中查库再回填；写时更新库并删除缓存。

三个经典问题：

| 问题 | 现象 | 对策 |
|---|---|---|
| 缓存穿透 | 查一个不存在的 key，每次都打到库 | 缓存空值（短 TTL）、布隆过滤器前置拦截 |
| 缓存击穿 | 热点 key 过期瞬间，大量请求同时打到库 | 互斥锁重建、逻辑过期 + 异步刷新 |
| 缓存雪崩 | 大批 key 同时过期，或 Redis 整体宕机 | TTL 加随机抖动、多级缓存、熔断降级 |

在数仓链路里，缓存常用于**维表**：`dim_campaign`、`dim_country` 这类小表读多写少，放 Redis 可以让接口和 Agent 工具避免每次 join。

#### ② 分布式锁：保证同一件事只有一个进程在做

场景：两个 scheduler 实例同时触发同一天的补数，或者 Agent 的写操作并发修改同一个预算。

```python
# 加锁：SET key unique_value NX PX 30000
lock_key = f"lock:partition:ad_cost:{dt}"
token = str(uuid.uuid4())
ok = redis.set(lock_key, token, nx=True, px=30_000)
if not ok:
    return "另一实例正在处理"

try:
    do_etl(dt)
finally:
    # 释放：必须用 Lua 保证"判断 value 是自己 + 删除"的原子性
    redis.eval("""
        if redis.call('get', KEYS[1]) == ARGV[1] then
            return redis.call('del', KEYS[1])
        else
            return 0
        end
    """, 1, lock_key, token)
```

三个必须注意的点：

1. **必须设过期时间**，否则进程崩溃后锁永远不释放（死锁）。
2. **value 必须是唯一 token**，释放时校验，防止"锁超时后被别人拿走，自己却删了别人的锁"。
3. **业务执行时间可能超过锁过期时间**，需要看门狗自动续期（Redisson 的 watchdog），或把锁 TTL 设得足够长并在业务侧兜底。

#### ③ 去重：让重试不产生重复数据

Kafka 是 at-least-once，消费端必然要做幂等。Redis 是最轻量的去重层：

| 场景 | 结构 | 做法 |
|---|---|---|
| 消息去重 | `SET NX` + TTL | `SET msg:{id} 1 NX EX 86400`，成功才处理 |
| 用户 UV 去重 | Bitmap / HyperLogLog | `PFADD uv:20261001 user_id`，误差约 0.81%，省内存 |
| 滑动窗口限流 | ZSet | `ZADD` + `ZREMRANGEBYSCORE` + `ZCARD` |
| 布隆过滤 | Bloom（RedisBloom 模块） | 判断"一定不存在 / 可能存在"，挡住无效查询 |

去重 key 的 TTL 要覆盖"最大重试窗口"，太短会漏，太长会占内存。

#### ④ 限流：保护上游 API

渠道 API（Facebook / Google / TikTok）都有调用频控。用 `INCR + EXPIRE` 做固定窗口计数，或用 Lua 做令牌桶，把 QPS 控制在配额内，避免被封禁。这比在代码里 `sleep` 更精确，也能跨进程共享配额。

#### ⑤ 任务队列：Celery 的 Broker

```python
from celery import Celery
app = Celery("jobs", broker="redis://localhost:6379/0")

@app.task
def clean_data(channel):
    ...

clean_data.delay("douyin")   # 不是立即执行，而是把任务塞进队列
```

多台机器各跑 `celery -A jobs worker`，连同一个 Redis，Worker **主动拉取**任务（pull），天然实现负载均衡。

Redis 当队列用 List：`LPUSH` 入队、`BRPOP` 出队（阻塞式，避免空轮询）。**但 List 没有 ack 机制**：消费者取走消息后崩溃，消息就丢了。需要可靠消费时用 Redis Stream（有消费者组和 ack），或者直接上 Kafka。

### 9.5 分布式执行的三个组件

```
大脑（Scheduler）      → 拆任务、派任务
中间协调者（消息队列）  → 任务放这里，Worker 来领
一群工人（Worker）      → 各自领任务、执行
```

**消息队列是灵魂**：Worker 主动拉取而不是被点名分配，谁空闲谁多干，天然负载均衡；新增 Worker 只需连上同一个队列，无需改调度端配置。

生产部署形态：

```
机器 1：scheduler + webserver
机器 2：Redis / RabbitMQ（Broker）
机器 3~5：airflow worker（连同一个 Broker）
```

### 9.6 Redis 需要掌握到什么程度

概念题要能答：**为什么快、单线程为何不慢、RDB 与 AOF 的区别、缓存三大问题、分布式锁的三个坑**。不需要背源码和底层结构。真正的战场在 Spark、数仓建模和 SQL 优化。

## 十、部署视角

**部署 = 把软件从本地搬到服务器，装依赖、配参数、启动进程、对外提供服务。**

| 组件 | 默认端口 | 部署形态 |
|---|---|---|
| MySQL | 3306 | 系统服务 / 容器 |
| PostgreSQL | 5432 | 系统服务 / 容器（Airflow 元数据库） |
| Redis | 6379 | 系统服务 / 容器 |
| Kafka | 9092 | 容器 / 集群 |
| Airflow Webserver | 8080 | 容器 |
| FastAPI | 8000 | 容器 / uvicorn |

所有组件的本质一样：**在服务器上各占一个端口、各跑一个进程、互相配合。** 用什么语言写和要不要会那种语言是两码事——Kafka 用 Java/Scala 写、Redis 用 C 写，但数据工程师始终用 Python / SQL 操作它们。

## 面试速查

- **Airflow 管哪三件事？** → 定时触发、任务编排（依赖）、状态监控与重试。
- **Airflow 和 crontab 的区别？** → crontab 只到点执行命令，Airflow 还管依赖、状态、重试、可视化和补数。
- **Airflow 是 ETL 工具吗？** → 不是，它是调度编排器，清洗逻辑写在自己的 Python / SQL 里。
- **DAG / Task / Operator / DagRun 分别是什么？** → 管道定义、图中的一个步骤、步骤的执行模板、一次运行实例。
- **Scheduler 和 Executor 的区别？** → Scheduler 决定"该不该跑"，Executor 决定"在哪、怎么跑"。
- **Triggerer 干什么？** → 跑 deferrable operator，用事件循环等待外部条件，等待期间不占 Worker 槽位。
- **LocalExecutor 和 CeleryExecutor 的区别？** → 前者本机多进程，后者把任务分发到多台 Worker，可水平扩展。
- **为什么 SQLite 只能配 SequentialExecutor？** → SQLite 不支持多连接并发写，无法支撑并行任务的状态更新。
- **`>>` 是什么？** → 依赖箭头，表示左边成功后右边才能跑。
- **怎么表示并行和汇合？** → `a >> [b, c]` 并行，`[b, c] >> d` 汇合。
- **cron `0 2 * * *` 什么意思？** → 每天 2:00；格式是分 时 日 月 周。
- **catchup 是什么？** → 是否自动补跑 `start_date` 到现在的历史周期，默认 True，容易一次性触发大量运行。
- **backfill 和 catchup 的区别？** → catchup 由配置自动补，backfill 是手动指定区间补。
- **补数必须满足什么？** → 任务幂等、按逻辑日期 `ds` 取数、下游一起重算。
- **Task 之间怎么传数据？** → 大数据落共享存储传路径，小数据用 XCom，不要用 XCom 传 DataFrame。
- **为什么调度器要分容器部署？** → 故障隔离、独立扩缩容、依赖隔离、滚动升级、环境可复现。
- **Windows 为什么不能直接跑 Airflow？** → 依赖 `pwd`、`fcntl` 等 Unix 专有模块，必须用 Docker/WSL。
- **任务卡住不动，最先查什么？** → 外部调用有没有设超时，以及下游服务是否无响应。
- **为什么需要消息队列？** → 解耦、削峰、异步、缓冲与背压。
- **Kafka 的 Topic / Partition / Offset 是什么？** → 逻辑分类、物理分片（有序追加日志）、分区内的消息编号。
- **Kafka 为什么能回放？** → 消息消费后不删除，只按保留策略过期，消费者靠 offset 自行定位。
- **Kafka 怎么保证顺序？** → 只保证分区内有序，把业务 key 作为消息 key 路由到同一分区。
- **Consumer Group 的组内和组间行为？** → 组内分摊（一个分区只给一个消费者），组间广播（各自读全量）。
- **Partition 数和消费者数的关系？** → 有效消费并行度上限等于分区数，多出的消费者会空闲。
- **acks 三个级别？** → 0 不等确认、1 Leader 确认、all 全 ISR 确认；可靠性递增，延迟也递增。
- **Kafka 的投递语义？** → 默认 at-least-once，靠下游幂等去重兜底；exactly-once 需事务或幂等 Producer。
- **Kafka 和 Redis 队列怎么选？** → 任务分发用 Redis，海量数据流、多下游、需回放用 Kafka。
- **Spark Streaming 的模型？** → 微批，把流切成小批次用批处理 API 算，checkpoint 记录 offset。
- **Spark Streaming 和 Flink 的区别？** → 微批（秒级）vs 原生流（毫秒级）；Flink 的状态管理和事件时间语义更强。
- **Redis 为什么快？** → 内存存储、单线程无锁无切换、IO 多路复用、数据结构高效。
- **Redis 单线程为什么还快？** → 瓶颈在内存和网络不在 CPU，单线程反而省掉锁和上下文切换开销。
- **RDB 和 AOF 的区别？** → RDB 是定期快照（恢复快、可能丢一段），AOF 是命令日志重放（丢得少、文件大）。
- **缓存穿透 / 击穿 / 雪崩？** → 查不存在的 key / 热点 key 过期 / 大批 key 同时失效，分别用空值缓存、互斥重建、TTL 抖动。
- **Redis 分布式锁要注意什么？** → 必须设过期、value 用唯一 token、Lua 原子释放、必要时看门狗续期。
- **Redis 怎么去重？** → `SET NX` + TTL 做消息去重，Bitmap / HyperLogLog 做 UV 去重。
- **Redis List 当队列有什么缺陷？** → 没有 ack，消费者取走后崩溃会丢消息；可靠消费要用 Stream 或 Kafka。
