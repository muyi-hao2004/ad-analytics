## 〇、这二十轮其实是一条线

看起来问了四件不相关的事：数据存在哪、怎么评测、agent 怎么搭、训练数据怎么弄。其实是从下往上的四层，每层回答同一个问题的不同部分——**怎么让数据变成可靠的能力**。

| 层 | 回答的问题 | 核心词 | 对应笔记 |
|---|---|---|---|
| **0 存储** | 数据放在哪，怎么被认出来 | Hive / Metastore / 对象存储 | 10、11 |
| **1 评测** | 怎么知道它做得好不好 | label / dev-holdout / 判断层 | 24 |
| **2 Agent 工程** | 怎么把模型变成能干活的系统 | 脚手架 / 护栏 / 工具集 | 17、18 |
| **3 训练数据** | 怎么让模型本身变强 | 去重 / 配比 / 质量判定 | 本篇 §3 |

**顺序不能倒**，而且每一层都卡在下一层下面：

- 没有 0，谈不了 1——数据自己都没落稳，评测分数是浮的
- 没有 1，谈不了 2——不知道"改好了"长什么样，改就是瞎改
- 没有 1，也做不了 3——训练数据的好坏只能靠评测来判

这也是为什么很多团队卡住：直接跳到第 2 层做 agent，做了半年发现没法回答"现在这一版比上一版好吗"。

## 一、第 0 层：存储

### 1.1 一句话骨架

> **一张表 = 一堆文件 + 一条登记。**

文件在 HDFS / 对象存储上，登记在 MySQL 里。两者缺一，表就不存在。

### 1.2 三层元数据（解开全部混乱的钥匙）

这一条是整轮答疑里最关键的一张表。前面之所以反复绕，是因为我把三个不同粒度的东西都叫成"元数据"。

| 层 | 回答什么 | 存在哪 | 谁管 |
|---|---|---|---|
| **第一层 文件自述** | 这个文件里有哪些列 | parquet 文件内部（头尾） | 文件格式 |
| **第二层 表定义** | 表叫什么、几个字段、数据在哪个**目录** | MySQL 里的**一行** | Hive Metastore |
| **第三层 版本清单** | 当前这一版由哪几个**文件**组成 | 数据目录旁边的 `metadata/` | 表格式（Iceberg / Delta） |

**Hive 只有前两层，Iceberg / Delta 补的是第三层。**

第二层只记到"目录"就停了：它说"数据在这个文件夹里"，但文件夹里到底有几个文件、哪些是刚写坏的，它不知道。第三层补的就是这个缺口。

### 1.3 为什么三样东西要分三个地方存

| 东西 | 特征 | 所以放哪 |
|---|---|---|
| 数据文件 | 体量大，要顺序扫 | HDFS / S3 |
| 表定义 | **一表一行，但一天改几百次，二十个任务抢着改** | 关系库（事务、行锁） |
| 版本清单 | **每次写入新增一个，写完不动，且必须跟数据一起原子提交** | 数据旁边 |

准确的规则不是"元数据必须放数据库"，而是：

> **访问模式决定存储选择。需要高频读写的状态留在事务型数据库；写完就不动、且要和数据一起提交的，放数据旁边。**

这条也解释了 Iceberg 为什么不推翻"元数据不能放 HDFS"——它只挪走了大块元数据，"当前最新快照是哪个"这个指针仍然在数据库里。

### 1.4 HDFS 与对象存储：四个会咬人的差异

同一类东西（都是底层存储），但设计目标几乎相反。

| 差异 | 后果 |
|---|---|
| **没有 rename** | 写 `_temporary/` 再改名的原子提交技巧失效 → Iceberg 改成"写新快照 + 切指针" |
| **按请求计费** | 小文件问题从"慢"变成"又慢又贵" |
| **没有数据本地性** | Spark on S3 的瓶颈从 CPU 变成网络和出口费用 |
| **不能 append** | 流式写入必须先攒批，不能边写边加 |

### 1.5 四层的物理落点

**四层数据全在同一块存储上，只是四个目录。** 不是四台机器、四个数据库。

```
warehouse/ods.db/表名/dt=2026-10-19/part-00000.parquet
          ↑库   ↑表      ↑分区         ↑任务编号
```

- 库名 → 目录，表名 → 目录，分区 → 子目录
- `part-00000` 是任务编号：200 个并行任务 = 200 个文件 = 小文件问题的来源
- **只有 ADS 例外**，必须再复制一份到 MySQL / Doris / ClickHouse 供 BI 点查

成本分布：ODS 只存一个月，ADS 很小，**DWD 占七成以上**。所以要讨论压缩格式和分区粒度，讨论的通常是 DWD。

### 1.6 三个能自己验证的判断

| 现象 | 说明什么 |
|---|---|
| `DESCRIBE` 正常，`SELECT` 报 FileNotFound | 元数据在，数据不在 → 两套系统 |
| Metastore 挂了，正在跑的任务照跑 | 读数据全程不经过 MySQL |
| 表删了文件还在 | 内部表删登记 + 删文件；外部表只删登记 |

## 二、第 1 层：评测

### 2.1 评测的第一个问题不是"怎么算分"

是"**答案从哪来**"。

| | 外生 label | 内生 label |
|---|---|---|
| 谁定的 | 数据集自带 | **必须人定义** |
| 例子 | 破产预测的 label、pytest 过不过 | 这个渠道"该不该删" |
| 评测的工作量在哪 | 基本不用辩护 | **全部在为答案的合法性辩护** |

你论文里的 XGBoost 是外生 label：数据集告诉你哪家公司破产了，你只需要把模型拟合上去。
Agent 评测是内生 label：没有任何数据集告诉你"这条渠道该删"，你得先把这个判断写成规则，才谈得上评测。

**记住这个分野**，它后面还会出现两次（§3.1 训练数据、§4 Agent 自研决策），是全篇出现频率最高的概念。

### 2.2 两套指标，别混

| 类型 | 主指标 | 用在哪 |
|---|---|---|
| **决策评测** | 混淆矩阵 → precision / recall / F1 | 分类、该不该做某个动作 |
| **检索评测** | recall@k、MRR、nDCG | RAG 的召回质量 |

为什么准确率会骗人：样本不平衡时，全判"不动"也能有 90% 准确率。所以要拆开看漏判和误判的代价。

### 2.3 三个会毁掉分数的东西

| 陷阱 | 机制 | 防法 |
|---|---|---|
| **test set leakage** | 反复看着同一批题改，改到全过，这批题就变成训练集 | dev / holdout 分离；**holdout 是消耗品**，看过一次就作废 |
| **单次跑** | 单次 p=0.9，连对 3 次只有 0.73 | `--repeat 3`，报 pass^k 不报单次 |
| **噪声** | 什么都没改，分数自己会动 | 多 seed，**信号 > 噪声才算发现** |

### 2.4 判断层 vs 生效层

这是你自己项目里踩出来的一个维度，比"过没过"信息量大得多：

| | 决定了正确动作 | 决定了错误动作 |
|---|---|---|
| **执行了** | 真本事 | 事故 |
| **被拦住** | 过度拦截 | 护栏有效，但想法错了 |

于是有四格。你测出来的"判断层 0/3、生效层 3/3"，翻译成人话就是：

> **护栏拦住的是后果，不是想法。**

这句话很重要，因为它同时说明护栏的价值（不出事）和它的边界（不会让模型变聪明）。

### 2.5 过度拦截：防御必须双向验证

只测"该拦的拦住了没有"是不够的，还要测"该放的放过没有"。否则最安全的做法是把所有动作都拒掉——分数满分，业务死掉。

### 2.6 硬判定 vs 软判定

| | 硬 | 软 |
|---|---|---|
| 手段 | 断言、pytest、查最终状态 | LLM 打分、人评审 |
| 优点 | 无歧义、可复现、便宜 | 能测开放式任务、能解释 |
| 缺点 | 只能测结果，测不出原因 | 有偏差、不稳定、贵 |

Terminal-Bench 把这条做到极端：**判分只看最终状态，一道题 10 个测试过 9 个也是 0 分，没有部分分。** 它测的是"能不能交付"，不是"做了多少"。

它和你的 eval 唯一的实质区别就在这里——**它用 pytest，你用 LLM judge**。所以你会看到"判断层 0/3、生效层 3/3"这种分裂，而它不会有。

顺带一条可直接用的改进：能写成断言的地方就别让模型判。"该拒的拒了没有""该删的真删了没有"，一行 `assert` 就够，而且再也不会因为桩数据串位而误判。

### 2.7 公开榜单怎么读

**四种失效模式**（其实都能映射到你熟悉的东西上）：

| 失效 | 机制 | 你的对应物 |
|---|---|---|
| 数据污染 | 测试题混进训练集 | test set leakage |
| 题目饱和 | 分数顶到 90+，分不开 | —— |
| 刷榜 | 针对榜单调优而非真变强 | overfitting to the eval |
| 判分偏差 | 长回答、Markdown 表格得分高 | LLM judge 的偏好 |

**Elo / Bradley-Terry 的本质**：分数不是"答对多少题"，是**对战胜率的压缩表示**。1525 对 1507，等于打 100 场赢 52.6 场。而且分数是相对的，锚定在当前池子里，**跨时间比没有意义**。

**读榜五步**：先看置信区间（重叠 = 打平）→ 看票数和是否 preliminary → 看专项榜不看综合 → 看每任务成本不看 token 单价 → 看版本号。

## 三、第 2 层：Agent 工程

### 3.1 agent = 模型 + 脚手架

模型只会一件事：**给一段文本，吐下一段文本。**

但"自己干活"还缺：记住前面做了什么、知道能用哪些工具、把中文意思变成函数调用、判断该不该执行、知道什么时候停。**这些全在脚手架里。**

### 3.2 脚手架的九件套

| 组件 | 作用 | 你项目里的对应物 |
|---|---|---|
| 系统提示词 | 角色、规矩 | `SYSTEM_PROMPT` |
| 工具定义 | 能用什么、参数怎么填 | `mcp_server.py` |
| 上下文组装 | 每轮塞哪些信息 | `_current_context_for()` |
| 输出解析 | 从文本里读出"要调哪个工具" | function calling 解析层 |
| 执行器 | 真去调函数、写库 | `_execute_action()` |
| 循环控制 | 继续还是停，最多几轮 | `run()` 的 while |
| **上下文管理** | 太长时怎么压缩 | **你还没有** |
| **错误恢复** | 工具报错后重试还是放弃 | **你还没有** |
| 护栏 | 执行前拦一道 | `guardrails.py` |

### 3.3 脚手架好坏是三层，不是一层

| 层 | 决定什么 | 是否影响分数 |
|---|---|---|
| **设计** | 模型看到什么、能做什么、什么时候停 | **直接影响，决定天花板** |
| **实现** | 有没有 bug、边界对不对、会不会漂移 | 不改变行为，但**决定分数是真是假** |
| **工艺** | 类型、测试、分层、命名 | 不影响分数，**决定你还能迭代几次** |

四象限：设计好 + 代码好（能长期跑）／设计好 + 代码糙（能跑，改不动）／设计差 + 代码好（跑分低，且查不出原因）／设计差 + 代码糙（demo）。

最容易忽略的是**实现层**：

> **脚手架 bug 最坏的地方，不是让 agent 干错事，是让你失去判断脚手架好坏的能力。**

你那个 `s03_metric` 不区分 `obj_id` 的桩 bug 就是标本——它没让 agent 干错任何事，它让报表从真 PASS 变成假 FAIL。不修的话你会去改护栏，越改越乱。

### 3.4 prompt 与护栏：建议 vs 强制

| | prompt | 护栏 |
|---|---|---|
| 性质 | **建议** | **强制** |
| 影响 | 想不想做 | 能不能做成 |
| 拦得住 | 通常情况 | **一定** |
| 改一次的成本 | 重跑评测 | 改代码 + 单测 |

实测结论（你做过对照实验）：给 prompt 加一条硬性规则，S02 从 0/3 到 2/3，**然后模型改成降预算绕过去了**。

所以：

> **prompt 不是无效，是"降到 2/3 就到底"。模型遵守字面，但会绕过语义。**

这就是自动化系统必须把约束放进执行层的原因——没有人盯着每一轮输出。

### 3.5 内生 label 决定"必须自研"

这个问题绕回 §2.1。看两个场景：

| | 编码 agent | 投放决策 agent |
|---|---|---|
| label | **外生**：pytest 说了算 | **内生**：该不该删必须人定 |
| 工具 | 标准化的：文件、终端、git | 私有的：渠道 ID、预算接口 |
| 能否产品化 | 能 | 不能 |

> **外生 label 的任务能做成产品，内生 label 的任务必须自己搭。**

不是因为技术难度，是因为**答案不在公共领域**。

### 3.6 公司自研的五档光谱

不是"买"和"造"二选一：

| 档 | 做法 | 场景 | 代价 |
|---|---|---|---|
| 1 | 直接用产品（Claude Code / Cursor） | 编码、通用办公 | 数据出内网 |
| 2 | 云厂商 agent 平台（Bedrock / Vertex / 百炼） | 业务 agent 快上线 | 被平台绑住 |
| 3 | 开源框架（LangGraph 等） | 要检查点、人工审批 | 多一层看不见的抽象 |
| 4 | 裸循环自研 | 场景窄、要全掌控 | 上下文管理自己写 |
| 5 | 私有化模型 + 全自研 | 金融、医疗 | 模型落后一档 |

**多数公司停在第 2 或第 3 档。** 第 5 档往往不是技术选择，是合规逼出来的。

### 3.7 能买的与买不到的

| 买得到（所有公司一样） | 买不到（公司私有资产） |
|---|---|
| 模型 API | **工具集**（内部系统接口） |
| 循环框架 | **判断标准**（什么算对） |
| 通用工具（文件/终端/搜索） | **护栏**（谁不能做） |
| 可观测性 | **评测集**（怎么算变好） |

外面一圈换供应商只要改配置；里面那圈**不是软件，是业务本身**。

两条补充：

1. **开源框架不是"买"，是 `pip install`。** 真正花钱买的是托管平台和工作流产品，卖的是"不用自己维护"。
2. **免费不等于零成本**，有三笔隐形账单：接入业务（估算占 5 倍工作量）、运维升级、迁移锁定（用它的 DSL 写了几千行业务逻辑后想换就是重写）。

一个实用判断：**你的工具是标准 HTTP API 吗？** 是 → 平台省事；不是（内网库、私有协议）→ 只能选框架。

### 3.8 云边界：三个问题，不是两个

判断数据安全，要依次问：

1. **数据会离开我控制的系统吗？** → 决定部署方式
2. **会离开国境吗？** → 决定选境内外服务商
3. **内容里有个人信息吗？** → 决定要不要脱敏

"上云"和"出内网"是**两个独立维度**，可两两组合：

| | 不出内网 | 出内网 |
|---|---|---|
| **上云** | 云上 VPC + 私有化模型 | 调公有 API |
| **不上云** | 自己机房跑开源模型 | 自己机房连外网调 API |

**云托管能说"不出内网"，靠的是三层叠加，不是物理隔离**：账号隔离（机器是别人的，但在你的 VPC 里）+ 私有通道（PrivateLink / 专线）+ 合同条款（不训练、不持久化、不共享）。

顺带纠正一句常见说法：很多公司说"数据不能出内网"，实际意思是"不能出我们控制的系统"。这两个要求差很远，后者可以用云，成本低一个量级。

## 四、第 3 层：训练数据工程

### 4.1 与数仓的六个分野

**根本差别不在工具，在目标函数**：

> 数仓关心「这个数字对不对」，训练数据关心「这批数据训出来的模型行不行」。

| 维度 | 数据工程（数仓） | 训练数据工程 |
|---|---|---|
| 数据单位 | 行、表、分区 | **样本**（input-output 对） |
| schema | 建表时固定 | 常常没有，长出来的 |
| 核心工序 | 抽、清洗、关联、聚合 | **过滤、去重、配比、合成** |
| 质量定义 | 准确、完整、一致、及时 | 正确、多样、难度合适、无污染 |
| 怎么验证 | 跟源系统核对 | **训个模型跑评测** |
| 产出物 | 一张表 → 报表 | **数据集版本 + 数据卡** |

三条反直觉的：

1. **处理原则几乎相反。数仓怕丢数据，训练数据怕留垃圾。** 删掉 92% 是标准动作。
2. **数仓能对账，训练数据没有可核对的对象。** 好不好只能训完才知道，而这要花几千美元。
3. **数仓改一行 SQL 就重算，训练数据改一次就重训。** 所以核心不是"跑得快"，是**尽量少做无用实验**。

### 4.2 schema 在训练数据里是长出来的

原始样本只有 `{"text", "url"}`，每道工序加一个字段：

| 工序 | 新增字段 |
|---|---|
| 语言识别 | `lang` |
| 规则过滤 | `passed_rules`, `reject_reason` |
| 质量分类器 | `quality_score` |
| 去重 | `dup_cluster_id` |
| 难度打分 | `difficulty_band` |
| 配比采样 | `source_weight` |

后果很直接：30% 样本有 `quality_score`、70% 没有，下游全得写兼容分支。**这是训练数据 pipeline 出 bug 的主要来源之一。** 成熟做法是加一份 JSON Schema 强制校验——本质是把缺的"建表语句"补回来。

### 4.3 去重：三级漏斗

| 级别 | 方法 | 抓什么 | 成本 |
|---|---|---|---|
| L1 | xxhash 整段指纹 | 转载、镜像、同一篇文章被不同 URL 抓到 | O(N)，一行 Spark |
| L2 | **MinHash + LSH** | 改几个字的近似重复 | 签名 128 维，比较降到常数级 |
| L3 | 后缀数组找长公共子串 | **跨文档的整段抄袭**（前面加段导语就绕过了 L1/L2） | 最难分布式 |

L2 的原理值得记住：

- **MinHash**：两个集合各自的最小哈希值相同的概率 = 它们的 Jaccard 相似度。128 个哈希函数 → 128 个整数 → 几万个 5-gram 压成 128 个数。
- **LSH**：把 128 维切成 16 个 band，任一 band 全同就进候选。Jaccard 0.9 的几乎必被抓到（99.99%），0.3 的几乎不产生候选（0.1%）。
- **band 数决定门槛**：band 多 → 严（宁可漏不可错杀）；band 少 → 松。

为什么值得花这么大力气：

> **重复样本让模型把"出现 50 次的废话"当成比"出现 1 次的真理"更重要。** 而且去重是**唯一一个只减成本、不减效果**的工序——去掉重复，训练反而更快更好。

### 4.4 配比：没有公式，只有实验

"配比"= 各来源各占多少 token。它没有解析解，因为目标函数是多维的（代码/中文/推理/长文本）且此消彼长。

标准做法七步：定源清单 → 定预算 → 用 Dirichlet 随机生成 10–20 组配比 → 各组各训一遍 → 固定 benchmark 评分 → 找 Pareto 前沿 → 大模型验证 2–3 组。

**最容易犯的错：没锁 token 预算。** A 训 100B、B 训 200B，比出来的差距是 token 量的功劳，跟配比无关。

**第二个容易忽略的：配比不是静态值，是分段时间函数。**

| 阶段 | 占比 | 构成 |
|---|---|---|
| 主体预训练 | 90% | 网页为主 |
| 中期 | 5% | 提高代码和数学 |
| 退火（annealing） | 5% | 只要高质量精选，学习率衰减到 0 |

同一份数据放在开头浪费（模型学不动），放在末期收益极大。

### 4.5 样本级质量：四道闸，成本递增

| 闸 | 手段 | 成本 | 关键点 |
|---|---|---|---|
| 1 | 规则（词数、符号比、停用词占比、重复 n-gram） | 0 | Gopher/C4 那套经典判据可直接抄 |
| 2 | 小分类器（fastText 就够） | 低 | 正样本用 Wikipedia/书籍，学的是"像不像正经内容" |
| 3 | 强模型打分（0–5 教育价值分） | **高，百万次调用** | **先人工标 500 条算 kappa**，一致性只有 0.4 就说明判据没定义清 |
| 4 | 难度分层（PPL 或通过率） | 中 | 取中间段，见 §4.7 |

**不要一上来就用大模型打分。** 用免费的先把明显垃圾砍掉，能给后面省一个数量级的调用量。

### 4.6 实验设计：四条纪律

一次训练几千美元几天时间，你只能做几十次，但要判断"哪批数据更好"。

1. **小模型 proxy**：0.3–1B 参数跑实验。趋势（A 比 B 好）能迁移，绝对值不能。
2. **一次只改一个变量**：否则赢了说不出是谁的功劳（这就是消融 / ablation）。
3. **2–3 个随机种子**：换 seed 分数波动 0.3–0.5% 是常态，差距只有 0.2% 就是噪声。
4. **看早期信号**：loss 早期斜率、前 10% token 的下游分数，通常已经分得出胜负。

**什么结论算可信**：同一结论在 **2 个 seed × 2 个 benchmark** 上都成立。只满足一条的叫"观察到的现象"，不能写进数据卡。

### 4.7 三个度量词，每个都有一个坑

| 词 | 是什么 | 坑 |
|---|---|---|
| **tokenizer** | 把文本切成高频片段再映射成整数的程序。切法由**词表**决定，不是语言学规则 | 中文早期 1 字占 2–3 token；同样"1T token"，不同 tokenizer 含义不同 |
| **PPL（困惑度）** | 模型平均在多少个词之间犹豫，`exp(平均交叉熵)` | **不能跨模型比**（分母 token 数不同）；**高 PPL ≠ 质量差**（艰深数学 PPL 高但质量高） |
| **噪声** | 什么都没改时结果自己的波动 | 固定 seed 看不到噪声，**必须换 seed 才暴露** |

PPL 的正确用法是**分难度**不是**评质量**：

- 极低（模型早会了）→ 丢弃或降权
- 中间段 → **保留，收益最高**
- 极高 → 可能是太难，也可能是乱码，**必须抽样看一眼**

质量分决定"要不要"，PPL 决定"什么时机喂"。高质量但 PPL 极高的数据不该扔，该放到退火阶段。

一个措辞校准：**seed 不是"记录"随机条件，是"生成"随机条件的起点。** 固定它为了复现，更换它为了测噪声——同一个工具，两个相反方向。

### 4.8 特征工程搬到哪去了

**没死，位置往上移了一层。**

| 原来叫 | 现在叫什么 | 在哪干 |
|---|---|---|
| 特征工程 | 数据工程（过滤、去重、配比） | 预训练前 |
| 特征选择 | 数据配比与难度分层 | 配比实验 |
| 特征交叉 | **模型自己学**，不用人做了 | 训练中 |
| 线上特征拼接 | **context engineering**（切块、top-k、few-shot 选择） | 推理时 |

> **从"人工构造单个样本的输入"，上移成"人工构造整个数据分布"。**

你项目里两条线都是：`dws` 层算 ctr/cvr 是传统特征工程；Agent 的 `_current_context_for` 组装上下文是新形态的特征工程。**不是两种技能，是同一种判断力的两个尺度。**

## 五、一条贯穿全部的线

把四层摊平看，会发现每个环节都在做同一件事：

> **定义"什么算对"。**

| 层 | "什么算对"具体是什么 | 谁定 |
|---|---|---|
| 存储 | 业务口径（ROI = 收入 ÷ 花费） | 业务方 |
| 评测 | label | 必须人定 |
| Agent | 判断标准（installs < 100 不许删） | 必须人定 |
| 训练数据 | 质量判据、什么算重复 | 必须人定 |

而且**全都是内生 label**——没有哪一层能靠"数据自带"混过去。这就解释了一个反复出现的现象：每个环节最难的都不是写代码，是**把一句模糊的业务判断变成一条可执行的检查**。

> 这句话写不出来，后面所有工程都是空转。

## 六、面试能直接用的三句

**1. 关于存储**
> 一张表是"文件 + 登记"。元数据分三层：文件自述在文件里，表定义在 Metastore 一行（只记到目录），版本清单在数据旁边（记到具体文件）。Hive 只有前两层，Iceberg 补的是第三层。分开放的依据是访问模式——表定义高频改、要并发，所以放关系库；版本清单写完不动、要和数据原子提交，所以放数据旁边。

**2. 关于护栏与评测**
> prompt 是建议，护栏是强制。我实测过：给 prompt 加一条硬性规则，某个场景从 0/3 提到 2/3，但模型改成降预算绕过去了——它遵守字面，绕过语义。所以约束必须放在执行层。评测上我分判断层和生效层两列，出现过"判断层 0/3、生效层 3/3"，说明护栏拦住的是后果不是想法。

**3. 关于训练数据**
> 训练数据和数仓的目标函数不同：数仓关心数字对不对，训练数据关心训出来的模型行不行。最反直觉的一条是主动扔掉 90% 的数据往往训出更好的模型——去重是唯一一个只减成本不减效果的工序。而每个环节的判断标准（什么算重复、什么算高质量、什么算变好了）都得人先定，因为没有可核对的对象，只能训个模型看效果。
