## 一、Airflow DAG 写法

### 1.1 什么是DAG
- DAG = 有向无环图，就是任务流程图
- 把一个大流水线拆成多个小任务，每个任务独立运行
- 用 `>>` 定义任务依赖关系（先跑左边，再跑右边）

### 1.2 DAG文件的基本结构
1. 导入模块（DAG、PythonOperator、datetime等）
2. 写Python函数（你要执行的任务逻辑）
3. 定义默认参数（重试、邮箱等公共配置）
4. 创建DAG对象（名字、定时时间、开始日期等）
5. 定义任务（每个任务做什么）
6. 定义任务依赖（谁先跑谁后跑）

### 1.3 核心参数
| 参数 | 意思 |
|------|------|
| `dag_id` | DAG唯一名字 |
| `schedule_interval` | cron表达式，定时执行时间 |
| `start_date` | 从哪天开始 |
| `catchup=False` | 不补跑历史任务 |
| `retries` | 失败重试次数 |
| `retry_delay` | 重试间隔 |

### 1.4 任务之间怎么传数据
- Airflow每个任务是独立运行的，不能直接共享内存变量
- 每个任务把结果存成文件（推荐Parquet），下一步从文件读
- 这也是生产环境的标准做法

## 二、数据仓库分层

### 2.1 四层结构
| 层级 | 英文 | 中文名 | 做什么 |
|------|------|--------|--------|
| ODS | Operational Data Store | 原始层 | 原始数据原样存，不改 |
| DWD | Data Warehouse Detail | 明细层 | 清洗、去重、格式统一 |
| DWS | Data Warehouse Summary | 汇总层 | 按维度聚合，算好常用指标 |
| ADS | Application Data Service | 应用层 | 直接给报表/API用的结果 |

### 2.2 为什么要分层
1. **复用**：干净数据多个下游共用
2. **统一口径**：指标只算一次，所有人查的都一样
3. **易维护**：改清洗规则只改ODS→DWD那步
4. **可追溯**：出问题了一层层往上查
5. **性能好**：查询直接读汇总表，不用扫原始数据

### 2.3 对应到我们的项目
| 项目代码 | 对应层级 |
|---------|---------|
| `data/raw/` 原始CSV | ODS层 |
| `clean_ad_data()` 清洗后数据 | DWD层 |
| `group_by_dimension()` 渠道汇总 | DWS层 |
| 生成的HTML日报 | ADS层 |

## 三、ETL核心概念

### 3.1 全量加载 vs 增量加载
| | 全量加载 | 增量加载 |
|---|---------|---------|
| 做法 | 每次全部重新算 | 只处理新增数据 |
| 优点 | 简单，不会错 | 快，省资源 |
| 缺点 | 数据量大了很慢 | 复杂，历史数据改了不会自动修正 |
| 适用 | 数据量小 | 数据量大、每天有新数据 |

### 3.2 幂等性
- **定义**：同一个任务跑一次和跑十次，结果一样
- **为什么重要**：Airflow失败会自动重试，不幂等就会重复计算
- **怎么实现**：
  - 先删后插（按日期删除再插入）
  - 主键去重（ON DUPLICATE KEY UPDATE）
  - 分区覆盖写

### 3.3 失败重跑
- 不用从头来，从失败的那步接着跑
- 每个任务的成功/失败状态都存在数据库里

## 四、Kafka 基础概念

### 4.1 什么是Kafka
- 一个"消息队列"，专门用来实时传输大量数据
- 解耦生产者和消费者，生产者扔数据进去，消费者自己取

### 4.2 核心概念
| 概念 | 一句话解释 |
|------|-----------|
| Topic | 数据的分类标签 |
| Partition | 把数据分成多块，并行处理 |
| Producer | 往Kafka里写数据的 |
| Consumer | 从Kafka里读数据的 |
| Consumer Group | 一组消费者，共同消费一个Topic，每条消息只处理一次 |
| Offset | 消息在Partition里的编号 |

### 4.3 关键特点
- 同一个Partition内消息有序，不同Partition之间不保证顺序
- 不同Consumer Group之间独立，各自消费一份完整数据
- Partition数量 >= Consumer数量（多了也没用）

## 五、Spark Streaming 基础

### 5.1 批处理 vs 流处理
| | 批处理 | 流处理 |
|---|--------|--------|
| 代表 | Spark SQL、Hive | Kafka + Spark Streaming/Flink |
| 频率 | 每天/每小时跑一次 | 每秒/毫秒级处理 |
| 延迟 | 小时级/天级 | 秒级/毫秒级 |
| 场景 | 日报、历史分析 | 实时监控、告警 |

### 5.2 Spark Streaming原理
- 微批处理：每隔一小段时间（比如1秒），把这1秒的数据当成小DataFrame处理
- 无界表：把数据流想象成一张永远在长大的表
- API和批处理几乎一样，学习成本低

## 六、FastAPI 入门

### 6.1 什么是FastAPI
- Python写API的Web框架，快、简单、自动生成文档
- 你写正常的Python函数，加个装饰器，就变成API了

### 6.2 GET vs POST
| | GET | POST |
|---|-----|------|
| 作用 | 查数据 | 提交/创建数据 |
| 参数位置 | URL里（?channel=xxx） | 请求体JSON里 |
| 适用 | 查询 | 提交表单、创建数据 |

### 6.3 路径参数 vs 查询参数
- **路径参数**：`/hello/{name}` 路径里的变量，必须传
- **查询参数**：`/metrics?channel=xxx` 问号后面的过滤条件，可选

### 6.4 Pydantic模型
- 定义请求体的格式，告诉FastAPI要传什么字段、什么类型
- FastAPI自动解析、自动校验、自动生成文档
- 继承自 `BaseModel`

### 6.5 Swagger文档
- FastAPI自动生成的交互式API文档
- 打开 `/docs` 就能看到所有接口，还能在线测试
- 不用自己写文档，改了代码文档自动更新

### 6.6 HTTPException
- 抛出HTTP错误，告诉调用者哪里错了
- 常见状态码：200成功、400参数错、404找不到、500服务器错

### 6.7 数据库连接注意事项
- 用 `try/finally` 确保连接一定会关闭
- 不然连接泄露，数据库会被占满

## 七、大模型怎么调用API（Function Calling）

### 7.1 为什么要调用API
- 大模型不知道你的内部数据
- 大模型不擅长精确数值计算
- 大模型上下文窗口有限，装不下所有数据

### 7.2 完整流程
```
用户提问
    ↓
大模型理解问题，决定调用哪个API
    ↓
调用你的API → 你的API查数据库 → 返回数据
    ↓
大模型拿到数据，组织成自然语言回答
    ↓
用户看到答案
```

### 7.3 我们学的东西怎么串起来
| 学过的技术 | 在AI应用里的角色 |
|-----------|-----------------|
| 数据清洗、Spark | 准备数据，存到数据库 |
| SQL、MySQL | 存数据，提供查询能力 |
| FastAPI | 把查询包装成API，给大模型调用 |
| Python函数 | 异常检测、指标计算，也包装成API |
| 大模型API | 理解问题，决定调用哪个工具 |
| RAG/Agent | 把这些串起来，变成智能助手 |
