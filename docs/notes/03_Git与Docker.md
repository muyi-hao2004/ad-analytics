## 一、Docker 解决什么问题

### 1.1 痛点

> 「在我电脑上能跑啊，你电脑上就报错。」

根因是**环境不一致**：

| 不一致项 | 后果 |
|---|---|
| Python 版本 | 语法 / 依赖行为不同，同一份代码一边能跑一边报错 |
| 依赖包 | 缺包、版本冲突、系统库缺失 |
| 路径 | 本地 `C:/...`、服务器 `/home/...`，写死的路径直接失效 |

手工维护环境的结果是：本地、测试、线上三套环境，每次上线都靠人肉对齐，出错只是时间问题。

### 1.2 一句话定义

**把「程序 + 依赖」打包成一个标准箱子，在任何机器上原样跑起来。**

箱子到哪，环境就到哪。机器上只需要装 Docker，剩下的由镜像自带。

### 1.3 它打包了什么

- 程序代码
- 运行时（Python 解释器及版本）
- 第三方依赖（`requirements.txt` 里的全部包）
- 系统层的库和工具
- 启动命令与工作目录

打包的是「一个能跑起来的最小环境」，而不是仅仅一个可执行文件。

## 二、核心概念：镜像、容器、Dockerfile

### 2.1 三个概念

| 概念 | 类比 | 关键点 |
|---|---|---|
| 镜像 Image | 箱子的「设计图纸」/ 菜谱 | **只读、不可变**，是模板 |
| 容器 Container | 按图纸造出的「活箱子」/ 做好的菜 | 真正在跑的实例，可启停、可删除 |
| Dockerfile | 「说明书」 | 告诉 Docker 怎么造镜像 |

「只读、不可变」很重要：镜像一旦构建完成就不会被修改，容器里的任何改动都发生在镜像之上的可写层，所以**删掉容器重建，环境必然回到镜像的原样**——这正是「环境可复现」的机制来源。

### 2.2 关系链

```
Dockerfile（说明书）--docker build--> 镜像（图纸）--docker run--> 容器（活箱子）
```

三个动作对应三条命令：

| 阶段 | 输入 | 命令 | 输出 |
|---|---|---|---|
| 构建 | Dockerfile + 构建上下文 | `docker build -t myapp .` | 镜像 |
| 运行 | 镜像 | `docker run -p 8000:8000 myapp` | 容器 |
| 分发 | 镜像 | （源笔记未展开：镜像仓库的 push / pull） | 远程镜像 |

### 2.3 一个镜像可以启动很多容器

镜像只读，所以同一份镜像能同时跑出多个互不影响的容器（例如同一个 Web 镜像起 3 个实例做负载均衡）。这与「一个类可以造很多对象」是同一种关系。

### 2.4 镜像仓库

`FROM python:3.12` 这类写法表示「基于官方镜像」，说明镜像是分层复用的：不必从零造，而是在别人的基础上加自己的东西。

镜像仓库（registry，如 Docker Hub）的登录、推送、拉取流程在源笔记中未涉及（源笔记未展开）。

## 三、Docker vs 虚拟机

### 3.1 对照表（超高频面试题）

| | 虚拟机 VM | Docker 容器 |
|---|---|---|
| 隔离层级 | 隔离整个操作系统（重） | 只隔离「应用 + 依赖」，共享宿主内核（轻） |
| 虚拟什么 | 整套 OS，含独立内核 | 不虚拟内核，只隔离进程与文件系统视图 |
| 大小 | GB 级 | MB 级 |
| 启动速度 | 分钟级 | 秒级 |
| 资源开销 | 大（每台都要一份完整 OS） | 小（共享内核） |

**一句话**：虚拟机「隔离到 OS 层」，容器「隔离到进程层」。

### 3.2 「共享内核」到底是什么意思

Docker 不装新内核。所有容器**共用宿主机同一个内核**，只是在进程、网络、文件系统上彼此隔离。虚拟机则要虚拟出整套硬件 + 一个「假内核」，指令还要经过虚拟化层中转。

少了这一层，就是容器「MB 级、秒级」而虚拟机「GB 级、分钟级」的根本原因。

### 3.3 两个类比

| 类比 | 对应 |
|---|---|
| 每户独立盖一栋房子（各自地基、水电） | 虚拟机 |
| 同一栋公寓，各自房间隔开，共用地基水电 | Docker 容器 |

### 3.4 与「跑 uvicorn」的区别

| | 直接跑 uvicorn | 虚拟机 / Docker |
|---|---|---|
| 是什么 | 一个**程序**，只是占了本机一个端口 | 真正虚拟出**隔离环境** |

在本机 `uvicorn main:app --port 8000` 并没有「虚拟出一台电脑」，只是开了个服务进程；只有 Docker / 虚拟机才提供独立的文件系统与运行环境。

## 四、Dockerfile

### 4.1 示例 A：通用 Python 项目

```dockerfile
FROM python:3.12                      # 基于官方镜像（地基）
WORKDIR /app                          # 工作目录
COPY requirements.txt .               # 先拷贝依赖清单
RUN pip install -r requirements.txt   # 装依赖（这一层会被缓存）
COPY . .                              # 再拷贝代码
CMD ["python", "main.py"]             # 容器启动时跑什么
```

### 4.2 示例 B：FastAPI 服务

```dockerfile
FROM python:3.11
COPY . /app
WORKDIR /app
RUN pip install -r requirements.txt
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]
```

`--host 0.0.0.0` 让服务监听所有网卡，否则容器外（宿主机）访问不到——这是容器化 Web 服务最常见的「本地能跑、映射端口却连不上」的原因。

### 4.3 指令表

| 指令 | 作用 | 要点 |
|---|---|---|
| `FROM` | 指定基础镜像 | 整个文件的第一条，决定「地基」 |
| `WORKDIR` | 设置工作目录 | 后续 `COPY` / `RUN` / `CMD` 的相对基准；目录不存在会自动创建 |
| `COPY 源 目标` | 把构建上下文里的文件复制进镜像 | `COPY . .` 表示当前目录全部复制到工作目录 |
| `RUN` | **构建时**执行命令 | 每条 `RUN` 生成一层，装依赖放这里 |
| `CMD` | **容器启动时**执行的命令 | JSON 数组形式，元素依次是可执行文件与参数 |

`RUN` 与 `CMD` 最容易混：`RUN` 发生在 `docker build` 阶段，结果被固化进镜像；`CMD` 发生在 `docker run` 阶段，每次启动都执行一次。

### 4.4 层缓存优化（关键技巧）

```dockerfile
COPY requirements.txt .                # 先只拷依赖清单
RUN pip install -r requirements.txt    # 依赖不变 → 这层命中缓存
COPY . .                               # 最后才拷代码
```

Docker 逐层构建，**某一层变了，它和它之后的所有层都要重建**。

如果把 `COPY . .` 写在 `RUN pip install` 前面，那么每次改一行代码都会让「装依赖」这层缓存失效，重新下载安装全部包，构建从几秒变成几分钟。分开写之后，只有代码层重建，依赖层始终命中缓存。

## 五、Docker Compose：编排多容器

### 5.1 解决什么

Docker 管「单个容器」，**Compose 管「一群容器怎么配合」**：一个 YAML 文件 + 一条命令拉起多个服务。

真实系统很少只有一个容器。以 Airflow 为例，它需要 webserver + scheduler + Postgres 多个容器同时运行，还要网络互通——逐个 `docker run` 既难记也难复现，所以用 Compose 声明。

### 5.2 一个 YAML 定义多个组件

```yaml
services:
  mysql:
    image: mysql:8.0
    ports: ["3306:3306"]
  redis:
    image: redis:7
    ports: ["6379:6379"]
  kafka:
    image: bitnami/kafka:latest
    ports: ["9092:9092"]
```

| 字段 | 含义 |
|---|---|
| `services` | 声明有哪些服务（每个服务最终是一个容器） |
| `image` | 用哪个镜像启动（有现成镜像就不必自己写 Dockerfile） |
| `ports` | 端口映射，`宿主机端口:容器端口` |

### 5.3 两条命令

```bash
docker-compose up -d     # 一条命令，MySQL / Redis / Kafka 全部起来
docker-compose down      # 一条命令全部停止并清理
```

`-d` 表示后台运行，不占住当前终端。

### 5.4 价值

| 价值 | 说明 |
|---|---|
| 环境可复现 | 新同事拿到 YAML，一条命令起整套环境 |
| 团队一致 | 所有人跑的是同一组镜像、同一套端口和依赖关系 |
| 可版本化 | YAML 是纯文本，可随项目一起管理 |

## 六、常用命令

| 命令 | 作用 | 说明 |
|---|---|---|
| `docker build -t myapp .` | 构建镜像 | `-t` 打标签（名字），`.` 是构建上下文目录 |
| `docker run -p 8000:8000 myapp` | 运行容器 | `-p` 做端口映射；不加则外部访问不到 |
| `docker ps` | 看正在运行的容器 | 排查「容器起没起来」 |
| `docker images` | 看本地镜像 | 确认镜像是否构建成功 |
| `docker exec -it xxx bash` | 进入容器调试 | `-it` 交互式终端，`xxx` 是容器 ID / 名字 |
| `docker-compose up -d` | 启动编排的全部服务 | 后台运行 |
| `docker-compose down` | 停止并清理全部服务 | 与 `up` 成对使用 |

`docker exec -it` 是排障主力：容器「起不来 / 行为不对」时，进去看一眼文件在不在、依赖装没装、环境变量对不对，比反复重建快得多。

## 七、为什么数据工程 / MLOps 需要 Docker

### 7.1 四类场景

| 场景 | 用法 |
|---|---|
| 部署模型服务 | 模型 + FastAPI 打包成镜像，`docker run` 上线 |
| 跑大数据组件 | Kafka / Redis / MySQL / Airflow 一条 `docker run` 拉起 |
| 保证环境一致 | 训练环境 = 上线环境 |
| 多人协作 | 同一镜像，环境完全一致 |

### 7.2 三条具体理由

1. **模型部署**：训练好的模型连同依赖打包成镜像再上线，避免「训练用 3.10、线上是 3.8」这类事故。
2. **环境一致**：算法团队、开发、线上用同一镜像，问题可以稳定复现。
3. **组件依赖重**：Airflow 这类编排工具本身就由多个服务组成，用 Docker / Compose 起环境是行业默认做法。

### 7.3 一句总结

> Docker = 把「程序 + 依赖」打包成标准箱子，到处跑一致。`Dockerfile → 镜像 → 容器` 是一条链；比虚拟机轻（只隔离进程、共享内核）；Compose 管多容器协作。对数据工程 / MLOps 岗，它是模型部署与环境一致性的地基。

## 面试速查

- **Docker 解决什么问题？** → 环境不一致（「我电脑上能跑」），把程序 + 依赖打包成一致的运行环境。
- **镜像和容器的区别？** → 镜像是只读模板，容器是镜像跑起来的实例；一个镜像可起多个容器。
- **Dockerfile 是什么？** → 构建镜像的说明书，`docker build` 按它逐层生成镜像。
- **三者关系？** → Dockerfile --build--> 镜像 --run--> 容器。
- **Docker 为什么比虚拟机轻？** → 共享宿主内核，只隔离应用与依赖，不虚拟整套操作系统。
- **虚拟机 vs 容器的隔离层级？** → 虚拟机隔离到 OS 层，容器隔离到进程层。
- **容器启动为什么是秒级？** → 不用启动操作系统、不用虚拟内核，只是起一个被隔离的进程。
- **`FROM` `RUN` `CMD` 的区别？** → 指定基础镜像 / 构建时执行并固化进镜像 / 容器启动时执行。
- **为什么 `COPY requirements.txt` 要单独一层？** → 利用层缓存，改代码时不必重装依赖。
- **层缓存什么时候失效？** → 某一层变化后，它及其之后的所有层都重建。
- **`docker run -p 8000:8000` 在做什么？** → 端口映射，把宿主机 8000 接到容器 8000，否则外部访问不到。
- **容器里服务绑 127.0.0.1 为什么宿主机访问不到？** → 只监听容器自身的回环地址，需绑 `0.0.0.0`。
- **怎么进容器排查？** → `docker exec -it <容器> bash`。
- **Compose 解决什么？** → 一个 YAML 定义多个容器及其端口关系，一条命令全部启动 / 停止。
- **`up -d` 和 `down` 分别做什么？** → 后台启动全部服务 / 停止并清理全部服务。
- **Compose 的核心价值？** → 环境可复现、团队一致，新同事一条命令起整套环境。
- **数据工程为什么需要 Docker？** → 模型部署、环境一致、组件依赖重（Airflow / Kafka 等），是 MLOps 的基础设施。
- **跑 uvicorn 算不算虚拟出一台服务器？** → 不算，那只是一个占端口的程序；隔离环境要靠 Docker / 虚拟机。
- **`.git` 为什么 `ls` 看不到？** → 以 `.` 开头是隐藏文件，需 `ls -a` / `ls -la`。
