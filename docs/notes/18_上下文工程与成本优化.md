# 上下文工程与成本优化

本篇覆盖：一轮 Agent 对话的 token 到底花在哪、Prompt Caching 的前缀命中机制与失效原因、DeepSeek / OpenAI / Anthropic 三家的缓存策略差异，以及"固定内容放最前面"究竟指什么。
后半部分讲快照（Snapshot）这个通用模式、上下文窗口有限时的取舍方法（分层摘要、状态外置），最后给一套可复用的 token 成本实测方法。
核心结论先放在这：**真正吃 token 的不是"生成文字指令"，而是 system prompt + 工具清单这块 5,650 token 的固定前缀；它靠 Prompt Caching 省，不靠换更便宜的模型。**

## 一、Token 成本从哪来

### 1.1 三个计费项

| 部分 | 计量对象 | 特点 |
|---|---|---|
| **输入（prompt）** | 本次请求发送的全部 messages + tools | 每次请求都按全量重算，历史越长越贵 |
| **输出（completion）** | 模型生成的 token | 单价通常高于输入，且生成是串行的，直接决定延迟 |
| **缓存命中（cached）** | 命中的前缀部分 | 单价远低于正常输入，DeepSeek 约为 1/10 |

第二项容易被忽略：**输出不仅贵，还慢。** 输入是一次前向并行处理的，输出是逐 token 循环生成的，所以"少说废话"既省钱又提速。

第三项是本节的重点：它不是"另一种输入"，而是输入里被平台判定为"重复前缀"的那一段，单独按折扣计价。**同一段文本，放在前缀里命中缓存是 1/10 价，放在中间没命中就是全价。**

### 1.2 一笔真实的账

以投放 Agent 的一轮对话为例：

| 部分 | 字符数 | 折算 token |
|---|---|---|
| `SYSTEM_PROMPT` | 1,379 | ~1,650 |
| `TOOLS_DEFINITION`（9 个工具） | 8,007 | ~4,000 |
| 快照 snapshot | ~3,000 | ~2,000 |
| **首轮输入合计** | — | **~7,500** |

两个关键发现：

1. **system + 工具清单 = 5,650 token，占首轮输入约 75%。**
2. **"生成一句文字指令"只花几十 token。** 纠结"要不要换个便宜模型来生成指令"，是在优化那 1%，而放过了那 75%。

多轮还会滚雪球：每调用一次工具，历史就变长一截，且**下一轮要把全部历史重新发送**。`max_rounds=8` 时，累计输入会到 1.5 万 ~ 3 万 token。这不是线性增长，而是"每轮都重发前面所有内容"的累加。

### 1.3 一个必须澄清的误区

> "跟我聊天时，前面聊过的内容不会重算吧？"

**会。每轮都把全部历史重新发送、重新计算。**

模型的 API 是无状态的，服务端不记得你上一轮说过什么。所谓"记得上下文"，是客户端把历史拼进 messages 又发了一遍。这叫**历史重发**，不叫缓存。

两者的区别在计费上非常具体：历史重发是**全价**，缓存命中是**折扣价**。只有命中缓存的那部分前缀才便宜。

## 二、两种"缓存"，别混

| | 多轮对话记忆 | Prompt Caching |
|---|---|---|
| 缓存什么 | 多轮历史记录 | 单次请求的固定前缀 |
| 存在哪 | 你的代码 / 数据库 | 平台服务端 |
| 触发条件 | 手动 append 历史 | 前缀一字不差 |
| 谁在管 | 你 | 平台 |
| 省钱吗 | 不省，反而越来越贵 | 省，命中部分按折扣价 |
| 解决什么 | 让模型"记得" | 让模型"不用重算" |

一句话：**对话记忆解决"知不知道"，Prompt Caching 解决"算不算第二次"。** 前者是业务逻辑，后者是计费与性能优化，两者互不替代。

## 三、Prompt Caching 是什么

### 3.1 定义

**平台把"重复出现的那段提示"算过一次就存起来，下次遇到同样的开头直接复用，省钱也提速。**

不是把你的文本存起来当缓存返回，而是把**这段文本在模型内部算出的中间状态**（K/V）存下来，下次跳过这部分计算。

### 3.2 原理：KV cache 复用

Transformer 从左往右算 token，算第 t 个位置时要依赖前面所有位置的中间结果——每层注意力的 Key 和 Value 矩阵。

```
token_1 → 算出 K1,V1
token_2 → 依赖 K1,V1，算出 K2,V2
token_3 → 依赖 K1,V1,K2,V2，算出 K3,V3
...
```

如果两次请求的开头完全一样，那么这段开头对应的 K/V 就是同一份，**可以直接从缓存读，不用重新做前向**。

两个直接推论：

- **只有前缀能缓存。** 因为 K/V 是"从左往右累积"的，中间某段变了，它后面所有位置的 K/V 全部失效。没有"只缓存中间一段"这回事。
- **省的是计算，也是钱。** 平台把省下的算力折成折扣给你，所以缓存命中的 token 单价更低。

### 3.3 命中三条件

1. **位置在最前**——缓存的单位是前缀，不是任意片段。
2. **内容一字不差**——差一个空格、一个标点、一个换行都作废。
3. **能重复出现**——只出现一次的内容没必要缓存，平台也不会命中。

### 3.4 四种典型情况

```
请求1：[A][B][问题1]
请求2：[A][B][问题2]         ✅ 命中 A+B
请求3：[A][B 打错一个字][..]  ❌ 从打错的位置起全部作废
请求4：[问题][A][B]          ❌ A、B 不在最前面，压根不算前缀
```

第四种最容易被忽略：开发者觉得"内容都在 prompt 里啊"，但把用户问题放在了最前面，A、B 就成了"问题之后的内容"，不构成前缀，一次都命中不了。**顺序即语义。**

### 3.5 什么会导致缓存失效

| 失效原因 | 具体例子 | 隐蔽程度 |
|---|---|---|
| 前缀里拼了日期 | `"今天是 2025-06-01"` 写进 system prompt | 高，每天全量失效一次 |
| 前缀里拼了动态数字 | `"最多返回 top_{n} 条"`，n 从配置读 | 高，改配置就失效 |
| 前缀里放了快照 | 把 snapshot 拼进 system prompt | 极高，每轮都失效 |
| 工具清单顺序不稳定 | 用 `set` 或无序 dict 生成工具列表 | 极高，看起来一样但字节不同 |
| 工具清单内容随环境变 | 按当前用户权限动态裁剪工具 | 中，不同用户各自一套前缀 |
| 空白/换行差异 | f-string 拼接时多了一个缩进 | 极高，肉眼几乎看不出 |
| 模型或版本变了 | 换模型、平台升级 tokenizer | 中，整个缓存池作废 |

**排查方法**：把最终发出的 messages 序列化成 JSON 落盘，连续两天的请求做 diff。**只要第一个字节不同，缓存就从那里断开。** 不要靠肉眼读 prompt。

### 3.6 三家平台的机制差异

| 平台 | 机制 | 特点 |
|---|---|---|
| **DeepSeek** | 自动缓存，前缀稳定即命中 | 无需配置，命中部分约 1/10 价 |
| **OpenAI** | 自动缓存（1k token 以上） | 无需配置，部分模型约 5 折；前缀需 ≥1024 token 才生效 |
| **Anthropic** | 手动 `cache_control` 标记 | 要显式指定缓存断点；写入贵约 25%，读取便宜约 90%，适合"写一次读很多次" |

设计含义：

- 用 DeepSeek / OpenAI 时，**能做的只有"把前缀整理干净"**，没有开关可开。
- 用 Anthropic 时，要主动决定"缓存断点打在哪"——通常打在工具清单之后、动态内容之前。
- 前缀太短（不到 1k token）时，自动缓存不生效。这也是"工具清单短一点"和"缓存命中"之间的一个权衡点：清单从 4,000 砍到 800，可能反而失去缓存资格，得算总账。

## 四、"固定在最前面"到底指什么

### 4.1 指 messages 数组的头部

`messages` 是一个有序列表，模型从第 1 条往下读。**"最前面"就是列表的第 1、2 条**，而不是"prompt 字符串的开头"这种模糊说法。

```python
messages = [
    {"role": "system", "content": SYSTEM_PROMPT},   # 第 1 条：固定常量
    {"role": "system", "content": tools_str},       # 第 2 条：固定常量（缓存命中点）
    {"role": "user",   "content": snapshot},        # 第 3 条：每天变，放后面
    {"role": "user",   "content": user_query},      # 第 4 条：每次变
]
```

前两条是**逐字节不变的常量**，它们构成缓存前缀。第 3 条开始才是变化部分——变化部分放在后面，不会影响前面的缓存。

用原生 `tools` 参数时同理：`tools` 数组在协议里位于消息之前参与编码，所以**工具清单天然是前缀的一部分**，只要内容稳定就能命中。

### 4.2 红线

**system prompt 和工具清单必须是写死的常量，不能拼任何动态变量。**

不许拼进去的东西：日期、`top_n` 数字、快照、当前用户 ID、随机 ID、请求级的时间戳、环境变量。

需要这些信息怎么办？**放到前缀之后的 user 消息里。**

```python
# ❌ 错误：日期进了 system prompt，每天第一次请求必然全量失效
SYSTEM_PROMPT = f"你是投放分析助手，今天是 {today}。规则如下……"

# ✅ 正确：system 保持常量，日期作为一条独立的 user 消息放在后面
messages = [
    {"role": "system", "content": SYSTEM_PROMPT},          # 常量
    {"role": "user",   "content": f"当前日期：{today}"},     # 变量，位置靠后
    {"role": "user",   "content": snapshot},
    {"role": "user", "content": user_query},
]
```

### 4.3 用户问题能不能也固定

**能，但要分清目的。**

定时自动化场景下，分析目标每天一样，问题可以写死：

```python
FIXED_QUERY = "请分析今天各渠道 D7 ROI，找出低于 0.7 的广告组并给优化建议"
```

但两点必须说清：

1. **固定问题不是为了省 token。** 一句问题才二十来个 token，省下来可以忽略。固定它的真实目的是**实现无人值守的自动化**——每天定时跑同一条指令，输出可对比的日报。
2. **问题本身缓存不了。** 因为快照排在问题前面，而快照每天变，前缀在快照那里就断了。问题再固定，也接不上前面的缓存。

所以真正的缓存贡献者只有一处：**system + 工具清单**。

## 五、省 token 的正确姿势

按性价比排序，前三项是零成本或低成本，最后一项才涉及架构改动。

### 5.1 第一优先：固定前缀放最前

把 system prompt 和工具清单整理成常量、放在数组头部、保证逐字节稳定，就能吃到 DeepSeek 自动缓存的那 5,650 token。

**这是零代码改动的收益**——不用换模型、不用改业务逻辑，只是把拼接用的 f-string 换成常量。收益却是首轮输入的 75% 按 1/10 计价。

### 5.2 第二优先：精简工具描述

9 个工具的工具清单约 8,000 字符 / 4,000 token。砍掉冗余表述能省 1,500 ~ 2,000 token。

怎么砍而不掉准确率：

- **把约束从自然语言搬到 schema**：不要写"budget 必须是数字，单位是元"，直接 `"type": "number"`。不要写"metric 只能是这几个之一"，直接 `enum`。
- **删掉模型已经知道的常识**："这个函数用于查询数据"——名字叫 `get_metric`，不用说。
- **保留的只有三样**：触发场景、边界（不该用它的情形）、与相似工具的区别。
- **合并同构工具**：4 类对象 × 6 个指标如果写成 24 个函数，清单会膨胀十倍；参数化成 1 个函数只占一份描述。

### 5.3 第三优先：快照做指纹缓存

快照的构建本身也要成本——查库、聚合、序列化。用 `mtime` 或数据版本号做指纹：

```python
def build_snapshot(date: str) -> str:
    fp = f"{date}:{get_warehouse_mtime(date)}"
    if cached := SNAPSHOT_CACHE.get(fp):
        return cached
    snap = _build(date)
    SNAPSHOT_CACHE[fp] = snap
    return snap
```

数据没变就不重复序列化。注意指纹要基于**源数据的更新时间**，不是"今天有没有跑过"——源表晚到了两小时，指纹必须变。

### 5.4 第四优先：减少往返轮次

每多一轮，就要重发一次全部历史。首轮 7,500 token，第 5 轮时输入可能已经 2 万。

三个手段：

- **并行工具调用**：两个互不依赖的查询一次发出，省一整轮。
- **工具返回精简结果**：工具不要返回 200 行明细，返回聚合后的 5 行 + 一句摘要。模型不需要原始数据，需要结论。
- **一次查够**：description 里提示"如需多个指标，一次传入数组"，避免模型一个一个查。

### 5.5 第五优先：简单判断用便宜模型

不是所有环节都需要最强模型。可以做**两段式**：

- 意图路由（这是查数、闲聊还是写操作）→ 小模型或分类器。
- 复杂归因和决策 → 大模型。

但要注意：这条路只在**高并发**时才有意义。日更几十次的内部工具，省下的钱不如多花的工程复杂度值钱。

### 5.6 完整排序

| 优先级 | 手段 | 收益 | 成本 |
|---|---|---|---|
| 1 | 固定前缀放最前 | 5,650 token 打 1/10 | 几乎为零 |
| 2 | 精简工具描述 | 1,500~2,000 token | 低，改文案 |
| 3 | 快照指纹缓存 | 省重复构建与序列化 | 低 |
| 4 | 减少往返轮次 | 每轮省一整份历史 | 中，改工具设计 |
| 5 | 意图路由给小模型 | 省单次调用单价 | 高，要维护两套 |

**顺序不能反。** 很多人的第一反应是"换个便宜的模型"，但单价降 50% 不如把 75% 的输入打到 1/10 折。

## 六、快照（Snapshot）

### 6.1 是什么

**把"当下的状态"压缩成一份 LLM 能读懂的精简结构化数据，作为每次对话的起点背景。**

| 关键词 | 含义 |
|---|---|
| **当下状态** | 不是历史、不是全量，是"此刻"的关键信息 |
| **压缩** | 原始数据太大太细，只留结论和可索引的骨架 |
| **起点背景** | 喂给模型的"开场白"，让它先知道发生了什么 |

### 6.2 为什么到处都用得到

LLM 有两个天生毛病：

1. **无状态**——不记得上一次说过什么。
2. **怕大怕细**——数据一多，token 爆炸；而且细节越多，它越容易读错、抓错重点。

快照一次治两个：**"别把整个数据库塞给 LLM，先把关键结论压成一份简报给它。"**

同一个思想在不同场景有不同名字：

| 场景 | 快照叫什么 | 压缩了什么 |
|---|---|---|
| 投放 Agent | snapshot | 每日报表的派生指标结论 |
| 智能客服 | 用户画像 / 订单摘要 | 用户历史、当前订单状态 |
| 代码助手 | 项目上下文摘要 | 文件树、关键代码片段 |
| 智能运维 | 系统状态快照 | CPU、告警、日志摘要 |
| 金融分析 | 行情简报 | 今日指数、持仓盈亏 |

### 6.3 设计三原则

**① 只给结论，不给过程。**

给 `D7 ROI = 0.65`（结论），不要给 `installs=1200, revenue=780` 让它自己算（过程）。

理由很硬：**LLM 算数容易错。** 派生指标在代码里算好，模型只读结论。这就是"硬口径走代码、软经验走 LLM"。

**② 给骨架 + 按需查细节。**

快照只给 top 20 的骨架，需要下钻时再调 `get_metric()`。

**快照是"目录"，细节靠 Function Calling 取。** 目录给多了会变成正文，目录给少了模型不知道有什么可查——top 20 是个经验值，覆盖了绝大多数决策场景。

**③ 快照是"会变的部分"，放后面。**

它每天变，必须放在固定前缀之后，否则缓存全废。这一条直接把快照和 Prompt Caching 连起来了：**缓存要求"变的往后放"，快照正好是最典型的"变的部分"。**

### 6.4 背后的三个通用模式

快照不是孤立技巧，它是三个底层概念的合体：

1. **上下文工程（Context Engineering）**：决定"喂什么、不喂什么、怎么喂"。这是 Agent 领域最核心的工程问题。
2. **摘要 / 压缩（Summarization）**：把大信息压成小信息。RAG 的查询改写、文档压缩用的是同一套思想。
3. **状态管理（State Management）**：快照是"对话开始时的状态"，配合多轮状态更新就是 Agent 的记忆系统。LangGraph 里的 `state` 就是它的工程化形态。

### 6.5 完整数据流

```
数仓事实表（大、细、会变）
  → 压缩（只留结论 + 骨架）
快照 snapshot（小、精、结构化）
  → 组装进 messages（固定前缀之后）
LLM 读快照 → 理解现状 → 决定查什么、做什么
  → 需要细节时 → 工具按需查真实数据
```

**注意：发给 LLM 的不是原始数仓数据，是精简快照。** 原始表太大太细，让模型自己算指标既慢又容易错。

### 6.6 每日自动决策的完整闭环

```python
def daily_auto_analysis():
    snapshot = build_snapshot()               # ① 算今天的数据快照
    messages = [
        {"role": "system", "content": SYSTEM_PROMPT},  # ② 固定
        {"role": "system", "content": tools_str},      # ③ 固定（缓存命中点）
        {"role": "user",   "content": snapshot},       # ④ 会变
        {"role": "user",   "content": FIXED_QUERY},    # ⑤ 固定问题
    ]
    decision = run_llm_loop(messages)          # ⑥ 多轮查数 → 决策
    propose(decision)                          # ⑦ 落库为 pending，等人批
    # apply_decision(decision)                 # ⑧ 人工 approve 后才由代码执行
```

每天变化的只有 `snapshot` 这一条，其余全部固定。**这就是"每天自动跑、但只花一份缓存钱"的结构。**

注意第 ⑦⑧ 步的分工：**决策是模型给的，落地是代码做的。** 模型只输出"建议删 sub_004，理由是连续 5 天 ROI 低于 0.4"这样的结构化对象，真正改数据库的是 `apply_decision`。这条边界既让 `dry_run` 和人工确认有地方插，也避免了"模型直接操作生产库"这种不可控风险。

### 6.7 快照最容易出的 bug

**取样方式错了，快照会骗人。**

原来的实现是 `head(top_n)` 取前 N 行，但每个素材有 8 天数据，结果前 20 行全是同一个素材的不同日期。模型看到的"top 20"其实只有 2~3 个对象，却以为这就是全貌。

修法：**按维度 ID 聚合，每个维度只占一行。**

```python
# ❌ 取前 N 行
snap = df.head(20)

# ✅ 每个维度聚合成一行，再取 top N
snap = (
    df.groupby(["obj_type", "obj_id"])
      .agg(d7_roas=("d7_roas", "mean"), spend=("spend", "sum"), days=("date", "nunique"))
      .sort_values("spend", ascending=False)
      .head(20)
)
```

判断快照对不对，有一个简单检查：**`snap` 的行数应该等于对象数，不应该是"对象数 × 天数"。** 如果发现某个对象在快照里反复出现，取样一定错了。

## 七、上下文工程

### 7.1 定义

**在有限的上下文窗口里，决定"喂什么、不喂什么、按什么顺序喂、以什么形式喂"。**

它不是"把 prompt 写好看"，而是一个资源分配问题：窗口是有限的，token 是花钱的，模型的注意力也是有衰减的。

### 7.2 窗口有限时怎么取舍

按"信息价值 / token 成本"排序，优先级从高到低：

| 层级 | 内容 | 是否固定 | 说明 |
|---|---|---|---|
| 1 | 系统提示、规则、工具清单 | 固定 | 必须完整，不能省——省了模型就不知道能干什么 |
| 2 | 状态快照 | 每天变 | 决策的起点，必须有，但要压缩 |
| 3 | 当前任务指令 | 每次变 | 短，但决定这一轮的目标 |
| 4 | 历史对话 | 累积 | 最早裁的就是它 |
| 5 | 工具返回的原始结果 | 累积 | 只保留摘要，原始数据落盘 |

**裁减顺序应该是从下往上**：先压缩工具返回（保留结论 + 关键字段），再摘要历史对话，最后才动快照。系统提示和工具清单永远不裁——它们是模型行为的边界。

### 7.3 分层摘要

历史对话不能无限增长，常用三级结构：

```
【最近 N 轮】保留原文          ← 细节最全，模型能直接引用
【更早的对话】压缩成要点列表    ← 保留"做过什么决定、查过什么"
【最初的目标】保留一句话        ← 防止摘要过程中丢掉原始意图
```

关键在于**分层而不是一刀切**：全摘要会丢掉最近几轮的精确参数（比如刚才查的是哪一天的哪个对象），全保留会爆窗口。分层的本质是"越近的信息保留越多细节"。

摘要的触发点：当历史 token 超过预算的某个比例（如 60%）时触发一次压缩，压缩后再继续累积。**不要每轮都摘要**——摘要本身也是一次 LLM 调用，有成本和延迟。

### 7.4 状态外置

**不要把状态放在对话历史里，放在外部存储里。**

对话历史是一种非常糟糕的状态载体：

- 它线性增长，且每轮全量重发。
- 它是自然语言，模型要"读"才能恢复状态，可能读错。
- 它无法被程序精确查询。

正确做法是把状态存成结构化对象（数据库一行、一个 JSON 文件、LangGraph 的 `state`），每轮**按需渲染成一小段文本**放进 prompt。这样状态可以精确更新、可以被代码读取、也不会随轮次膨胀。

```python
state = {
    "date": "2025-06-01",
    "decisions": [{"obj": "crt_002", "action": "keep", "reason": "单日异常"}],
    "pending": ["sub_004"],
}
# 每轮只渲染需要的那部分
prompt_fragment = render_state_digest(state)   # 控制在 200 token 内
```

这和快照是同一个思想的两端：**快照是"进对话时的状态"，状态外置是"对话过程中的状态"，两者都不放在自然语言历史里。**

### 7.5 与 RAG 的关系

RAG 是上下文工程的一种具体手段：**不是把所有文档塞进窗口，而是按当前问题检索最相关的几段塞进去。**

所以"上下文工程"是更大的框：

```
上下文工程
├── 固定层：system prompt、工具清单、业务规则
├── 状态层：快照、外部 state
├── 检索层：RAG（按需注入文档）
└── 历史层：对话记录 + 分层摘要
```

理解了这一层，"为什么要设相似度阈值"也就有了统一解释：**上下文里塞错的东西，比不塞更糟。**

## 八、成本实测方法

### 8.1 用 API 返回的 usage，不要靠估

每次调用的响应里都有 usage 字段，这是唯一准确的数：

```python
resp = client.chat.completions.create(...)
u = resp.usage
print(u.prompt_tokens, u.completion_tokens, u.total_tokens)
print(getattr(u, "prompt_cache_hit_tokens", None))    # DeepSeek：命中缓存的输入
print(getattr(u, "prompt_cache_miss_tokens", None))   # DeepSeek：未命中的输入
```

**必须把 cache hit / miss 分开看。** 只看 `prompt_tokens` 会得出"输入没变便宜"的错误结论——总量一样，但其中 5,650 是打折的。

### 8.2 分段估算（改 prompt 之前先算账）

在动手优化前，用字符数做一次粗算，能快速定位大头：

| 部分 | 字符数 | 经验折算 |
|---|---|---|
| system prompt | 1,379 | ~1,650 token |
| 工具清单 | 8,007 | ~4,000 token |
| 快照 | ~3,000 | ~2,000 token |

中英混排的折算比例不固定（中文一个字常对应 1~2 个 token，JSON 的括号引号也占 token），所以只能用来**比较各部分占比**，不能用来对着账单核数。

### 8.3 算一轮完整对话的账

单轮不够，要按"一次任务"算总账：

```python
total_in = total_out = total_cached = 0
for round in rounds:
    total_in     += round.usage.prompt_tokens
    total_out    += round.usage.completion_tokens
    total_cached += round.usage.prompt_cache_hit_tokens or 0

effective_in = total_in - total_cached          # 全价部分
cost = effective_in * P_IN + total_cached * P_CACHE + total_out * P_OUT
```

关键指标是三个比值：

| 指标 | 算法 | 健康值 |
|---|---|---|
| 缓存命中率 | `cached / total_in` | 稳定前缀下应 > 60% |
| 平均轮次 | `rounds / runs` | 越小越好；持续接近 `max_rounds` 说明工具设计有问题 |
| 输出/输入比 | `total_out / total_in` | 通常 < 5%；异常高说明模型在长篇大论 |

### 8.4 优化前后怎么对比

改一处、测一组，不要一次改五处：

1. 固定 20 个真实问题作为测试集。
2. 记录基线：总输入、总输出、命中率、总成本、平均轮次、任务成功率。
3. 改一项（比如只把日期从前缀里移出去）。
4. 重跑同一组问题，对比。

**必须同时看成本和效果。** 把工具 description 砍一半，token 是省了，但工具选错率上去了，总成本反而更高——因为选错要多跑两轮。

## 九、易错点清单

| 易错点 | 后果 | 正确做法 |
|---|---|---|
| 以为"聊过的不会重算" | 成本模型完全算错 | 每轮全量重发，只有前缀命中才打折 |
| 把日期/快照拼进 system prompt | 缓存每天/每轮失效 | 常量放前面，变量放后面 |
| 用 f-string 拼 system prompt | 缩进或空格变化导致字节不同 | 用模块级常量，拼接只发生在动态部分 |
| 工具清单顺序不稳定 | 内容一样但字节不同，缓存不命中 | 用有序 list，固定顺序 |
| 只优化"生成指令"那几十 token | 抓小放大 | 先优化 5,650 token 的固定前缀 |
| 换便宜模型代替缓存 | 单价降一半，不如打到 1/10 | 先整理前缀，再考虑模型分层 |
| 认为固定问题能省 token | 快照挡在问题前，缓存断在那 | 固定问题是为了自动化，不是为了省钱 |
| 快照用 `head(n)` 取样 | 全是同一对象的不同日期 | 按维度 ID 聚合，一维度一行 |
| 摘要每轮都做 | 多一次 LLM 调用，成本和延迟双增 | 超阈值才触发 |
| 优化只看 token 不看成功率 | 省了钱但任务失败率上升 | 成本与效果成对测量 |

## 面试速查

- **一轮对话的 token 花在哪？** → 输入、输出、缓存命中三部分；本项目首轮输入 ~7,500，其中 system + 工具清单 5,650 占 75%。
- **最吃 token 的是什么？** → 工具说明书，不是"生成文字指令"（那才几十 token）。
- **多轮为什么成本涨得快？** → 每轮把全部历史重新发送，`max_rounds=8` 时累计 1.5 万~3 万 token。
- **"聊过的不会重算"对吗？** → 不对，那是历史重发，全价重算；只有前缀命中缓存才打折。
- **Prompt Caching 是什么？** → 平台缓存重复前缀的 KV，下次同样开头直接复用，省钱提速。
- **为什么只有前缀能缓存？** → K/V 是从左往右累积的，中间变了后面全失效。
- **命中三个条件？** → 在最前面、一字不差、能重复出现。
- **什么会让缓存失效？** → 前缀里拼日期/快照/动态数字、工具顺序不稳、空白差异、换模型。
- **DeepSeek 的缓存机制？** → 自动缓存，前缀稳定即命中，约 1/10 价，无需配置。
- **OpenAI 和 Anthropic 呢？** → OpenAI 自动缓存（1k token 以上，约 5 折）；Anthropic 要手动 `cache_control`，写贵 25%、读便宜 90%。
- **"固定在最前面"具体指什么？** → messages 数组的第 1、2 条，或 `tools` 数组，逐字节不变的常量。
- **为什么不能把日期放进 system prompt？** → 前缀每天变，缓存全量失效；日期应作为后面的 user 消息。
- **用户问题能固定吗？** → 能，但目的是无人值守自动化，不是省 token；快照挡在它前面，问题本身缓存不了。
- **省 token 的第一优先是什么？** → 固定前缀放最前，零成本拿到 75% 输入打 1/10。
- **工具描述怎么精简还不掉准确率？** → 约束搬进 schema（enum/required/type），只保留触发场景、边界、与相似工具的区别。
- **快照是什么？** → 把当下状态压缩成 LLM 能读的简报，作为对话起点。
- **快照为什么通用？** → 同时治 LLM 的"无状态"和"怕大怕细"。
- **快照三原则？** → 只给结论不给过程、给骨架按需查细节、会变的部分放后面。
- **快照背后是哪三个模式？** → 上下文工程、摘要压缩、状态管理。
- **快照最常见的 bug？** → 用 `head(n)` 取样，取到的是同一对象的多天数据；要按维度 ID 聚合。
- **上下文窗口不够时先裁什么？** → 先压工具返回结果，再摘要历史，系统提示和工具清单不裁。
- **分层摘要怎么做？** → 最近几轮留原文、更早的压要点、最初目标留一句。
- **为什么状态要外置？** → 对话历史线性膨胀且不可精确查询；结构化 state 可按需渲染。
- **怎么准确测 token？** → 用 API 的 usage，且必须把 cache hit / miss 分开看。
- **优化效果怎么验证？** → 固定 20 个真实问题做测试集，一次只改一项，同时看成本和任务成功率。
