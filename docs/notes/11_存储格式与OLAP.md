# 存储格式与 OLAP

本篇覆盖：行式存储与列式存储的本质差异，以及列存在分析场景下的优势与代价。
格式部分包括 CSV / JSON / Parquet / ORC / Avro 五种格式的对比与选型、压缩算法（snappy / gzip / zstd）的取舍、HDFS 与 Parquet 为何属于两个层面。
引擎部分包括 OLTP 与 OLAP 的定位差异、列存 + 向量化 + MPP 为什么能提速分析查询、ClickHouse / Doris / Kylin / Presto 各自的定位。
最后回答历史数据为什么要从业务库搬进 OLAP 层，以及什么数据不该放进去。

## 一、行式存储 vs 列式存储

### 1.1 数据在磁盘上怎么排

同一张表：

| channel | clicks | cost | dt |
|---|---|---|---|
| 抖音 | 100 | 50.2 | 2026-10-01 |
| 微信 | 200 | 80.1 | 2026-10-01 |
| 快手 | 80 | 30.5 | 2026-10-01 |

**行式（Row-oriented）**——一行连续存放：

```
[抖音,100,50.2,2026-10-01][微信,200,80.1,2026-10-01][快手,80,30.5,2026-10-01]
```

**列式（Column-oriented）**——一列连续存放：

```
channel: [抖音, 微信, 快手, ...]
clicks:  [100, 200, 80, ...]
cost:    [50.2, 80.1, 30.5, ...]
dt:      [2026-10-01, 2026-10-01, 2026-10-01, ...]
```

### 1.2 差异带来的三个后果

| 后果 | 行式 | 列式 |
|---|---|---|
| 读少量列 | 要把整行读出来再丢弃，I/O 放大 | 只读目标列，I/O 精确 |
| 读整行 / 点查 | 一次连续 I/O 就拿到，快 | 要跳读多列再拼装，慢 |
| 压缩 | 一行内类型混杂，压缩率低 | 同列类型相同、值域相近，压缩率高 |
| 写入 | 追加一行很自然 | 追加要写多个列块，成本高 |
| 更新 | 原地更新方便 | 更新代价大，通常批量重写 |

一句话：**行存适合"整行读写"，列存适合"按列扫描聚合"。**

### 1.3 为什么分析场景必须列存

```sql
SELECT channel, SUM(cost) FROM ad_cost GROUP BY channel;
```

这条查询只碰 2 列（`channel`、`cost`），表若有 60 列：

- 行存要读 60 列的数据，再丢掉 58 列，**有效 I/O 占比 3%**。
- 列存只读 2 列，**有效 I/O 占比 100%**。

再叠加两个放大效应：

1. **压缩率更高**：同列同类型，Parquet 用字典编码（把重复字符串映射成整数）、RLE（连续重复值只存"值 + 次数"）、bit-packing，压缩比常是 CSV 的 5～10 倍。压缩后读的字节更少，I/O 进一步下降。
2. **向量化执行**：列存天然按批（如 1024 行一批）交付数据，CPU 可以对整批做循环、命中 SIMD 指令、减少虚函数调用和分支预测失败，比逐行处理快数倍。

### 1.4 列存的代价

| 代价 | 说明 |
|---|---|
| 点查慢 | `WHERE id = 123` 要读多列再拼一行，不如行存索引 |
| 频繁更新贵 | 改一行要改多个列块，通常用"追加 + 合并"（LSM 思路）代替原地更新 |
| 写入放大 | 小批量频繁写入会产生大量小文件，需要 compaction |
| 不适合 OLTP | 事务、行锁、二级索引都不是列存的强项 |

所以工程上不是"列存取代行存"，而是**分工**：MySQL 行存扛交易，Parquet / ORC 列存扛分析。

## 二、五种文件格式

### 2.1 逐项说明

#### CSV

纯文本，逗号分隔，一行一条记录。

- 优点：任何工具都能读写，人眼可读，Excel 直接打开。
- 缺点：无 schema、无类型（数字也是字符串）、无嵌套、无统计信息、解析要逐字符扫描、压缩率一般、空值和逗号转义容易出错。
- 场景：数据交换、人工核对、给非技术方的小批量导出。**不适合做数仓的落地格式。**

#### JSON

半结构化文本，支持嵌套对象和数组。

- 优点：灵活、可嵌套、字段可缺失，适合上游 schema 不稳定的场景。
- 缺点：冗余大（每个字段名都重复存一遍）、解析慢、无法列裁剪、压缩率一般。
- 变体：**JSONL / NDJSON**（一行一个 JSON 对象），可流式处理、可按行切分，是日志落地的常见形态。
- 场景：API 响应、埋点事件、Kafka 消息体。落数仓前通常先转成 Parquet。

#### Parquet

Apache 顶级项目，列式二进制格式，Spark 生态的事实标准。

结构：

```
magic "PAR1"
  Row Group 0   ← 一批行（默认约 128MB）
    Column Chunk: channel → Page, Page, ...
    Column Chunk: cost    → Page, Page, ...
  Row Group 1 ...
Footer            ← schema + 每个 row group / 列的 min、max、null_count + offset
magic "PAR1"
```

关键能力：

| 能力 | 靠什么实现 |
|---|---|
| 列裁剪 | 只读需要的 Column Chunk |
| 谓词下推 | Footer 里每列每 row group 的 min / max |
| 高压缩 | 列内同质 + 字典编码 + RLE |
| 嵌套结构 | Dremel 的 repetition / definition level |
| schema 演进 | Footer 存 schema，可增列（读旧文件时新列为 null） |
| 可切分 | 按 row group 边界切，与压缩算法无关 |

缺点：二进制不可读；schema 演进能力有限（删列、改类型支持差）；小文件多时元数据开销大。

#### ORC

Optimized Row Columnar，Hive 生态原生列式格式，为 Hive 深度优化。

结构：由 **Stripe**（相当于 Parquet 的 row group，默认 64MB）+ **File Footer** + **Post Script** 组成，每个 stripe 内有列级索引（min / max / sum / bloom filter）。

和 Parquet 的差异：

| | Parquet | ORC |
|---|---|---|
| 出身 | Twitter / Cloudera，Spark 生态 | Hortonworks / Hive，Hive 生态 |
| 压缩率 | 高 | 通常略高（尤其字符串） |
| 嵌套结构 | 支持好（Dremel） | 支持，但不如 Parquet 通用 |
| 更新支持 | 不支持行级更新 | **支持 ACID 事务表**（Hive 0.14+，需分桶） |
| 生态 | Spark、Presto、Flink 默认偏好 | Hive、Tez 偏好 |

选型经验：**Spark 为主选 Parquet，Hive 为主且需要 ACID 更新选 ORC。** 两者性能差距在同代版本里不大，生态适配比微小的压缩率差异更重要。

#### Avro

行式二进制格式，带 JSON 描述的 schema，强调 **schema 演进**和写入效率。

- 优点：写入快（行式追加）、schema 随文件走（自带 reader / writer schema，可做字段增删改名）、支持多版本兼容。
- 缺点：行式，分析时列裁剪无效；压缩率不如列存。
- 场景：**数据接入层**、Kafka 消息序列化、需要长期 schema 兼容的归档。Confluent Schema Registry 常配 Avro 使用。

### 2.2 对比总表

| 维度 | CSV | JSON / JSONL | Parquet | ORC | Avro |
|---|---|---|---|---|---|
| 布局 | 行式文本 | 行式文本（可嵌套） | **列式二进制** | **列式二进制** | 行式二进制 |
| Schema | 无 | 无（自描述但无类型约束） | 有，存 Footer | 有，存 Footer | 有，随文件 |
| 类型系统 | 全字符串 | 弱类型 | 强类型 | 强类型 | 强类型 |
| 嵌套结构 | 不支持 | 支持 | 支持 | 支持 | 支持 |
| 列裁剪 | 否 | 否 | **是** | **是** | 否 |
| 谓词下推 | 否 | 否 | **是**（min/max） | **是**（含 bloom filter） | 否 |
| 压缩率 | 低 | 低 | 高 | 很高 | 中 |
| 写入速度 | 快 | 中 | 中（需缓冲） | 中 | **快** |
| 读取速度（分析） | 慢 | 慢 | **快** | **快** | 慢 |
| 行级更新 | 否 | 否 | 否 | 有限支持（ACID 表） | 否 |
| 人可读 | **是** | **是** | 否 | 否 | 否 |
| 典型场景 | 交换 / 导出 | 日志 / API | 数仓明细、Spark | Hive 数仓、需 ACID | 接入层、Kafka |

### 2.3 选型决策

```
数据要给人看 / 给 Excel 打开？        → CSV
数据是半结构化日志、上游 schema 不稳？  → JSONL 落地，再转 Parquet
数据要长期存、频繁按列聚合？            → Parquet（Spark 生态）/ ORC（Hive 生态）
数据要频繁写入、需要 schema 兼容？      → Avro
数据要支持行级更新 / 事务？             → ORC ACID 表，或直接用 Iceberg / Hudi / Delta
```

一条实践原则：**接入层用行式（Avro / JSON），存储层用列式（Parquet / ORC），服务层用 OLAP 引擎自己的格式。** 每一层选最适合自己读写模式的格式，而不是全链路统一一种。

## 三、压缩

### 3.1 为什么压缩

| 收益 | 机制 |
|---|---|
| 省存储 | 压缩比 3～10 倍，冷数据成本直接下降 |
| 省 I/O | 读的字节数变少，这是查询提速的主要来源 |
| 省网络 | Shuffle、跨节点传输的都是压缩后的字节 |
| 提升缓存命中 | 同样内存能缓存更多数据 |

代价是 CPU 编解码。分布式系统里瓶颈通常在磁盘和网络，不在 CPU，所以**压缩几乎总是划算的**，关键是选对算法。

### 3.2 常见算法

| 算法 | 压缩比 | 压缩速度 | 解压速度 | 可切分 | 适用 |
|---|---|---|---|---|---|
| **snappy** | 中（约 2～3x） | 很快 | 很快 | 容器格式内可切 | 热数据、Shuffle 中间结果、默认首选 |
| **gzip** | 高（约 4～6x） | 慢 | 中 | **否** | 冷数据归档、一次性导出 |
| **zstd** | 高（接近 gzip） | 较快 | 很快 | 新版本支持 | 综合最优，逐步替代 gzip |
| **lzo** | 中 | 快 | 快 | 可（需建索引） | 历史方案，已少用 |
| **bzip2** | 很高 | 很慢 | 慢 | 可 | 极少用，CPU 代价过高 |

### 3.3 两个容易答错的点

**① "gzip 不可切分"影响的是文本文件，不是 Parquet。**

一个 10GB 的 `data.csv.gz` 无法从中间切开解压（gzip 的字典跨块依赖），所以只能由一个 map task 读完，并行度 = 1。
而 Parquet 的切分点是 **row group 边界**，每个 row group 内部的压缩块独立解码，所以 `data.parquet` 即使内部用 gzip 压缩，仍然可以按 row group 并行读。**Parquet / ORC 的可切分性来自容器结构，不来自压缩算法。**

**② 压缩不是越强越好。**

压缩比高意味着 CPU 时间长。对于每天跑一次的离线批处理，CPU 多花 20%、I/O 少 60% 是赚的；对于秒级交互查询，解压延迟会直接体现在响应时间上，snappy / zstd 更合适。

### 3.4 配置位置

| 位置 | 参数 | 建议 |
|---|---|---|
| Hive 中间结果（map 输出） | `hive.exec.compress.intermediate` | true + snappy，减少 shuffle 流量 |
| Hive 最终输出 | `hive.exec.compress.output` | true + snappy / zstd |
| Parquet 表 | `TBLPROPERTIES("parquet.compression"="SNAPPY")` | 热表 snappy，冷表 zstd |
| ORC 表 | `TBLPROPERTIES("orc.compress"="ZLIB")` | ZLIB 压缩比高，SNAPPY 更快 |
| Spark | `spark.sql.parquet.compression.codec` | snappy（默认） |
| Kafka | `compression.type` | lz4 / zstd，兼顾吞吐与延迟 |

## 四、HDFS 与 Parquet 是两个层面

这是最容易被混为一谈的一组概念。

| | HDFS | Parquet |
|---|---|---|
| 是什么 | **文件系统** | **文件格式** |
| 管什么 | 文件怎么切块、放哪台机器、存几份 | 文件内部怎么组织行列、怎么编码压缩 |
| 类比 | 超级文件柜 | 柜子里文件的排版方式 |
| 可替换性 | 可换成 S3 / OSS / 本地盘 | 可换成 CSV / ORC / Avro |
| 谁决定 | 集群运维 | 建表时的 `STORED AS` |

正确的关系：

```
一份 Parquet 文件
   ↓ 写入 HDFS
被切成 128MB 的 Block（最后一个块可能不满）
   ↓
每个 Block 存 3 个副本，分散到不同机架的 DataNode
```

两者**互不绑定**：

- Parquet 不依赖 HDFS：可以放本地盘、S3、OSS、GCS。
- HDFS 不依赖 Parquet：可以存 CSV、JSON、图片、模型文件。

之所以总被一起提，是因为它们在数仓里**总是叠加使用**：HDFS 解决"存得下、不丢"，Parquet 解决"读得快、省空间"。这也是"存算分离"架构的基础：存储层（HDFS / 对象存储）与计算层（Spark / Presto）通过标准文件格式解耦，任何引擎都能读同一份数据。

## 五、OLTP vs OLAP

### 5.1 定义

| | OLTP | OLAP |
|---|---|---|
| 全称 | Online Transaction Processing | Online Analytical Processing |
| 干什么 | 处理日常业务交易：下单、支付、改地址 | 支持分析决策：聚合、多维切片、趋势 |
| 典型操作 | `INSERT` / `UPDATE` / 按主键 `SELECT` | 全表 / 大范围扫描 + `GROUP BY` + `JOIN` |
| 单次涉及数据 | 几行 | 百万到几十亿行 |
| 响应要求 | 毫秒 | 秒级到分钟级 |
| 并发 | 高并发小事务（数千 QPS） | 低并发大查询（几十 QPS） |
| 存储模型 | 行存 | 列存 |
| 索引 | B+ 树、哈希索引 | 分区、min/max、bloom filter、位图索引 |
| 事务 | 强 ACID | 弱事务或最终一致 |
| 数据模型 | 规范化（3NF），避免冗余 | 反范式、星型 / 宽表，允许冗余 |
| 数据时效 | 当前状态 | 历史全量 + 多版本 |
| 典型系统 | MySQL、PostgreSQL、Oracle | ClickHouse、Doris、Presto、Kylin、Spark SQL |

### 5.2 为什么分析不能用 OLTP 库

以 MySQL 为例，跑一条"过去一年各渠道各素材的消耗与 ROI"：

| 障碍 | 原因 |
|---|---|
| 行存 I/O 放大 | 只要 5 列却要读整行，有效 I/O 极低 |
| 无列级统计 | 无法跳过不相关的数据块，只能全表扫 |
| 单机扩展上限 | 数据到 TB 级后，单机磁盘和内存都吃紧；分库分表又不擅长跨片聚合 |
| 索引帮不上 | B+ 树适合点查和范围查，对"全表聚合"几乎无效，反而增加写入成本 |
| 挤占业务资源 | 一条大查询把 buffer pool 打满，线上交易跟着抖动 |
| 存储成本 | 行存压缩率低，保留三年历史成本高 |

### 5.3 OLAP 为什么快：三个支柱

#### ① 列存（Columnar Storage）

只读需要的列，I/O 与列数无关；同列同质，压缩率高；天然按列批量交付，为向量化铺路。

#### ② 向量化执行（Vectorized Execution）

传统执行引擎是**火山模型**：每次 `next()` 返回一行，虚函数调用、分支判断的开销分摊到每一行上。
向量化改成**一次处理一批**（如 1024 行），把循环压到紧凑的数组运算里：

```
逐行：for each row → 判断类型 → 计算 → 写回      （每行都有函数调用开销）
向量：for each batch(1024) → 整列相减 → SIMD 并行  （开销摊薄 1024 倍）
```

配合 **SIMD**（单指令多数据）指令，一次 CPU 指令处理 4～8 个值，CPU 利用率从个位数提升到接近饱和。这是 ClickHouse 单表扫描能到亿级行/秒的核心原因之一。

#### ③ MPP（Massively Parallel Processing）

大规模并行处理：**每个节点有自己的 CPU、内存、磁盘，互不共享（share-nothing）**。

```
              Coordinator（解析 SQL、生成分布式计划）
             /            |            \
        Node 1         Node 2         Node 3
     扫描本地分片    扫描本地分片    扫描本地分片
             \            |            /
              Exchange（按 key 重分布数据）
             /            |            \
         聚合片段       聚合片段       聚合片段
             \            |            /
                 Coordinator 汇总返回
```

关键机制是 **Exchange / Shuffle**：按 join key 或 group key 把数据重分布到对应节点，让每个节点只算自己那份。节点越多，并行度越高，扫描和聚合近似线性扩展。

MPP 与 SMP 的区别：SMP 是"一台机器加 CPU / 加内存"（scale up，有上限）；MPP 是"加机器"（scale out，近似无上限），代价是网络 shuffle 和分布式事务的复杂度。

### 5.4 三个支柱的配合

```
列存       → 减少要读的数据量（I/O 层）
向量化     → 提高单位数据的计算效率（CPU 层）
MPP        → 把剩余工作量摊到多台机器（集群层）
压缩       → 进一步减少 I/O 与网络字节
分区/索引  → 在进入扫描前就砍掉大部分数据
```

任何一层缺失，整体都会出现短板：只有列存没有向量化，CPU 仍在逐行空转；只有向量化没有 MPP，单机算力封顶；只有 MPP 没有列存，网络和磁盘被无用列打满。

## 六、常见 OLAP 引擎

| 引擎 | 一句话定位 | 存储 | 强项 | 弱项 | 典型场景 |
|---|---|---|---|---|---|
| **ClickHouse** | 单表扫描极快的列存 MPP 数据库 | 自有 MergeTree 本地盘 | 亿级行聚合秒级、写入吞吐高、压缩强 | 多表 join 弱、无完整事务、运维较复杂 | 日志分析、行为明细、宽表聚合、实时大屏 |
| **Apache Doris** | 兼容 MySQL 协议的 MPP 分析型数据库 | 自有列存，支持湖仓外表 | join 能力强、物化视图、易用、支持高并发点查 | 超大规模单表极致性能不如 ClickHouse | 实时报表、多维分析、统一分析入口 |
| **Apache Kylin** | 预计算 Cube 的 MOLAP 引擎 | HBase / Parquet 存 Cube | 亚秒级响应、高并发、对固定报表极快 | 维度组合爆炸、schema 变更成本高、只适合可枚举查询 | 固定维度的 BI 报表、指标看板 |
| **Presto / Trino** | 不存数据的分布式 SQL 查询引擎 | 无（读 Hive / MySQL / ES 等） | 联邦查询、秒级 ad-hoc、存算分离 | 内存易 OOM、不适合超大规模 ETL、依赖上游存储 | 即席查询、跨源分析、数据湖查询 |

补充两个常见但不在上表的：

- **Spark SQL**：批处理引擎，能读 Hive / Parquet，延迟分钟级，适合 ETL 而非交互查询。
- **Hive LLAP**：Hive 的交互式模式，常驻进程 + 内存缓存，定位介于批处理和 OLAP 之间。

### 6.1 选型思路

```
查询模式固定、维度可枚举、要求亚秒 → Kylin（预计算）
单表超大、聚合为主、join 少          → ClickHouse
多表 join 多、要易用、要高并发        → Doris / StarRocks
跨多个数据源、即席探索、不落地        → Presto / Trino
超大规模 ETL、离线批处理              → Spark SQL / Hive
```

没有"最好的 OLAP 引擎"，只有"匹配查询模式的引擎"。选型前先问三个问题：**查询是固定的还是任意的？join 多不多？数据要不要实时写入？**

## 七、历史数据为什么要放 OLAP 层

### 7.1 数据的分层存放

```
HDFS / 对象存储（冷、全量、便宜）
   全量明细、原始日志、多年历史
        ↓ 聚合 / 筛选
OLAP 引擎（温、宽表、快）
   ADS 层结果、DWS 汇总宽表、常用维度组合
        ↓ 极热数据
MySQL / Redis（热、点查、接口）
   单条配置、实时状态、缓存
```

### 7.2 五个理由

| 理由 | 说明 |
|---|---|
| 查询性能 | 列存 + 分区 + min/max 索引 + 向量化，让"扫一年数据做聚合"从分钟级降到秒级 |
| 存储成本 | 列存压缩比通常是 MySQL 行存的 3～10 倍，长期保留历史才负担得起 |
| 资源隔离 | 分析大查询不碰线上业务库，避免一条 SQL 拖垮交易系统 |
| 并发能力 | 看板类应用要支撑几十上百个并发查询，OLAP 的 MPP 架构可以水平扩展 |
| 查询模式匹配 | 分析是"少列、多行、聚合"，正是列存的主场；MySQL 的 B+ 树索引在这种模式下几乎无效 |

### 7.3 什么时候不该放 OLAP

- **需要强事务**（转账、扣库存）→ 留在 OLTP。
- **需要按主键高频点查单行**（用户详情页）→ MySQL / Redis 更合适。
- **数据量很小、查询很简单**（几千行的配置表）→ 直接 MySQL，引入 OLAP 是过度设计。
- **需要频繁行级更新**（状态机流转）→ OLAP 的更新代价高。

一句话总结：**OLTP 负责"把当前状态记准"，OLAP 负责"把历史数据算快"，HDFS / 对象存储负责"把全量数据存便宜"。** 三者按数据的温度分层，各司其职。

## 面试速查

- **行存和列存的本质区别？** → 行存按行连续存放，列存按列连续存放；前者适合整行读写，后者适合按列扫描聚合。
- **为什么分析场景用列存？** → 只读需要的列（省 I/O）、同列同质压缩率高、天然支持向量化。
- **列存的代价是什么？** → 点查要拼多列、频繁更新贵、小批量写入会产生小文件。
- **CSV 为什么不适合做数仓落地格式？** → 无 schema、无类型、无统计信息、解析慢、压缩率低。
- **Parquet 和 ORC 怎么选？** → Spark 生态选 Parquet，Hive 生态且需要 ACID 选 ORC，性能差异不大，生态适配更重要。
- **Avro 适合什么？** → 写入密集的接入层、Kafka 消息、需要 schema 演进和兼容的场景。
- **Parquet 为什么能谓词下推？** → Footer 里存了每个 row group、每个列的 min / max / null_count。
- **Parquet 的 row group 是什么？** → 一批行的集合（默认约 128MB），是列裁剪、下推、并行读的基本单位。
- **snappy 和 gzip 怎么选？** → 热数据和中间结果用 snappy（快），冷数据归档用 gzip / zstd（压缩比高）。
- **gzip 不可切分，那 Parquet 用 gzip 还能并行读吗？** → 能，Parquet 按 row group 切分，可切分性来自容器结构而非压缩算法。
- **HDFS 和 Parquet 是什么关系？** → 文件系统 vs 文件格式，两个层面，可自由组合，不是替代关系。
- **一份 Parquet 写进 HDFS 后发生了什么？** → 被切成 128MB 的 Block，每块 3 副本，分散到多个 DataNode。
- **OLTP 和 OLAP 的区别？** → OLTP 高并发小事务、行存、毫秒级；OLAP 大范围扫描聚合、列存、秒级。
- **为什么 MySQL 跑不动分析查询？** → 行存 I/O 放大、无列级统计、单机扩展有限、大查询会挤占业务资源。
- **OLAP 为什么快？** → 列存减少 I/O、向量化提高 CPU 效率、MPP 把计算摊到多节点，再叠加压缩和分区裁剪。
- **什么是向量化执行？** → 一次处理一批数据（如 1024 行）而不是一行，摊薄函数调用开销并利用 SIMD。
- **什么是 MPP？** → Share-nothing 的大规模并行处理，每个节点独立算本地分片，通过 Exchange 重分布数据。
- **ClickHouse 的定位？** → 单表扫描极快的列存数据库，适合日志和行为明细的大宽表聚合，多表 join 弱。
- **Doris 的定位？** → 兼容 MySQL 协议的 MPP 分析库，join 和易用性好，适合实时报表与统一分析入口。
- **Kylin 的定位？** → 预计算 Cube 的 MOLAP 引擎，固定维度报表亚秒响应，但维度组合会爆炸。
- **Presto / Trino 的定位？** → 不存数据的分布式查询引擎，擅长跨源联邦查询和秒级 ad-hoc。
- **历史数据为什么放 OLAP？** → 列存压缩降低成本、分区和下推提升速度、与业务库隔离、MPP 支撑高并发看板。
- **什么数据不该放 OLAP？** → 强事务、高频单行点查、超小表、频繁行级更新的数据。
