# Agent 评测：概念与作用

本篇不写「怎么跑」，只讲**概念**：评测到底是什么、它和传统测试差在哪、Agent 评测为什么必须换一套方法，以及那一串术语（golden set、holdout、pass^k、判断层/生效层、归因、hit@1/recall@k）各自解决什么问题。

一个 Agent 系统有两半要评，而且是两类不同的问题：
**决策评测**（它会不会做对）和**检索评测**（它有没有拿到做对所需的信息）。

核心结论先放这：

> **评测不是给 Agent 打分，是给你自己一个判据——「这次改动是真的变好了，还是我感觉变好了」。**
> 没有这个判据，所有优化都只是自我安慰。

---

## 一、评测是什么

一句话：**用一批「答案已知的输入」去跑系统，把输出和答案比对，统计出错的方式和频率。**

拆开有三个必需件：

| 要素 | 含义 | 缺了会怎样 |
|---|---|---|
| **输入集** | 一批有代表性的任务（考题） | 只能靠临场试几个，样本有偏 |
| **标准答案** | 每个输入「正确输出是什么」 | 无法判定，只能凭感觉 |
| **判定规则** | 怎么算「对上了」 | 答案再准也用不上 |

评测之所以是一门学问，难点几乎全在第二、三项。**第一项（造输入）反而最容易**——真正难的是「凭什么说这是正确答案」。

### 它和「我试了一下，感觉还行」的区别

这两件事的差别不在精度，在**能否比较**。

「感觉还行」是一个绝对判断，而且每次判断的尺子都在变。上个月你觉得「回答得挺专业」，这个月你觉得「有点啰嗦」，其实是你的容忍度变了，不是模型变了。

评测给的是**相对判断**：同一个尺子量两次，数字从 4/8 到 7/8，这个变化才是可信的。所以评测最核心的产出不是一个分数，而是**一条可比的历史曲线**。

---

## 二、三类测试的分野

这是理解 Agent 评测的钥匙：**它和软件测试、机器学习评测都不是一回事。**

| | 软件测试 | 机器学习评测 | Agent 评测 |
|---|---|---|---|
| 输出是什么 | 确定的（同样的输入必然同样的输出） | 一个数值/类别 | **一串动作**（删哪个、调多少） |
| 对错怎么定 | 断言，非黑即白 | 和 label 比对 | **要判「动作+对象+方向」三项** |
| 答案从哪来 | 需求文档写的 | 数据集自带 | **人定义的** |
| 跑两次一样吗 | 完全一样 | 固定种子基本一样 | **不一定**（采样有随机性） |
| 主要失败模式 | 崩溃、逻辑错 | 精度不够 | 该动没动、不该动却动了 |

### 关键差异：答案的「外生」与「内生」

这一条值得单独讲，因为它是整个 Agent 评测的根。

**外生（exogenous）= 答案存在于系统之外，和你无关。**

你论文里做的事就是这一类：数据集里原本就存着「这家公司后来破产了没有」。这个 label 是别人（现实）给的，你只是去读它。所以你能放心地算 AUC，因为尺子不是你造的。

**内生（endogenous）= 答案不存在于任何地方，必须由人定义。**

「这个渠道只装了 30 次、ROI 5%，该不该删？」——世界上没有任何数据库存着这个答案。它是业务判断，必须有人写下来。

这就带来了 Agent 评测最根本的困难：

> **你既是考生又是出题人。** 所以必须额外做两件事来防止自欺——把答案写得足够硬（业务上唯一合理），以及留一部分题不让自己看（holdout）。

软件测试没有这个问题（答案在需求里），机器学习评测也没有（答案在数据集里）。**只有 Agent 评测需要为「答案的合法性」本身辩护。**

### 所以「准确率」这个词在这里不够用

传统测试报一个通过率就够了。Agent 评测不行，原因在下一节——**错误不对称**。

## 三、核心概念逐个讲

下面每个概念都按同一个结构讲：**它是什么 → 为什么需要 → 不加会怎样**。

### 3.1 评测集（golden set）

**是什么**：一批人工确认过「正确答案」的输入，是评测的基准盘。

**为什么需要**：单次测试只能验证「这条路走得通」，不能验证「别的路走不通」。一批题才能覆盖不同的失败方式。

**不加会怎样**：每次改完随手试一个例子，试的那个恰好是通过的，就以为改好了。这是最常见的自欺方式。

### 3.2 题目的三种类别

一批题不能混着算分，要先分类。因为**「该不该动手」本身是三种不同的情况**：

| 类别 | 含义 | 考的是 |
|---|---|---|
| **该不动**（must_hold） | 正确做法是什么都不做 | 克制力——会不会误伤 |
| **该动**（must_act） | 正确做法是执行某个动作 | 行动力——会不会漏掉 |
| **不可达**（known_gap） | 当前架构下信息不够，做不到 | 不考，单独记录 |

第三类是这套方法里最容易被忽略、也最重要的一类，见 3.9。

### 3.3 鉴别力：为什么要做「对照题」

**是什么**：故意让两道题**表面现象相同、正确答案相反**。

**为什么需要**：一道题只能测「答对没有」，测不出「因为什么答对」。

举例：同样都是「ROI 很低」，一道该不动（数据还没长熟，是假象），一道该删（真的差，样本充足）。**只会「数字低就动手」的 Agent，在这两道里必然错一道。**

这就把「碰巧蒙对」和「真的会判断」区分开了。

**不加会怎样**：题目全是「明显的坏渠道」，Agent 全删光也能拿满分，而它在真实场景里会把健康渠道一起删掉。

> 这个概念有个通用名字：**对照设计**。它在实验科学里叫控制变量，在机器学习里叫 hard negative，在评测里叫 discriminating cases。本质是同一件事——**让错误无法靠运气躲过**。

### 3.4 dev 与 holdout：为什么要把题分成两半

**是什么**：一批评测集分成两部分，一部分允许你看着结果改（dev），一部分在改完之前不许看（holdout）。

**为什么需要**：这是从机器学习借来的，理由完全一样。

你反复看着 8 道题改，改到 8/8 全过。这时那 8 道题已经**不是考题了，是训练材料**。你测出来的不是「它变强了」，而是「它把这 8 道背下来了」。

这在 Agent 领域有个专名叫 **overfitting to the eval**（对评测过拟合），在 ML 里叫 **test set leakage**（测试集泄漏）。两者是同一个病。

**holdout 的作用**：改完之后跑一次，回答一个问题——

> 这次改动是真的提升了泛化能力，还是只把 dev 那几条记住了？

**不加会怎样**：报表 100%，换个真实场景就崩，而且你完全没有预警信号。

**holdout 是消耗品**：一旦它暴露了缺陷、你针对它改过代码，它就「见过」了，必须降级成 dev，另补新的。不轮换的话，三次迭代之后 holdout 就变成第二个 dev，你又会得到「全过」的假象，**而且这次连警报都没有**。

### 3.5 为什么指标必须分层：错误不对称

**是什么**：不报一个总分，而是按错误类型分开报。

**为什么需要**：因为不同类型的错误，代价差一个数量级。

| 错误 | 业务后果 | 可逆性 |
|---|---|---|
| 删掉一个正在赚钱的渠道 | 流量没了，重新起量要重新学习 | **不可逆** |
| 该删没删 | 多花一天钱，明天还能发现 | 可逆 |

「切错一条腿」和「晚一天复诊」不能加在一起算平均分。

**不加会怎样**：两个退化策略都能拿高分——

- **永远不动**：所有「该不动」的题满分，看起来特别安全，实际什么活都没干
- **见低就删**：靠蒙能过几条，但是资损级

合并成一个数之后，这两个策略的分数可能差不多，**而线上后果差一个数量级**。

> 一句话记法：**指标不能替业务做加权。** 加权的权力属于业务方，不属于做评测的人。

### 3.6 判断层与生效层：为什么同一个场景要报两个分数

**是什么**：

- **判断层** = Agent 自己想出来的动作对不对
- **生效层** = 这些动作里，有多少真的会被执行

两者中间夹着一道**护栏**（guardrails，确定性代码，不合格的动作直接拒绝执行）。

**为什么需要**：因为「想错了」和「造成后果」是两件事，混在一起就看不见真相。

实测最典型的一幕：某个场景 Agent 三次都提交了删除（判断层 0/3），但三次都被护栏拦住（生效层 3/3）。

- 只报判断层 → 结论是「护栏没用，分数没变」
- 只报生效层 → 结论是「修好了」，掩盖了「它一点没长进」

**两列一起看，才能说出那句完整的话：护栏买到的是「不出事」，不是「变聪明」。**

这个概念可以推广：

> **任何有「决策 → 校验 → 执行」三段结构的系统，都应该把中间那道校验前后的指标分开统计。** 否则你永远分不清「模型变强了」和「规则变严了」。

### 3.7 过度拦截：护栏的对称性

**是什么**：护栏把**正确动作也拦掉**的情况，要单独统计。

**为什么需要**：护栏不是越严越好。过严的后果是「优化永远落不了地」——判断对了却被系统挡住，业务上表现为「Agent 好像什么都干不了」。

**不加会怎样**：只测「有没有拦住坏动作」，就会不断把阈值调紧，直到一个正确的删除也过不去。报表上「零误删」，看起来完美，实际上系统已经废了。

> 这条原则有普适性：**任何防御机制都要同时验两个方向——拦住了该拦的，没拦住该放的。** 只验前者，等于鼓励自己调得过严。

### 3.8 为什么要跑多次：随机性

**是什么**：同一个场景跑多次，取**最坏那次**作为结果，而不是取平均或取多数。

**为什么需要**：模型采样有随机性，同一份代码同一个场景，三次里可能一次过两次不过。

**为什么取最坏**：因为业务关心的是「最坏会怎样」，不是「平均下来还行」。

数学依据是 **pass^k**（来自 τ-bench，Sierra 2024）：单次通过率 p，连续 k 次全对的概率约 p^k。

一个单次通过率 2/3 的 Agent，跑三次全对的概率只有 **0.296**。也就是说：**「三次里两次没犯错」在业务上仍然不能上线**，它有 1/3 的概率造成资损。

**不加会怎样**：只跑一次，那个不稳定场景恰好通过了，你会以为没问题。**单次结果只能用来发现问题，不能用来报分数**——实测同一份代码单次跑出来的数字，比跑三次取最坏高出一倍。

### 3.9 known_gap：把「做不到」和「做错了」分开

**是什么**：有一类失败，原因不是模型笨，而是**系统给它的信息或动作空间本身不匹配**。

举个真实例子：Agent 被要求给某个素材加预算，但它能看到的维度是「素材」，而调预算这个动作作用在「系列+国家」上，两者之间**没有映射字段**。它知道该加，但不知道加哪个。

**为什么需要**：这是架构欠账，不是能力问题。混进正常指标里，会把「接口设计缺陷」算成「模型能力不足」，然后你去优化 prompt——改到死也没用。

**不加会怎样**：优化方向直接跑偏，而且你会一直以为自己模型不行。

> 这条的价值在方法层面：**评测的第一产出不是分数，是「这个失败该由谁负责」。** 见 3.10。

### 3.10 失败归因：评测真正的价值所在

**是什么**：每次失败之后，先回答「这是谁的错」，再决定改什么。

**四类归因，处理方式完全不同：**

| 归因 | 典型表现 | 该改什么 |
|---|---|---|
| **模型能力不足** | 该拆维度不拆、该查的数据不查 | 改提示词 / 补知识 / 加护栏 |
| **考题本身有错** | Agent 说「数据和快照对不上」 | **改题，不是改模型** |
| **架构缺陷** | 信息不够、动作对象不匹配 | 改数据/接口，标 known_gap |
| **评测环境有错** | 反复查同一个工具直到耗尽轮数 | 修评测，不是修 Agent |

**为什么这是最重要的一步**：因为如果不归因，人的本能是把所有失败都当成「模型笨」，然后疯狂改提示词。而四类里有两类根本不是提示词能解决的。

**怎么判断**：看 Agent 的推理过程。它如果说「数据矛盾/串位/查不到」，先怀疑题，不要怀疑模型——**被测系统在告诉你，你的考卷有问题。**

> 这条是整篇最实用的一句：**Agent 的失败理由，常常是对评测设计的一份 bug report。**

### 3.11 三种评测范式（以及为什么常常选最朴素的那个）

开放式任务没有唯一答案，业界只有三条路：

| 范式 | 做法 | 代价 |
|---|---|---|
| **固定题集 + 规则判定** | 答案可执行验证（看最终状态、跑单元测试） | 造题贵，但判定免费且稳定 |
| **LLM 当裁判** | 让另一个模型打分 | 便宜，但裁判自己有偏好偏差 |
| **人类投票** | 众包/专家打分，算 Elo | 最可信，最贵最慢 |

**为什么主流 benchmark（τ-bench、SWE-bench、函数调用榜）都停在第一种？**

因为它们要的就是「可执行验证」——**宁可样本少，也不引入裁判模型的主观性**。裁判模型有已知偏差（偏爱长回答、偏爱排在前面的选项），一旦引入，你的分数就开始反映裁判的口味，而不是被测系统的能力。

第二种只在「开放式生成」（写作、对话质量）上才必要，因为那类任务根本无法用规则判定。

**这个选择的含义**：不是「第一种低级、第三种高级」，而是**能用规则判定就绝不上裁判**。可验证性比规模重要。

### 3.12 评测在开发流程里的角色

这是概念层面最后一件事，也是最容易被误解的：

> **评测不是验收环节，是驱动开发的引擎。**

传统流程是「写完 → 测试 → 上线」。Agent 开发不是这样，它更像科学实验的循环：

```
造题 → 跑基线 → 失败 → 归因 → 修复 → 重跑 → 补新题 → 循环
```

关键在于**每一轮都要有新的题进来**。因为修完的题会退化（见 3.4），只靠固定的题集，你会在第三轮之后失去所有信号。

这个循环有个名字：**eval-driven development（评测驱动开发）**。它的价值不在于「证明我做对了」，而在于**让每一次改动都有可证伪的判断**。

## 四、检索评测：另一半，而且简单得多

前面三节讲的全是「评 Agent 的判断」。但这类系统里还有一半东西没被评到：**知识库检索（RAG）**。

### 4.1 为什么必须有「组件级评测」

这是本节最重要的概念。

Agent 失败的时候，你只知道「最后答错了」，但答错可能来自四个环节：

```
检索 → 上下文组装 → 推理 → 动作执行
```

**端到端评测只能告诉你「坏了」，不能告诉你「哪一环坏了」。**

如果检索返回的内容就是错的，那后面推理再漂亮也没用；反过来，如果检索是对的而判断错了，那问题在模型而不在知识库。**混在一起评，你永远不知道该修哪一边。**

所以正确的做法是分层：**端到端评测看整体，组件级评测定位。** 概念上这叫「把一个大系统拆成可独立验证的环节」——和软件工程里拆单元测试是同一个思路。

检索这一环的好处是**它可以被单独测量**：给它一个问题，看它返回什么，不需要模型参与。

### 4.2 它属于「答案唯一」那一类，所以标准指标能用

回到第二节的三分法：检索评测其实是**机器学习评测**那一类，不是 Agent 评测。

因为给定一个问题，**「应该命中哪段知识」是有客观答案的**（只要知识库是人写的）。这和外生 label 一样——答案不在被测系统里，你去读就行。

所以指标可以用学界几十年没变过的标准指标：`hit@1`、`recall@k`、`MRR`。不用发明新东西，也不用 LLM 裁判。

> 这个对比很能说明问题：**同一个项目里，两半的评测难度完全不同。** 决策评测要为人定义的 label 辩护，检索评测只要数排名。困难不是均匀分布的——**它集中在「答案不确定」的地方。**

### 4.3 但「对」是分层的，这是一处特有的难处

检索的正确答案不是一个字符串，是「语义上正确的那一段」。这就带来一个判定上的困难：

- **只判文档级**（命中了《渠道质量》篇）：太松。命中了正确的篇，但里面是「引用规则」那一节，而问题问的是「怎么判断刷量」——仍然是错的。
- **只判段落级**（命中的段里必须出现某几个词）：太严。同一段话换个说法就判失败。

所以判定要**两级**：先判文档对不对，再判命中的段落里有没有关键信息。两级都过才算命中。

> 这个概念可以推广：**当「正确答案」本身有结构（文档 → 段落 → 句子）时，判定也必须是分层的。** 只判最粗的层级会放过错误，只判最细的层级会把正确判成错误。

### 4.4 三个指标其实在说三件不同的事

很多人把这三个当「同一件事的不同精度」，其实不是。

| 指标 | 字面意思 | 它真正在诊断什么 |
|---|---|---|
| `hit@1` | 第一名就对 | **首选质量**——第一眼给人的印象 |
| `recall@k` | 前 k 名里有 | **召回**——该有的东西漏没漏 |
| `MRR` | 正确结果排名的倒数均值 | **整体排名质量**，不只是有无 |

关键洞察在 `hit@1` 和 `recall@k` 的**差值**上：

- 两者都很低 → **召回问题**：正确的那段根本没被检索到
- recall 高但 hit@1 低 → **排名问题**：找到了，但被别的东西挤到后面

**这两类问题的修法完全不同。** 召回问题要改切块策略（段落太大/太小）、加关键词通路；排名问题要改打分融合、去重、防止同文档块互相霸榜。

如果只报一个数，你永远不知道自己在修哪一类。

**为什么 `recall@k` 最重要**：因为下游拿的是 top-k 一起去喂模型，不是只看第一条。排在第二第三，模型照样看得见。所以「该有的没漏」比「排第一」更贴近业务价值。

这也解释了为什么 `k` 的取值不是随便定的——**它应该等于下游实际取几条**。取 3 条就用 recall@3，不要拿 recall@10 来美化数字。

### 4.5 难度分层：让分数有梯度

固定 20 条 query，分成四档：

| 档 | 考什么 | 失败意味着 |
|---|---|---|
| **easy** | 问题里的词基本来自原文 | 嵌入连字面对齐都做不到 |
| **medium** | 换说法、口语化 | 语义匹配不行（这是真实用户的主要问法） |
| **hard** | 答案分散在多个段落/文档 | 切块策略有问题 |
| **negative** | 知识库里没有答案 | 会不会硬凑 |

**为什么要分档**：如果全是最简单的题，100% 通过也没有信息量——你无法知道「改进」有没有发生。难度分层的作用是**制造可观测的梯度**，让每次改动的效果落在某一档上，从而反推出改对了什么。

这和第三节 3.3 的对照设计是同一个原理的两个用法：**对照设计制造「必须真懂才能过」的题，难度分层制造「能看出进步了多少」的刻度。**

### 4.6 negative 用例：考「会不会硬凑」，以及一处方法论上的折中

检索系统最危险的失败不是「没找到」，而是**找到了一个看起来相关、其实无关的段落，然后模型拿它当真**。

- 没找到 → 模型会说「我不知道」，这是安全的
- 找到错的 → 模型会自信地编出一个答案，这是危险的

所以必须有一类题，**正确答案是「这里没有答案」**。

但这里有一处必须诚实交代的折中：**理想做法是「检索系统主动拒答」**，而那需要相似度阈值。纯向量检索没有可靠的阈值机制，所以这批判题的期望被改成了「命中的那段，正好是文档里明写『没有可靠公开基准』的那一节」。

**它考的是「不硬凑」，还没真的考到「主动弃答」。** 这两件事不一样，加了阈值才谈得上后者。这个区别必须写清楚，否则等于夸大覆盖范围。

> 概念上的教训：**评测的期望值往往被实现能力倒逼着降低。** 遇到这种情况，正确做法是把降低的部分明确写出来，而不是悄悄改掉标准然后报个好数字。

### 4.7 评测的第一产出，是推翻你的直觉

这节有一个很典型的例子，值得单独说，因为它说明了评测**独立于「打分」之外的价值**。

背景：文档被切成块之后，子块丢失了它所在小节的标题。直觉上，把标题补回每个子块，应该更容易被检索到——信息更完整了。

实测：`hit@1` 从 85% 掉到 **80%**。

原因：同一篇文档的所有子块补上相同标题前缀后，**块与块之间的嵌入变得高度相似**，检索时同文档的多个块互相霸榜，把别的文档的正确块挤出前列。

**这个结论只有评测能给。** 如果靠翻两三条结果目测，你会觉得「补了标题的块看起来更完整、更像一段正经知识」，然后认为改好了。

> 所以评测的一个核心作用不是「证明我对了」，而是**「排除我看起来对」**。
> 直觉在工程里经常是错的，而且错得很有说服力——它错在「合理」，不是错在「荒谬」。

### 4.8 成本结构决定了迭代速度

这是一个容易被忽略、但很实际的概念差别：

| | 决策评测 | 检索评测 |
|---|---|---|
| 要不要调模型 | 要 | 不要 |
| 单轮成本 | 约 $0.05 | 0 |
| 单轮耗时 | 约 6 分钟 | 秒级 |
| 结果稳定吗 | **不稳定**（要跑多次） | **确定**（同样输入同样输出） |

后果是：**检索评测可以一天跑几十次，决策评测一天跑不了几次。**

这直接决定了迭代速度——检索那条线在一天内做了四次完整迭代（改切块 → 加标题 → 回退 → 混合检索），每次都有数据支撑；决策那条线一天只能跑几轮，所以必须更谨慎地选择改什么。

> 概念上：**一个评测如果很贵，它就只能做验收，做不了驱动。** 想让评测真正推动开发，第一件事是把它变便宜、变快、变确定。

这也是为什么「不调 LLM 的评测」特别值得做——**它把评测从「偶尔体检」变成了「随时可跑」。**

### 4.9 它的边界：检索对 ≠ 判断对

最后一条限定，必须说：**检索指标好，不代表 Agent 判断好。**

检索对只是判断对的**必要条件，不是充分条件**：

- 检索到了正确知识，模型可能还是不听
- 检索漏了一段，模型可能靠常识补上了
- 检索全对，但动作对象选错了——那是决策层的问题

所以两套评测**不能互相替代，也不能相加**。它们各自回答不同的问题：

> 决策评测问：**它会不会做对？**
> 检索评测问：**它有没有拿到做对所需的信息？**

两个都通过，才谈得上「这个系统在这一环上是可靠的」。

## 五、这套东西的固有局限

概念层面必须承认的几条，不承认就是在卖方法：

1. **样本量决定不了统计显著性。** 十几条题只能回答「有没有已知问题」，回答不了「准确率是多少」。行业 benchmark 是 100–500 条。
2. **单标注没有一致性检验。** 答案是一个人写的，就没有第二个人验证「这个答案是不是真的唯一」。学术上要算标注者间一致性（Cohen's κ），工业上要求 ≥0.8。
3. **通过率不能外推。** 题目是刻意挑的边界情况，所以「通过 60%」**不等于**「线上准确率 60%」。这条最容易被误用。
4. **判定只看结果，不看过程。** 动作对了但理由是瞎猜的，仍然判对。要测这个得引入裁判模型，又回到 3.11 的偏差问题。
5. **合成数据不等于假数据。** 真实业务数据往往**没有 label**（没人标注过「这条该不该删」），所以它做不了监督评测。合成场景的答案是人为设计的，但可以做到业务上唯一合理，而且能控制变量。**关键是陷阱设计得对不对，不是数据真不真。**
6. **检索评测的负样本是折中。** 它只考到「不硬凑」，还没考到「主动弃答」——后者需要相似度阈值，而纯向量检索没有可靠阈值。**期望值被实现能力倒逼降低了，这一点要明说，不能悄悄改标准然后报好数字。**
7. **两套评测不能相加。** 检索指标好只是判断对的必要条件。把「recall@3 100%」写成一个整体质量数字，是偷换概念。

## 六、概念速查

| 概念 | 一句话 | 解决什么 |
|---|---|---|
| 评测集（golden set） | 一批答案已知的题 | 让「有没有变好」可比 |
| must_hold / must_act | 该不动 / 该动 | 把克制力和行动力分开考 |
| 对照设计 | 表面相同、答案相反 | 防「碰巧蒙对」 |
| dev / holdout | 可看 / 不许看 | 防「把题背下来」 |
| test set leakage | 在考题上调参 | 同上，是那个错误的学名 |
| 指标分层 | 不报总分，按错误类型报 | 因为错误代价不对称 |
| 判断层 / 生效层 | 想对没有 / 真被执行 | 分清「变聪明」和「变严格」 |
| 过度拦截 | 好动作也被拦 | 防护栏调得过严 |
| pass^k | 连续 k 次全对的概率 | 单次通过率不能代表稳定性 |
| known_gap | 架构做不到 | 别把设计缺陷算成模型笨 |
| 失败归因 | 先问「谁的错」 | 防止朝错误方向优化 |
| eval-driven development | 评测驱动迭代 | 每次改动都可证伪 |
| 端到端 / 组件级评测 | 看整体 / 定位到环节 | 端到端只知道坏了，不知道哪坏 |
| 两级判定 | 文档级 + 段落级 | 只判粗的放过错误，只判细的误杀正确 |
| hit@1 | 第一名就对 | 首选质量 |
| recall@k | 前 k 名里有 | **召回**，k 应等于下游实际取几条 |
| MRR | 排名倒数的均值 | 整体排名质量 |
| hit@1 与 recall@k 的差 | 两个数的差值 | 区分「召回问题」和「排名问题」 |
| 难度分层 | easy / medium / hard / negative | 制造可观测的梯度 |
| negative 用例 | 正确答案是「没有答案」 | 考会不会硬凑 |
| 离线评测的成本结构 | 免费 vs 花钱 | 决定它是能驱动开发还是只能验收 |

## 七、面试怎么讲（概念版）

**「你怎么评 Agent？」**

> 分两步：先定义「什么叫正确答案」，再选判定方式。
>
> Agent 和传统机器学习最大的差别是 **label 的来源**——你论文里的破产 label 是外生的，数据集里本来就存着；Agent 的 label 是内生的，世界上没有任何数据库存着「这条数据该不该删」，必须由人定义。所以 Agent 评测的核心工作不是跑分，是**为答案的合法性辩护**。
>
> 判定方式我选的是「固定题集 + 规则判定」，没上 LLM 裁判。因为裁判模型有偏好偏差，宁可样本少也不引入主观性——τ-bench、SWE-bench 都停在这一层。

**「指标怎么设计？」**

> 不报总分，按错误类型分三层。因为误删和漏检的代价差一个数量级，合并等于替业务做加权，而加权权属于业务方。
>
> 另外把「判断层」和「生效层」分开——就是想对没有 vs 真被执行。加了护栏之后生效层涨了，判断层没变，两列一起看才能说出「护栏买到的是不出事，不是变聪明」。

**「检索那一半怎么评？」**

> 和决策评测是两类问题。决策要为人定义的答案辩护，检索的答案是客观的——「该命中哪段知识」由知识库内容决定，属于外生 label。所以直接用标准指标：hit@1、recall@3、MRR，不用发明新东西。
>
> 但检索有个特有难处：**正确答案是分层的**。只判文档太松（命中了对的篇、但错的那一节），只判段落太严（换个说法就失败），所以两级判定。
>
> 最有用的不是分数本身，是 **hit@1 和 recall@k 的差值**——它区分「召回问题」和「排名问题」：两者都低是召回坏了，recall 高但 hit@1 低是排名被挤掉了。这两类修法完全不同。
>
> 为什么值得单独做这一层？因为端到端评测只能告诉你「坏了」，不能告诉你「检索坏了还是判断坏了」。组件级评测负责定位。

**「怎么保证不是自己骗自己？」**

> 三件事。一，题目做成对照：表面现象相同、正确答案相反，只会看单一指标的必然错一半。二，留 holdout，改完才跑一次，而且用过就作废，防止对评测过拟合。三，跑三次取最坏，不取平均——单次通过率 2/3 的 Agent，连续三次全对只有 0.296。

**「失败之后怎么办？」**

> 先归因，再修。四类：模型能力、考题有错、架构缺陷、环境有错。这四类我全踩过。跳过这一步，就会把所有失败都当成模型笨，然后疯狂改提示词——但其中两类根本不是提示词能解决的。
>
> 最实用的判据是：**Agent 的失败理由，常常是对评测设计的一份 bug report。** 它说「数据矛盾」，先查题，别急着换模型。
