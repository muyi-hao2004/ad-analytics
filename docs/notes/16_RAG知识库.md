# RAG 知识库

本篇覆盖：RAG 的定义与它真正解决的问题、从切分到生成的完整链路、四个核心组件（切分 / Embedding / 向量库 / 检索方式）的选型与取舍。
后半部分讲检索质量优化（top-k、相似度阈值、rerank、元数据过滤、多路召回）、什么数据该建 RAG、什么数据不该建、引用溯源与效果评估。
主线一句话：**RAG 把"让模型记住"换成"现场查资料"，所以工程质量的重心不在生成，而在检索——检索错了，后面生成得再通顺也是错的。**

## 一、RAG 是什么

### 1.1 定义

RAG = Retrieval-Augmented Generation，检索增强生成。

核心思想四个字：**先查后答**。相当于把闭卷考试改成开卷考试——模型不需要把知识背在参数里，而是在回答前先翻到相关的那几页。

### 1.2 它解决四个问题

| 问题 | 具体表现 | RAG 怎么解 |
|---|---|---|
| 不知道私有数据 | 团队方法论、内部指标口径、历史踩坑记录，都不在预训练语料里 | 把这些文档建成库，提问时检索进 prompt |
| 知识过期 | 模型参数有训练截止时间，新业务、新政策它不知道 | 更新知识库即可生效，不用重新训练模型 |
| 幻觉 | 没见过的内容也会编出一个格式正确的答案 | 把回答约束在检索到的原文上，并允许"查不到就说不知道" |
| 无法引用 | 说不清这句话的依据来自哪份文档 | 检索结果自带来源元数据，可以逐句标注出处 |

前两个是"知识覆盖"问题，后两个是"可信度"问题。**RAG 同时改善两者，但真正不可替代的是第三个和第四个：它把"模型说的"变成"文档说的"。**

### 1.3 与微调的区别（别混）

| | RAG | 微调（Fine-tuning） |
|---|---|---|
| 改什么 | 推理时喂进去的上下文 | 模型权重 |
| 适合 | 事实、知识、口径、文档问答 | 风格、格式、特定任务的输出习惯 |
| 更新成本 | 改一个文件就生效 | 要重新构造数据、重新训练、重新评估 |
| 成本 | 低，只塞相关几篇文档 | 高，要 GPU 和标注数据 |

一句话：**RAG 管"知道什么"，微调管"怎么说话"。**

红线：不要把 RAG 说成"重新训练模型"——它全程不训练、不改权重。

## 二、完整链路

### 2.1 两段式：离线建库 + 在线检索

```
【离线，一次性或增量】
原始文档（md / pdf / 网页）
   ↓ 切分
chunk 列表（每块 500~1000 字）
   ↓ embedding
向量列表（每条 chunk 一个定长向量）
   ↓ 写入
向量库（向量 + 原文 + 元数据）

【在线，每次提问】
用户问题
   ↓ embedding（同一个模型）
查询向量
   ↓ 相似度搜索 top-k
命中的 chunk（带原文和来源）
   ↓ 拼进 prompt
[系统提示] + [检索到的资料] + [用户问题]
   ↓
大模型生成回答
```

**关键点：建库和查询必须用同一个 Embedding 模型。** 换了模型，向量空间就变了，旧库全部作废，必须重建。

### 2.2 五步记法

**切块 → 嵌入 → 检索 → 增强 → 生成。**

前两步是建库，后三步是问答。"增强"指的不是模型变强，而是把检索结果拼进上下文这个动作。

### 2.3 检索与生成的代码骨架

```python
import chromadb

client = chromadb.PersistentClient(path="./chroma_db")
col = client.get_or_create_collection("notes")

# 建库
col.add(
    ids=[f"chunk-{i}" for i in range(len(chunks))],
    documents=chunks,
    metadatas=[{"source": "playbook.md", "section": "ROI 优化"} for _ in chunks],
)

# 检索
hits = col.query(query_texts=["D7 ROAS 低于 70% 怎么优化"], n_results=5)
docs = hits["documents"][0]

# 拼 prompt
context = "\n\n".join(f"[{i+1}] {d}" for i, d in enumerate(docs))
prompt = f"""只根据下面的资料回答，资料里没有就说"资料未覆盖"。
回答时用 [编号] 标注依据。

资料：
{context}

问题：D7 ROAS 低于 70% 怎么优化？"""
```

### 2.4 Prompt 组装的三条硬约束

1. **限定范围**："只根据资料回答"，否则模型会用自己的参数知识盖过检索结果。
2. **允许弃权**："资料未覆盖就说不知道"，这是抑制幻觉最便宜的手段。
3. **要求标注**：让模型输出 `[1]` `[2]`，配合资料编号，才有可溯源性。

### 2.5 包装成服务

用 FastAPI 把 RAG 包成 HTTP 接口（`POST /search` 或 `POST /ask`），别的程序——包括 Agent——就能通过网络调用。

这一步的意义：**RAG 从"一个脚本"变成"一个可复用服务"**。同一套知识库可以同时被聊天窗口、Agent 工具、内部系统调用，不用各写一份。

### 2.6 流式输出（Streaming）

调用 API 时加 `stream=True`，模型生成一个字就吐一个字，不用等整段生成完。

- 收益：首字延迟从"几秒"降到"几百毫秒"，用户感知的快慢主要取决于首字时间，而不是总时长。
- 代价：流式下拿不到完整的 usage 统计（要在最后一个 chunk 里取），且错误处理更麻烦——流到一半断了，前端要能续或者重试。
- 与引用结合时的坑：如果要求模型在句末标 `[1]`，流式输出会出现"话说完才出现编号"的跳变，一般做法是先出正文、结束后再补引用块。

## 三、核心组件

### 3.1 文档切分（Chunking）

**为什么必须切**：embedding 模型有输入长度上限，整篇文档塞不进去；即使塞得进去，一整篇混了十几个主题的文档，向量会被"平均"成一个什么都不像的方向，检索精度断崖下跌。

**粒度**：常用 500~1000 字。

| 粒度 | 后果 |
|---|---|
| 太大 | 一块里混多个主题，向量语义被稀释，检索不准；同时白占 prompt token |
| 太小 | 一句话一个块，缺上下文，检索到了也读不懂；召回数量不够拼不出完整答案 |

**三种切分策略**：

| 策略 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| 固定长度 | 按字符数硬切，可带 overlap | 实现最简单，块大小可控 | 会从句子/表格/代码中间切断 |
| 按语义结构 | 按标题层级（`#` `##`）、段落、列表切 | 每块语义完整，最贴合文档 | 依赖文档本身结构良好 |
| 重叠切分（overlap） | 相邻块保留 10%~20% 重叠 | 缓解"答案正好落在切口上" | 库变大，可能返回重复内容 |

实践上通常是**组合**：先按标题结构切，某节仍然超长再按长度二次切，并加少量 overlap。

项目里的做法是**按 `##` 标题结构切**，理由是保留语义完整——一个二级标题下通常就是一个完整的方法论或一条经验，切开就变味了。

**易错点**：

- 切断了表格和代码块。表格被切成两半后，后半段全是数字没有表头，检索到了也没法用。
- chunk 里没带标题路径。检索出"阈值设 0.7 以下"这么一句，但不知道它属于哪个指标的口径。**做法是给每个 chunk 的正文前面拼上它的标题路径**（如 `投放优化 > ROI 判断 > 阈值`），再送去 embedding。
- 切完不做检查。建库后应该随机抽 10 个 chunk 人眼读一遍，确认没有断头断尾。

### 3.2 Embedding（向量嵌入）

**是什么**：把一段文字映射成一串定长浮点数。语义相近的句子，向量在空间里的方向也相近，所以可以用余弦相似度衡量"意思像不像"。

注意它衡量的是**语义相似**，不是**事实正确**。"CPA 太高怎么办"和"CPI 太高怎么办"向量很近，但这是两个不同指标——这一点在后面讲"为什么口径不能塞进 RAG"时会再用到。

**模型选型**：

| 模型 | 语言 | 形态 | 备注 |
|---|---|---|---|
| `bge-m3` | 多语言（中文强） | 开源，本地部署 | 中文首选。难负样本训练 + 多阶段训练 + 多向量输出 + 多语言 |
| `text-embedding-3-small` / `-large` | 英文强、中文可用 | API | 免运维，按量计费 |
| `all-MiniLM-L6-v2` | 英文 | 开源，极小 | 本地跑得动、速度快，但中文语义弱 |

选型的判断顺序：

1. **语料是什么语言** → 中文语料优先 bge-m3，英文语料用 text-embedding-3 系列。
2. **能不能出网** → 内网/离线环境只能本地开源模型。
3. **维度与成本** → 维度越高检索越细，但存储和计算越贵；小库（几千 chunk）用大模型没必要。
4. **有没有 instruction 前缀要求** → 部分模型（如 bge 系列）查询侧要加指令前缀，建库侧不加。加错会显著掉点。

**项目里的真实约束**（值得记，是"踩过"的证据）：

- **DeepSeek 不提供 embedding 接口**，只有 chat 接口。所以嵌入这一环不能用 DeepSeek API，必须另找模型——这是很多人一开始的想当然。
- **HuggingFace 直连不通**，本地中文模型 bge-m3 下载受阻，于是先用 ChromaDB 内置的 MiniLM 跑通链路：**中文弱，但能把全流程验证完**。
- 因此把嵌入层做成**可插拔接口**：上层只依赖 `embed(texts) -> list[list[float]]` 这一个函数签名，换模型只改一个实现类，不动建库和检索代码。

```python
class BaseEmbedder:
    def embed(self, texts: list[str]) -> list[list[float]]:
        raise NotImplementedError

class MiniLMEmbedder(BaseEmbedder):
    def embed(self, texts):
        return model.encode(texts, normalize_embeddings=True).tolist()

class BgeM3Embedder(BaseEmbedder):
    def embed(self, texts):
        return bge.encode(texts, normalize_embeddings=True).tolist()
```

**易错点**：

- 建库和查询用了不同模型/不同版本 → 向量不在同一空间，检索结果接近随机。
- 忘了归一化 → 用内积算相似度时，长文本因为模长大而被系统性偏袒。
- 换模型不重建库 → 最隐蔽的 bug：能跑、不报错、就是不准。

### 3.3 向量库

**是什么**：专门存向量、并支持"给一个向量，快速找出最相似的 k 个"的数据库。

**为什么不用 MySQL 硬算**：几万条还能全表扫，上百万条时逐条算余弦距离就是灾难。向量库靠近似最近邻索引（HNSW / IVF 一类）把复杂度从"全量比较"降到"走图/走桶"，用少量精度换数量级的延迟下降。

**选型**：

| 方案 | 定位 | 适用 |
|---|---|---|
| **ChromaDB** | 轻量、嵌入式、pip 装完就能用 | 本地开发、单机小库、原型验证 |
| **pgvector** | PostgreSQL 扩展 | 已有 PG，想少引一个组件，事务和元数据过滤强 |
| **Qdrant** | 独立服务，过滤与混合检索能力好 | 中等规模生产 |
| **Milvus** | 分布式 | 亿级向量、需要水平扩展 |

项目的选择是 **ChromaDB**：单机、数据量是内部文档（几十到几百 chunk）、要的是"跑通链路"而不是"扛并发"。这是典型的按规模选型，不是按"哪个更出名"选型。

**易错点**：向量库同时要存**原文**和**元数据**。只存向量和 id、原文另存一张表，会让每次检索多一次回表，且删除/更新时容易两边不一致。

### 3.4 检索方式

| 方式 | 原理 | 擅长 | 不擅长 |
|---|---|---|---|
| **向量检索** | 比较语义向量距离 | 同义改写、口语化提问、跨表述匹配 | 专有名词、编号、缩写、精确字符串 |
| **关键词检索（BM25）** | 词频 + 逆文档频率打分 | 精确词命中，如 `crt_002`、`D7 ROAS`、`eCPM` | 换个说法就查不到 |
| **混合检索（Hybrid）** | 两路各取 top-k，再融合 | 兼顾语义与精确命中 | 要调权重，工程复杂度上升 |

一个具体例子说明为什么需要混合：用户问"crt_002 这个素材为什么被删"。向量检索很可能返回一堆"素材衰退的常见原因"，因为语义上最像；而真正该命中的是那份提到 `crt_002` 的操作日志复盘。**编号这类 token 的向量几乎不携带语义，只有关键词检索能抓住。**

**融合方式**：最常用 RRF（Reciprocal Rank Fusion），不看两路分数量纲是否可比，只看排名：

```
score(d) = Σ_over_lists 1 / (k + rank_i(d))     # k 常取 60
```

好处是免调权重、对分数量纲不敏感；坏处是丢掉了"某一路非常确信"的信息，所以有的实现会用加权分数融合。

## 四、检索质量优化

RAG 效果差，九成问题出在检索，不是出在生成。按"改动成本从低到高"排：

### 4.1 top-k 怎么定

- 太小（k=1~2）：一次没召回正确答案就彻底失败，没有容错。
- 太大（k=20+）：噪声淹没信号，模型容易被不相关段落带偏，token 也白烧。
- 常用 3~5；配合 rerank 时可以"粗召回 20~50，精排留 3~5"。

判断依据不是感觉，而是**看 recall@k 曲线**：k 从 3 加到 10，召回率还在明显涨就说明该加大；已经平了就说明再加只是加噪声。

### 4.2 相似度阈值（最重要的一条）

**低于阈值宁可说"不知道"，也不要把不相关的块塞给模型。**

原因很直接：模型不会质疑上下文。你塞给它一段讲"素材衰退"的内容，它就会用这段内容去回答"预算怎么分配"，而且答得很像那么回事。**空上下文至少会触发"资料未覆盖"，错上下文会直接生产一个高置信度的错误答案。**

实现上是检索后加一道过滤：

```python
hits = col.query(query_texts=[q], n_results=5)
docs = [(d, s) for d, s in zip(hits["documents"][0], hits["distances"][0]) if s < 0.8]
if not docs:
    return "知识库里没有相关内容。"
```

阈值取多少要实测：拿 20 个"库里有答案"的问题和 20 个"库里没有答案"的问题，看两组相似度分布的分界点。**没有万能阈值，因为不同 embedding 模型的分数分布完全不同。**

### 4.3 重排（Rerank）

两段式检索：

1. **召回（recall）**：向量检索快速取回 20~50 条候选，追求"不漏"。
2. **精排（rerank）**：用一个 cross-encoder 类模型，把"问题 + 候选块"拼在一起逐对打分，追求"排序准"。

为什么有效：向量检索是**双塔**结构，问题和文档各自独立编码，只在最后算一次距离，交互信息损失大；rerank 模型让问题和文档在同一个注意力里过一遍，能捕捉"这个词到底是不是在回答这个问题"。

代价：每条候选都要跑一次前向，延迟和成本随候选数线性增长，所以只能用于精排，不能用于全库。

### 4.4 元数据过滤

在向量检索之前先按结构化字段缩小范围：

```python
col.query(query_texts=[q], n_results=5, where={"doc_type": "playbook"})
```

常用过滤维度：文档类型（方法论 / 操作日志 / 指标口径）、时间（只要最近三个月）、业务线（IAA / IAP）、语言、权限。

两个价值：**提精度**（把不可能相关的文档排除掉）和**控权限**（不同用户只能检索自己有权限的文档，这是企业场景的硬需求）。

### 4.5 多路召回

同一个问题，用多种方式各召回一批，再合并去重：

- 原始问题向量检索
- 改写后的问题向量检索（换一种说法，覆盖不同表述）
- 关键词 BM25 检索（保住编号和专有名词）
- 按标题/摘要检索（短查询匹配短文本更准）

多路召回解决的是"单一检索器的盲区"，代价是延迟叠加。实践上先上"向量 + BM25"两路，收益最明显、成本最低。

### 4.6 查询改写

用户的问题往往不适合直接检索："这个咋整"、"ROI 又掉了"。

- **补全指代**：把"它"、"这个"替换成上文的具体对象。
- **拆解多跳问题**："A 和 B 哪个好" → 分别检索 A、B 的资料。
- **生成多个查询**：让模型把一个问题改写成 3 个不同角度的查询，分别检索后合并。

这一步和"摘要压缩"是同一个思想的两面：**都是把原始信息换一种更适合被匹配的形式。**

### 4.7 问题定位表

| 现象 | 大概原因 | 先改什么 |
|---|---|---|
| 该命中的没命中 | 切分切断、embedding 太弱、查询表述差异大 | 换模型 / 加关键词路 / 查询改写 |
| 命中了但答非所问 | top-k 太大、无阈值、无 rerank | 加阈值 + rerank |
| 答案缺关键细节 | chunk 太小、overlap 不足 | 调大块、加 overlap |
| 同一段反复出现 | overlap 过大、去重缺失 | 检索后按 doc_id 去重 |
| 答得像但事实错 | prompt 没限定"只根据资料" | 加约束 + 要求引用 |

## 五、什么数据适合建 RAG

### 5.1 一句话判断标准

**能写 SQL 精确查出来的 → 数仓 + Function Calling；查不出来、只能靠语义匹配的 → RAG。**

这是这套系统里最重要的一条分界线。走错路的代价不是"效果差一点"，而是"结论根本不可信"。

### 5.2 正例与反例

| 内容 | 该走哪 | 为什么 |
|---|---|---|
| 优化师方法论、行业经验、踩坑总结 | RAG | 非结构化文本，没有唯一写法，靠语义匹配 |
| 平台政策、投放规范、FAQ | RAG | 同上，且会更新 |
| 历史头部包是哪些 | **数仓** | 精确数值 + 排序，一句 SQL 就出来了 |
| 昨天各渠道消耗 | **数仓** | 精确数值 |
| 指标口径定义 | **语义层** | 必须唯一、精确、不能"差不多" |
| 操作日志 | **数仓** | 结构化记录，按对象和时间查 |

典型误区：**"用 RAG 统计历史头部包"**。这是把检索当聚合用——RAG 只能返回"看起来相关"的几条文本，它不会做 `GROUP BY` 和 `ORDER BY`，也保证不了全量。要统计就必须查数仓。

### 5.3 三路分工总表

| 内容类型 | 走哪 | 性质 |
|---|---|---|
| 指标口径 / 定义 | 语义层（精确键值查询） | 硬，一个标点都不能错 |
| 数值 / 排行 / 趋势 | 工具查数仓（精确查询） | 硬，不能错 |
| 行业经验 / 方法论 | RAG（相似度检索） | 软，参考用 |

### 5.4 为什么口径不能塞进 RAG

这是最容易做错的一处，值得单独讲透。三个层面：

**一、性质不同。** 经验是"软"的——同一件事两个优化师说法不同，都有参考价值，允许"差不多"。口径是"硬"的——`D7 ROAS` 到底是 7 天累计还是第 7 天当天，差一个字结论就反了。

**二、机制不同（最致命）。** RAG 靠语义相似度检索，**会漏、会歪**。`CPA` 和 `CPI` 语义极近，可能一起返回，甚至排错序；而语义层是精确键值查询，要 `d7_roas` 就返回 `d7_roas`，不多不少。用相似度去查"必须唯一确定"的东西，是工具用错了。

**三、优先级直觉早就有了。** "先数据后经验"这条规则，本质就是"硬的走精确查询，软的走 RAG"。

一句话：**RAG 是"猜最像的"，语义层是"查确定的"。算口径这种不能错的事，必须用"查确定的"。**

类比：RAG 像问一个记性不太好的同事，他凭印象给你经验，可能偏；语义层像翻公司的《指标口径白皮书》，翻到哪页就是哪页，一个字不变。

（语义层的具体做法见《17_FunctionCalling与Agent》第六章。）

## 六、RAG 接入 Agent：把它做成一个工具

RAG 不该是一个独立系统，而应该**作为第 8 个工具 `search_knowledge` 接入 Agent 的 Function Calling 体系**，registry 里的工具数从 7 变成 8。

```python
{
    "type": "function",
    "function": {
        "name": "search_knowledge",
        "description": (
            "检索团队知识库，获取优化方法论、行业经验、踩坑总结等非结构化文本。"
            "适用于『为什么』『一般怎么做』『有什么经验』类问题。"
            "不适用于查询具体数值、排行、趋势——那些用 get_metric / get_top_history。"
        ),
        "parameters": {
            "type": "object",
            "properties": {
                "query": {"type": "string", "description": "检索语句，用业务术语，不要口语化"},
                "top_k": {"type": "integer", "enum": [3, 5, 8], "default": 5},
            },
            "required": ["query"],
        },
    },
}
```

这样做的价值：**由模型自己判断"这个问题该查数仓还是查知识库"**，而不是在代码里写 if-else 猜意图。判断依据完全来自 description 里写清的"触发场景 + 边界"。

配套还要在 SYSTEM_PROMPT 里定优先级：**先数据后经验**——凡是能用数值回答的，先用工具查数仓；数仓查不到的（方法论、原因解释、经验），再走知识库。否则模型遇到"ROI 为什么低"会直接去知识库捞一段泛泛而谈的经验，而正确答案是先查明细定位是哪个渠道掉的。

## 七、引用与溯源

### 7.1 为什么必须做

- **可信**：用户能点开原文核对，而不是只能选择信或不信。
- **可调试**：答错了能立刻分清是"检索错了"还是"生成错了"。
- **可追责**：业务场景里，一个基于文档的结论和一句模型自己编的话，责任完全不同。

### 7.2 怎么实现

1. **建库时给每个 chunk 存元数据**：`source`（文件名）、`section`（标题路径）、`chunk_id`、`updated_at`。
2. **拼 prompt 时给资料编号**：`[1] ... [2] ...`。
3. **在 prompt 里要求标注**：`每句结论后用 [编号] 标注依据；没有依据的句子不要写`。
4. **返回时把编号映射回元数据**，前端渲染成可点击的来源卡片。

```python
return {
    "answer": text,
    "citations": [
        {"id": 1, "source": "playbook.md", "section": "ROI 判断", "chunk_id": "chunk-12"},
    ],
}
```

### 7.3 易错点

- 只让模型"提到来源名"，不给结构化 id → 前端没法定位，模型还可能把文件名记错。
- 引用编号与资料顺序错位 → 模型常见错误。稳妥做法是在返回后用字符串匹配校验编号是否越界，越界的引用直接丢弃。
- 引用粒度太粗（只标到整篇文档）→ 用户还是要自己找。标到 section 才有用。

## 八、如何评估 RAG 效果

### 8.1 先分开评：检索 vs 生成

RAG 的错误可以清楚分成两段，混在一起评就永远不知道该改哪。

| 环节 | 指标 | 怎么算 |
|---|---|---|
| 检索 | **recall@k** | 标准答案所在的 chunk 有没有出现在前 k 条里 |
| 检索 | precision@k / MRR | 前 k 条里有多少是相关的；正确结果排在第几位 |
| 生成 | 忠实度（faithfulness） | 回答里的每个论断能否在检索结果中找到依据 |
| 生成 | 答案相关性 | 回答是否真的解决了问题 |
| 端到端 | 人工通过率 | 抽 30~50 个真实问题，人判"能用 / 不能用" |

**优先看 recall@k。** 检索没召回，生成再强也救不回来；检索召回了但生成用错，那是 prompt 的问题，好修。

### 8.2 项目里的验证方式

建库 8 个 chunk，用问题"D7 ROAS 低于 70% 怎么优化"做检索验证，确认正确命中对应的方法论段落。

这个验证很小，但它验证的是**整条链路的连通性**：切分没切断、embedding 能编码中文、向量库能查、相似度排序合理。8 条数据跑通，再往上加语料才不会一出问题就无从下手。

（源笔记未展开：没有生成侧的评估记录，也没有留存评估集。要往生产走，这两样必须补。）

### 8.3 建评估集的正确姿势

- 问题要从**真实使用场景**里来，不要自己编。
- 每个问题标注**标准答案所在的 chunk_id**，这是算 recall 的前提。
- 必须包含 **10~20 个"库里没有答案"的问题**，用来验证阈值和"说不知道"的能力。只测能答的题，会系统性地高估效果。

## 九、易错点清单

| 易错点 | 后果 | 正确做法 |
|---|---|---|
| 把 RAG 说成"训练模型" | 面试直接减分 | RAG 不训练，只做检索增强 |
| embedding 模型说成"自己训的" | 诚信问题 | 是现成模型（MiniLM / bge-m3） |
| 建库与查询用不同模型 | 检索接近随机 | 同一模型同一版本，换模型必须重建库 |
| 没有相似度阈值 | 用不相关资料硬答，幻觉更严重 | 低于阈值返回"不知道" |
| 用 RAG 做统计/聚合 | 数字不可信 | 数值走数仓，RAG 只处理文本经验 |
| 用 RAG 装指标口径 | 会漏会歪 | 口径走语义层精确查询 |
| chunk 不带标题路径 | 检索到也读不懂 | 正文前拼标题层级 |
| 只测"能答的题" | 高估效果 | 评估集必须含无答案问题 |

## 面试速查

- **RAG 是什么？** → 检索增强生成，回答前先从知识库取相关资料拼进 prompt，不训练模型。
- **RAG 解决什么问题？** → 私有/最新知识缺失、幻觉、无法引用，同时让知识更新不用重训。
- **RAG 五步？** → 切块、嵌入、检索、增强、生成。
- **切分粒度怎么定？** → 500~1000 字；太大语义被稀释检索不准，太小缺上下文。
- **三种切分策略？** → 固定长度、按语义结构（标题/段落）、带重叠。
- **中文 embedding 选什么？** → bge-m3；英文用 text-embedding-3 系列。
- **DeepSeek 能做 embedding 吗？** → 不能，只有 chat 接口。
- **向量库为什么不用 MySQL？** → 百万级逐条算距离太慢，向量库靠 ANN 索引把延迟降数量级。
- **ChromaDB 适合什么场景？** → 单机、小库、原型验证；大规模换 Milvus / Qdrant。
- **向量检索和 BM25 的区别？** → 前者看语义，后者看词命中；编号、缩写只有 BM25 抓得住。
- **为什么要混合检索？** → 补单一检索器的盲区，用 RRF 按排名融合。
- **top-k 怎么定？** → 常用 3~5，看 recall@k 曲线是否已平；配合 rerank 可粗召回 20~50。
- **为什么要设相似度阈值？** → 模型不会质疑上下文，错的资料比没有资料更危险。
- **rerank 为什么有效？** → cross-encoder 让问题和文档同注意力交互，比双塔的一次距离更准。
- **元数据过滤的两个价值？** → 提精度、控权限。
- **什么数据适合 RAG？** → 非结构化文本经验；能写 SQL 查出来的都走数仓。
- **为什么口径不能放 RAG？** → 相似度检索会漏会歪，口径必须精确键值查询。
- **RAG 怎么接进 Agent？** → 做成 `search_knowledge` 工具，靠 description 写清触发场景和边界。
- **怎么做引用？** → chunk 存 source/section，prompt 里编号并要求标注，返回时映射回元数据。
- **RAG 怎么评估？** → 分开评：检索看 recall@k，生成看忠实度；评估集要含无答案问题。
- **流式输出怎么开？** → `stream=True`，收益是首字延迟，代价是 usage 统计和错误处理更麻烦。
