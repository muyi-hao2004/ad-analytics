## 一、项目全景：两个子项目，一条主线

```
ad-analytics/                        ← 学习型项目：完整的数据分析流水线
├── data/                            原始 CSV
├── src/                             data_loader / cleaning / metrics / anomaly / database / report
├── reports/                         HTML 日报
└── iaa-analytics-agent/             ← 进阶项目：仿真 BI 中台 + Agent 决策
    ├── warehouse/                   ODS / DWD / DWS / ADS 四层
    ├── semantic/                    指标语义层
    ├── platform_layer.py            平台抽象（Mock 实现）
    ├── app.py                       FastAPI 后端
    ├── src/agent.py                 Agent 主循环
    └── dags/                        Airflow DAG
```

**一句话定位**：

> 一个海外 IAA 广告投放的数据分析与决策系统——从原始投放数据出发，经过四层数仓建模，产出业务指标，再由 LLM Agent 每天读取快照、调用工具、给出「删 / 留 / 加预算」的建议，人工确认后执行。

## 二、ad-analytics：六步流水线

```
原始 CSV → ①加载 → ②清洗 → ③指标计算 → ④异常检测 → ⑤写 MySQL → ⑥HTML 日报
```

| 步骤 | 模块 | 干什么 | 关键技术点 |
|---|---|---|---|
| ① 加载 | `data_loader` | 读 CSV | `encoding` 防乱码、`parse_dates` 转日期、读后校验 + 摘要 |
| ② 清洗 | `cleaning` | 6 步洗数据 | 标准化列名 / 类型转换 / 去重 / 补缺失 / 去异常值 / **零曝光过滤** |
| ③ 指标 | `metrics` | 算广告指标 | CTR / CVR / CPC / CPA + 环比（shift）/ 移动平均（rolling）/ 排名（rank） |
| ④ 异常 | `anomaly_detection` | 找异常 | 5 种异常 + 严重程度分级 |
| ⑤ 存储 | `database` | 写 MySQL | SQLAlchemy + `df.to_sql` |
| ⑥ 报表 | `report` | 生成 HTML | Jinja2 模板渲染 |

### 2.1 清洗为什么是这个顺序

```
标准化（列名/类型） → 去重 → 补缺失 → 去异常 → 业务过滤（零曝光）
```

逻辑是「先整理形状，再处理内容」：列名和类型不统一，后面所有操作都不可靠；去重要在补缺失之前（否则会补出重复）；去异常要在补缺失之后（否则缺失值会被当成异常）。

### 2.2 零曝光为什么必须过滤

`impressions = 0` 时 CTR = 点击 / 0，分母为零。更重要的是：零曝光意味着广告**根本没投出去**，这类记录不反映素材质量，留在表里会污染所有比率指标。

实测：1069 行里删掉 28 行零曝光，剩 1041 行。

### 2.3 异常检测模块实现（第 ④ 步展开）

#### 两种方法

| 方法 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **统计规则**（项目采用） | 按业务经验设阈值，超阈值即异常 | 简单、可解释、不需要训练数据 | 阈值靠人定，复杂异常抓不到 |
| 机器学习 | 自动学「正常模式」，偏离即异常 | 能抓复杂异常 | 难解释、需要数据量、调参复杂 |

常见算法：Isolation Forest（孤立森林）、One-Class SVM、Autoencoder。

#### 五种异常的检测规则

| 异常类型 | 检测规则 | 严重程度 |
|---|---|---|
| 花费暴涨 | 当天花费 > 前 7 天平均花费 × 1.5 | 高 |
| 点击率过低 | CTR < 1%（且曝光 > 100 才检测） | 中 |
| 转化率过低 | CVR < 1%（且点击 > 50 才检测） | 中 |
| CPA 过高 | CPA > 全部记录平均 CPA × 2 | 高 |
| 零曝光 | 曝光量 = 0 | 高 |

每条异常记录包含：日期、渠道、计划名、异常类型、实际值、阈值、严重程度、描述。

#### 六个函数

| 函数 | 要点 |
|---|---|
| `detect_spend_surge(df, threshold=1.5)` | 按渠道 + 日期分组算当天花费；**前 7 天平均必须是同一渠道自己的**；历史不足 7 天跳过，历史均值为 0 跳过 |
| `detect_low_ctr(df, threshold=0.01)` | 按日期 + 渠道 + 计划分组求曝光和点击；`np.where` 除零保护；**曝光 > 100 才检测** |
| `detect_low_cvr(df, threshold=0.01)` | 与 CTR 版几乎一致，指标换成 `conversions / clicks`；**点击 > 50 才检测** |
| `detect_high_cpa(df, threshold_multiplier=2.0)` | 无转化时 CPA 设为 `np.inf`；**求平均 CPA 时必须排除无穷大**，否则均值被拉爆；阈值 = 平均 × 2 |
| `detect_zero_impressions(df)` | 直接筛 `impressions == 0`；**必须在清洗前调用**，因为清洗模块已经把零曝光删掉了 |
| `detect_all_anomalies(df, config=None)` | 依次调用五个检测，`pd.concat(ignore_index=True)` 合并，按严重程度排序；支持 `config.get('key', 默认值)` 覆盖阈值 |

#### 五个关键语法

```python
# ① np.where 做除零保护
grouped['ctr'] = np.where(
    grouped['impressions'] > 0,
    grouped['clicks'] / grouped['impressions'],
    0
)

# ② 命名聚合：不同列用不同聚合方式
grouped = df.groupby(['date', 'channel', 'campaign']).agg({
    'impressions': 'sum',
    'clicks': 'sum'
}).reset_index()

# ③ concat 合并多个 DataFrame（按行拼，重建索引）
all_anomalies = pd.concat(anomaly_list, ignore_index=True)

# ④ map 把文字等级转成数字，用于排序
severity_order = {'高': 0, '中': 1, '低': 2}
all_anomalies['severity_order'] = all_anomalies['severity'].map(severity_order)

# ⑤ pandas 多条件筛选：用 & 不用 and，每个条件必须加括号
low_ctr = grouped[(grouped['ctr'] < threshold) & (grouped['impressions'] > 100)]
```

#### 小样本过滤为什么必要

CTR 检测要求曝光 > 100，CVR 检测要求点击 > 50。

原因：样本量太小时比率波动极大。10 次曝光 1 次点击 = CTR 10%，但这个数字没有任何统计意义。**不做小样本过滤，异常检测会被噪音淹没，每天报出上百条「异常」，业务方会直接关掉这个功能。**

#### 实测结果（1041 条清洗后数据）

| 异常 | 条数 | 等级 |
|---|---|---|
| 点击率过低 | 70 | 中 |
| CPA 过高 | 36 | 高 |
| 花费暴涨 | 20 | 高 |
| 转化率过低 | 12 | 中 |
| 零曝光 | 0（清洗已删） | — |
| **合计** | **138** | 高 56 / 中 82 |

#### 一个容易漏的顺序问题

`detect_zero_impressions()` 和清洗模块的「零曝光过滤」是**互斥**的：

- 清洗里删掉零曝光 → 后续指标计算不会除零
- 但异常检测想报告「有 28 条零曝光」时，数据已经被删了

所以这个函数要单独跑在**清洗前的原始数据**上。这类「同一个现象在不同阶段有不同用途」的情况，是多模块流水线里最容易出错的地方。

## 三、IAA Agent 中台：数仓建模

### 3.1 双轴事实表（核心设计）

**install_date × report_date 两个日期轴 + 7 个维度 + 6 个度量，共 15 字段。**

| 组成 | 内容 |
|---|---|
| 双时间轴 | `install_date`（安装日）、`report_date`（回传日） |
| 维度 | campaign、ad_group、creative、country、sub_channel、投放人、包 |
| 度量（原子） | `dact`（活跃）、`drev`（收入）、`dimp`（展示）、`dview`（观次）等 |

**设计意义**：

- 按 `report_date` 切 → 日历视角，今天账上有多少钱
- 按 `install_date` 切 → cohort 视角，这批用户后续表现如何

**原子 vs 派生**：只落原子度量（人数、收入、展示数），派生指标（留存率、eCPM、ROI、CPI）全部用时计算。

> 为什么？因为比率不可加。存了留存率，就没法跨 cohort 汇总；存了原子值，任何比率都能重新算。

### 3.2 买量与变现必须拆表

| | 买量 | 变现 |
|---|---|---|
| 业务含义 | 投放当天的动作 | 安装后第 N 天的表现 |
| 时间轴 | 单轴（report_date） | **双轴**（install_date × report_date） |
| 关键字段 | clicks、buy_impressions、installs、spend | dact、drev、dimp、dview |

**时间轴不同，硬塞进一张表会导致大量空值和不一致的聚合语义。** 所以拆成：

- `acquisition_daily`（买量日表，单轴）
- `monetization_fact`（变现事实表，双轴）

### 3.3 五张维度表（星型模型）

```
dim_campaign            系列（含投放人、出价策略）
dim_campaign_country    系列 × 国家粒度（预算、目标值）
dim_creative            素材（类型、上线时间）
dim_sub_channel         子渠道（Unity / Kwai / NewsBreak...）
dim_country             国家（T0/T1 分层、时区、货币）
```

`dim_campaign_country` 是特意拆出来的——预算和目标值挂在「系列 × 国家」粒度上，不在 campaign 上。这个粒度直接决定「加预算」这个动作的作用域。

### 3.4 SCD Type 2：配置变更要留痕

预算、目标 ROAS、出价策略会被优化师随时调整。如果直接覆盖（Type 1），历史就丢了。

**Type 2 的做法**：变更时不改旧行，而是「关旧 + 插新」。

```
campaign_id | 目标ROAS | start_date | end_date   | is_current
ch_001      | 70%     | 2026-09-01 | 2026-10-05 | 0
ch_001      | 65%     | 2026-10-05 | 9999-12-31 | 1
```

**为什么必须这么做**：Agent 要判断「这个系列现在不达标」时，需要知道「它当初的目标是多少」。没有历史，就只能用当前目标去评价过去的表现，结论必然是错的。

### 3.5 四层数仓

| 层 | 职责 | 关键点 |
|---|---|---|
| **ODS** | 只搬不洗，落 Parquet | 保留原始形态，可重跑 |
| **DWD** | 5 条清洗规则 | 去重 / 补空 / 修负值（clip 到 0）/ 日期标准化 / 类型规范 |
| **DWS** | pivot 成宽表 | 按 `day_offset`（安装后第 N 天）算 4 个度量，列名 `dact1` / `drev2` |
| **ADS** | 派生指标日常表 | `ret_n` / `ecpm_n` / `roi_n` / `cpi` |

**DWS 的口径陷阱**：`drev2` 的「2」是安装后第 2 天，不是日历日期。10-01 的 `drev2` 和 10-02 的 `drev1` 都发生在 10-03，但属于不同 cohort。

### 3.6 两条数据通道

| 通道 | 数据 | 走向 |
|---|---|---|
| 结果数据 | 广告平台 API 推送 | 四层数仓（事实表） |
| 配置数据 | 优化师在后台手工设置 | Playwright 抓取 → 维度表 |

**为什么要分开**：一类是「跑出来的数」，一类是「人设的规则」。前者高频、结构化；后者低频、变更要留痕（SCD2）。混在一条通道里，语义会打架。

## 四、后端与平台抽象层

### 4.1 为什么需要后端

中台的「读」用静态 HTML 就够，「写」（删子渠道、调预算、改目标）**必须经后端**——浏览器的 JS 碰不到广告平台，也拿不到凭证。

### 4.2 平台对接的三种方式

| 方式 | 说明 | 现状 |
|---|---|---|
| ① 官方 API | 平台开放接口 | 未接（拿不到正式授权） |
| ② Playwright 模拟 | 浏览器自动化操作后台 | 已验证可行 |
| ③ Mock | 改本地 `dim.db` | **当前使用** |

### 4.3 依赖倒置

```python
class BasePlatform(ABC):
    @abstractmethod
    def delete_sub_channel(self, ...): ...
    @abstractmethod
    def adjust_budget(self, ...): ...

class MockPlatform(BasePlatform):
    """改本地 SQLite，用于开发和演示"""

def get_platform() -> BasePlatform:
    return MockPlatform()

class RealPlatform(BasePlatform):
    """Playwright 或官方 API，将来替换"""
```

上层业务代码只依赖 `BasePlatform`，换实现时不用改调用方。**这是这个项目里最能体现工程思维的一处设计。**

### 4.4 FastAPI 接口

```
POST /api/delete_sub_channel
POST /api/adjust_budget
POST /api/adjust_target
GET  /api/logs
GET  /api/health
```

配 CORS，供前端看板直接调用。

**踩坑**：文件原名 `platform.py`，与 Python 标准库 `platform` 重名，导致 `import platform` 拿到的是自己的模块。改名 `platform_layer.py` 解决。

## 五、Airflow 落地

### 5.1 为什么用 Docker

Windows 原生装 Airflow 失败——依赖 `pwd` 等 Unix-only 模块。改容器部署。

| 项 | 配置 |
|---|---|
| 镜像 | `apache/airflow:2.10.5-python3.12`（国内源 `docker.1panel.live`） |
| 元数据库 | Postgres |
| 执行器 | LocalExecutor |
| 容器 | postgres / scheduler / webserver / triggerer |

### 5.2 DAG

```python
update_warehouse >> run_agent   # 先造数入仓，再跑 Agent 分析
```

cron：`0 8 * * *`（每天早上 8 点）。

**为什么是这个依赖**：Agent 读的是 DWS/ADS 的快照。如果数仓没更新完就跑 Agent，它拿到的是昨天的结论，会做重复决策。

### 5.3 四个真实踩坑（面试可讲「解决过真问题」）

| 问题 | 现象 | 解法 |
|---|---|---|
| Docker Hub 超时 | 拉镜像卡住 | 换国内镜像源 |
| root 不能 pip | 官方镜像以 root 运行 | 切 `USER airflow` |
| SQLite 卷不共享 | 多容器读不到同一份元数据 | 改共享卷 / 升级 Postgres |
| 挂载目录属主 | 容器内无写权限 | `user: "50000:0"` + `AIRFLOW_UID=50000` |

### 5.4 SQLite → Postgres 的升级（讲「为什么」比讲「做了什么」加分）

| 改动 | 原因 |
|---|---|
| `SequentialExecutor` → `LocalExecutor` | SQLite 只支持串行，Postgres 支持并行 |
| 连接串改 `postgresql+psycopg2://` | 元数据库迁到 Postgres |
| 新增 postgres 服务 | 含 healthcheck `pg_isready` + 卷持久化 |
| 加 `depends_on: postgres: service_healthy` | 避免调度器先起来连不上库 |

### 5.5 LLM 调用挂起

`run_agent` 曾经卡在 DeepSeek 的第一次 POST 上：HTTP 200 但响应体不返回，宿主机 curl 也超时（exit 124）。定位是服务端问题，不是 Airflow/Docker。

**解法**：LLM 客户端加 `timeout=60` + `max_retries=2`。核心思想是——**外部依赖必须有超时，不能让它拖死整个 DAG**。

## 六、Agent 部分（一句话带过，详见 17 篇）

```
读快照（只给结论，不给原始数据）
   → LLM 决策：调哪些工具
   → 工具执行：查 campaign 指标 / 查历史决策 / 查知识库
   → 输出建议：删 / 留 / 加预算 + 理由
   → 人工确认（pending / approve / reject）
   → 执行写操作
```

关键设计：快照只给结论、工具 description 写清触发场景与边界、写操作默认 `dry_run=True`、全链路 trace 日志。

## 七、高频追问的标准答案

### Q1：为什么删零曝光？

> `impressions = 0` 时 CTR 的分母为零，指标无意义；而且零曝光说明广告根本没投出去，不反映素材质量，留着会污染比率。实测 1069 行删掉 28 行。

### Q2：清洗为什么是这 6 步这个顺序？

> 先整理形状（标准化列名和类型），再去重，再补缺失，再去异常，最后做业务过滤。顺序反了会出问题——比如先去重再补缺失，补完可能又出现重复；先补缺失再去异常，缺失值会被误判成异常。

### Q3：异常阈值怎么定的？

> 初期用业务经验值（比如目标 CPI 是某个数，超了算异常）。更严谨的是统计方法：3-sigma 或者 IQR。因为不同 campaign 的量级差异大，固定阈值容易误报，动态阈值是后续优化方向。

### Q4：为什么存 MySQL 不直接存 CSV？

> CSV 是文件，不能做多表关联、并发查询、权限控制。入库之后可以用 SQL 灵活聚合、JOIN 维度表、多人同时访问，也能被下游系统和 Agent 直接读。

### Q5：双轴事实表为什么不建两张表？

> 「双轴」是**一张表里两个日期维度**，不是两张表。建两张表会导致同一笔收入在两处重复出现，还得再做对齐，反而更复杂。

### Q6：为什么只存原子度量，不存比率？

> 比率不可加。存了留存率，跨 cohort 汇总时就没法加权；存了活跃人数和安装数，任何比率都能重算。所以 ADS 层才生成派生指标。

### Q7：SCD Type 2 解决了什么问题？

> 预算和目标值会被优化师随时改。如果直接覆盖，历史就丢了，Agent 评价过去的表现时会拿现在的目标去套，结论是错的。Type 2 用「关旧插新」保留版本，每个决策都能对应到当时的配置。

### Q8：为什么要拆买量和变现两张表？

> 时间轴不一样。买量是投放当天的动作，单轴；变现是安装后第 N 天的表现，双轴。硬塞一张表会有大量空值，聚合语义也会混。

### Q9：平台对接为什么用 Mock？

> 拿不到真实平台的 API 授权，所以先用 Mock 改本地库跑通全链路。但上层代码依赖的是 `BasePlatform` 抽象接口，将来换成 Playwright 或官方 API 只需要加一个实现类，不用改调用方。

### Q10：这个项目是 AI 写的吗？（诚实版）

> 是学习项目，过程中大量借助了 AI 辅助写代码。但业务逻辑、指标口径、数仓分层和数据流是我自己设计的，每个模块我都能讲清它在做什么、为什么这么做。代码细节有些需要查，但设计决策我能扛住追问。

| 「异常检测会删数据」 | 标记 + 告警，不删原始数据 |
| 「完全自己写的」 | AI 辅助，但设计和口径自己定 |

## 九、怎么讲（两个版本）

### 30 秒版

> 我做了两个阶段的项目。第一个是从 CSV 到 HTML 日报的数据分析流水线，六个模块：加载、清洗、算指标、异常检测、写 MySQL、出报表。第二个是进阶的仿真 BI 中台，做了 install_date × report_date 的双轴事实表，既能看日历收入也能看 cohort 表现；买量和变现因为时间轴不同拆成两张表；配置变更用 SCD2 保留历史。数仓分 ODS/DWD/DWS/ADS 四层。调度用 Airflow 容器化部署，跑在 Postgres 元数据库上。

### 2 分钟版（加设计理由）

在 30 秒版基础上补三句：

1. 「只存原子度量不存比率，是因为比率不可加，跨 cohort 汇总会失真。」
2. 「平台对接用了依赖倒置——上层依赖抽象接口，底层现在是 Mock，将来换 Playwright 或官方 API 不用改业务代码。」
3. 「Agent 每天的决策是从 ADS 快照起步的，所以 DAG 里必须 `update_warehouse >> run_agent`，否则它拿到的是昨天的结论。」

## 十、面试速查

- **项目一句话？** → IAA 广告投放的数据分析与决策系统，四层数仓 + Agent 决策。
- **六步流水线？** → 加载/清洗/指标/异常/入库/报表。
- **双轴事实表的价值？** → 一张表同时支持日历视角和 cohort 视角。
- **为什么要拆买量变现？** → 时间轴不同，单轴 vs 双轴。
- **SCD2 为什么必要？** → 配置会变，历史版本决定决策评价是否成立。
- **只存原子度量的原因？** → 比率不可加。
- **DWS 的 drev2 是什么？** → 安装后第 2 天的收入，不是 10-02 的收入。
- **平台抽象层的意义？** → 依赖倒置，Mock 与真实实现可替换。
- **Airflow 为什么上 Docker？** → Windows 原生缺 Unix 模块。
- **SQLite 换 Postgres 换来了什么？** → 并行执行器。
- **LLM 调用的最大风险？** → 无超时导致整个 DAG 阻塞。

## 附录：从「看懂代码」到「写出代码」

> 这个项目大量代码是 AI 辅助生成的。面试官迟早会问「这段你能自己写吗」。下面这套方法是为了那个问题准备的。

### 为什么看懂了却写不出来

「看懂」和「写出」是两个完全不同的能力，中间差了大约 100 倍的练习量。

| 能力 | 难度 |
|---|---|
| 看懂代码 | ⭐⭐ |
| 修改代码 | ⭐⭐⭐ |
| 调试代码 | ⭐⭐⭐⭐ |
| 从零写出 | ⭐⭐⭐⭐⭐ |

看懂是被动识别，写出是主动生成。看别人骑车和自己骑是两件事。

### 四阶段练习法

**阶段 1 · 仿写（看着写）**

1. 看着代码手打抄一遍，**不要复制粘贴**
2. 每一行想「这一行在干什么」
3. 运行确认能跑通
4. 删掉，不看代码自己再写一遍
5. 写不出来就看一眼，继续写

**阶段 2 · 改写（改着玩）**

拿能跑通的函数动逻辑：改阈值、改参数、加新异常类型、改分组维度、加新功能。

这一步的价值在于——**你必须先理解结构，才能改对**。

**阶段 3 · 拆解（大函数拆小步骤）**

面对复杂需求，拆成可以单独验证的小步：

```
第一步：分组计算   → 写一步，打印确认
第二步：排序       → 加一步，打印确认
第三步：算历史均值 → 加一步
第四步：比较阈值   → 加一步
第五步：组装结果   → 加一步
```

**每写完一步就运行验证，不要一口气写完再调试。** 这是新手和熟手最大的差别。

**阶段 4 · 默写（不看写）**

1. 只看需求和思路，不看具体代码
2. 合上资料从零写
3. 卡住时问自己「怎么拆的？第一步是什么？」
4. 写完和原代码对比

### 四周计划（针对本项目）

| 周 | 任务 |
|---|---|
| 第 1 周 | 仿写 6 个异常检测函数，从最简单的 `detect_zero_impressions` 开始，每天 1 个 |
| 第 2 周 | 给每个函数加新参数 / 新异常类型（改写） |
| 第 3 周 | 新需求自己拆步骤写（拆解） |
| 第 4 周 | 自己设计一个小模块（综合） |

### 一个必须接受的事实

实际工作中 **90% 的代码不是从零写的**，而是：

- 参考已有代码，复制过来改
- 参考官方文档 / 示例，改参数
- 问 AI 生成，然后检查、修改、调试
- 搜 Stack Overflow 找现成方案

真正需要「从零写」的场景很少。**能看懂 + 会改 + 会调试，已经够用。** 面试时与其假装能默写，不如说清「我理解每个模块的设计理由和边界，实现细节我可以借助工具完成」——这更符合真实工作状态。
