# 数仓分层与建模

本篇覆盖：广告投放数仓的四层结构（ODS / DWD / DWS / ADS）与各层裁剪原则、分层存在的理由、ETL 与 ELT 的差别。
维度建模部分包括事实表与维度表、星型与雪花、维度退化，以及双轴事实表和原子度量列的设计动因。
建模之后是 SCD 缓慢变化维、操作日志表、宽表与拉链表、数据质量与幂等、全量与增量。
场景取自 IAA 休闲游戏买量分析项目：投放侧数据来自渠道 API，变现侧数据按安装后第 N 天回传，配置侧数据来自优化师后台。

## 〇、业务场景与指标口径

建模的每个选择都由业务约束决定，先把约束摆清楚。

| 项 | 内容 |
|---|---|
| 市场 | 美国 T0 |
| 变现模式 | 网赚类 IAA（In-App Advertising），**纯广告变现**，无内购、无订阅 |
| 核心目标 | **D7 ROAS 70%** |
| 投放层级 | campaign（广告系列，连着投放人）→ ad_group（广告组）→ creative（素材） |
| 建系列策略 | 固定选一种：D7_ROAS / D0_ROAS / CPI（ROAS 填百分比，CPI 填美元） |
| 素材归因 | last-click |
| 观次 | 用户主动观看激励视频的平均次数 = `rewarded_views / active_users` |

两条数据通道，走向完全不同：

| 通道 | 数据 | 走向 |
|---|---|---|
| 结果数据 | 渠道 API 推送的消耗、转化、收入 | 四层数仓，最终成为事实表 |
| 配置数据 | 优化师在后台设置的预算、目标值、策略 | Playwright 抓取后写入维度表 |

这个区分很重要：**结果数据是"发生了什么"，配置数据是"当时是怎么设的"**。前者进事实表，后者进维度表并需要 SCD 留痕；两者混在一起，就无法回答"这个系列在目标 ROAS 是 70% 时的表现如何"。

## 一、为什么要分层

### 1.1 五个理由

| 理由 | 具体含义 |
|---|---|
| 消除重复计算 | 同一份清洗逻辑只写一次，下游全部复用，不必每个需求重写一遍 |
| 隔离上游变化 | 上游表结构或字段口径变了，只改 ODS→DWD 一段，DWS / ADS 不受影响 |
| 缩小排错范围 | 报表数字对不上时，从 ADS 逐层往上比对，能快速定位是哪一层的口径出了问题 |
| 节省计算资源 | 全量明细只被扫一次，汇总结果反复复用，避免每个新需求都去扫原始日志 |
| 提升查询性能 | 报表直接读汇总好的宽表，不必每次对原始明细做大规模聚合 |

### 1.2 追问：为什么不直接从 ODS 写 SQL 出报表

因为**口径会失控**。每个分析师都要自己实现一遍去重、时区换算、异常值过滤，必然出现"同一个 CPA，三个人算出三个数"。分层的本质是**把口径固化成代码**，让"消耗""转化""留存"这些词在组织内只有一种算法。

### 1.3 分层的代价

分层不是免费的：多一层就多一次读写、多一份存储、多一段调度依赖。所以层数要克制，常见做法是四层，小团队可以压到三层（ODS / DWD / ADS），把 DWS 的聚合直接写进 ADS。判断标准是**这张表是否被两个以上下游复用**：只有一处用，就不值得单独成层。

## 二、四层架构全景

```
ods_ad_cost_log              渠道消耗日志（API 原样落地）
ods_ad_click_log             点击流埋点
ods_ad_conversion_log        转化回传
        │
        ├── dwd_ad_cost_detail          去重 / 标准化后的消耗明细
        └── dwd_ad_conversion_detail    完成归因后的转化明细
                    │
                    ├── dws_ad_channel_daily    渠道 × 日
                    ├── dws_ad_campaign_daily   计划 × 日
                    └── dws_ad_creative_daily   素材 × 日
                                │
                                ├── ads_ad_daily_report     日报（BI / API）
                                └── ads_ad_anomaly_alert    异常检测结果
```

一句话概括四层：**ODS 原样落地保证可追溯，DWD 清洗标准化形成可信明细，DWS 按主题域聚合成可复用宽表，ADS 面向应用直接出数。**

同一套分层在小脚本里也能对应上，不必等有了集群才叫数仓：

| 项目中的形态 | 对应层级 |
|---|---|
| `data/raw/` 下的原始 CSV | ODS |
| `clean_ad_data()` 清洗后的数据 | DWD |
| `group_by_dimension()` 产出的渠道汇总 | DWS |
| 生成的 HTML 日报 | ADS |

### 2.1 ODS（Operational Data Store，原始数据层）

职责：**原样落地，不做任何业务加工。**

| 表 | 内容 | 来源 |
|---|---|---|
| `ods_ad_cost_log` | 渠道消耗日志 | Facebook / Google / TikTok 等渠道 API |
| `ods_ad_click_log` | 点击流埋点 | 客户端埋点上报 |
| `ods_ad_conversion_log` | 转化回传 | 归因平台回传 |

设计要点：

- 字段与上游**完全一致**，一个不多一个不少，字段名也尽量不改。
- 按 `dt` 分区，存储格式用 **Parquet**（列式 + 压缩，扫描成本远低于 CSV）。
- 增加 `etl_time` 记录抽取时间，便于判断数据新鲜度。
- 原始 JSON 即使已经解析过，也要**保留一份原始字段**（raw_json），方便上游改字段后回溯。

为什么 ODS 不做清洗：一是**可追溯**，上游数据出问题要能看到原始值；二是**重跑成本低**，加工逻辑写错了直接从 ODS 重跑，不必重新调 API 拉数（很多渠道 API 有频控，重拉很贵）。

### 2.2 DWD（Data Warehouse Detail，明细数据层）

职责：**清洗 + 标准化 + 维度退化**，产出"可信的明细事实"。

| 表 | 内容 |
|---|---|
| `dwd_ad_cost_detail` | 去重后的消耗明细 |
| `dwd_ad_conversion_detail` | 完成归因后的转化明细 |

五件标准动作：

1. **去重**：按 `channel + campaign_id + date` 去重，防止 API 分页重复拉取或调度重跑导致翻倍。
2. **异常值处理**：`cost < 0`、`impressions = 0 但 clicks > 0` 这类记录不直接删，而是**打标隔离**（`is_valid = false`），保留证据。
3. **标准化**：币种统一成 CNY，时区统一成 UTC+8，日期统一成 `yyyy-MM-dd` 字符串。
4. **维度退化**：把 `campaign_name`、`creative_name` 等高频维度**冗余**进明细表，减少下游 join。
5. **归因关联**：转化与点击按归因窗口关联（本项目为 7 天点击 / 1 天浏览，素材归因取 last-click）。

两类典型工程坑（都真实发生过）：

| 现象 | 根因 | 处理 |
|---|---|---|
| `2026-10-02T00:00:00+08:00` 解析失败 | 带时区的 ISO 字符串不是标准日期格式 | `pd.to_datetime(..., format="mixed")` + 正则剥掉时区后缀 |
| merge 报类型不匹配 | `install_date` 在一处是 datetime、另一处是 str | 全链路统一转字符串，落盘前断言 dtype |

DWD 与 ODS 的本质区别：ODS 是"数据的原样副本"，DWD 是"可信的明细事实"。**DWD 之后的数据下游可以直接信任，不需要每次再做防御性处理。**

### 2.3 DWS（Data Warehouse Summary，汇总数据层）

职责：**按主题域聚合，形成可复用的宽表。** 这是最核心、最值得投入设计的一层。

| 表 | 粒度 |
|---|---|
| `dws_ad_channel_daily` | 渠道 × 日 |
| `dws_ad_campaign_daily` | 计划 × 日 |
| `dws_ad_creative_daily` | 素材 × 日 |

#### 原子指标与派生指标

| 类型 | 字段 | 特性 |
|---|---|---|
| 原子指标 | `cost`、`impressions`、`clicks`、`conversions`、`revenue` | 可加，能直接 SUM |
| 派生指标 | CTR、CPC、CPA、ROI、eCPM | 不可加，必须用分子分母重算 |

| 派生指标 | 公式 |
|---|---|
| CTR | `SUM(clicks) / SUM(impressions)` |
| CPC | `SUM(cost) / SUM(clicks)` |
| CPA | `SUM(cost) / SUM(conversions)` |
| ROI | `SUM(revenue) / SUM(cost)` |
| eCPM | `SUM(revenue) / SUM(impressions) * 1000` |

#### 高频陷阱：CTR 为什么不能用 AVG

各渠道曝光量差异巨大，简单平均会让小曝光量渠道的极端值被放大。

举例：渠道 A 曝光 100 万、CTR 2%；渠道 B 曝光 1 000、CTR 50%。

- 错误算法 `AVG(ctr)` = 26%，完全失真。
- 正确算法 `SUM(clicks) / SUM(impressions)` = (20 000 + 500) / (1 000 000 + 1 000) ≈ 2.05%。

**所有比率型指标都只能"先 SUM 分子分母、再做除法"，不能对已经算好的比率再求平均。** 这也是后面"只存原子值"的直接原因。

#### 窗口指标：异常检测基线

```sql
-- 过去 7 天 CPA 均值，作为当天的异常检测基线
AVG(cpa) OVER (
    PARTITION BY channel
    ORDER BY dt
    ROWS BETWEEN 7 PRECEDING AND 1 PRECEDING
) AS cpa_7d_avg
```

注意是 `1 PRECEDING` 而不是 `CURRENT ROW`：基线**不能包含当天**，否则当天的异常值会把基线一起抬高，自己稀释掉自己，导致检测不出来。

#### 按 day_offset 做 pivot 的宽表

变现侧的统计口径不是日历日，而是"安装后第 N 天"。DWS 把长表 pivot 成宽表，列名形如 `dact1`、`drev2`、`dimp3`、`dview7`：

| 列 | 含义 |
|---|---|
| `dact{n}` | 安装后第 n 天的活跃用户数 |
| `drev{n}` | 安装后第 n 天的广告收入 |
| `dimp{n}` | 安装后第 n 天的广告展示次数 |
| `dview{n}` | 安装后第 n 天的激励视频观看次数 |

由此产生一个必须讲清楚的认知：**`drev2` 的"2"是相对安装日的偏移量，不是日历日期。** 10-01 这批用户的 `drev2` 落在 10-03，10-02 这批用户的 `drev1` 也落在 10-03——同一天，不同 cohort。日历口径与 cohort 口径不能混在一张表里直接相加。

### 2.4 ADS（Application Data Service，应用数据层）

职责：**面向具体应用，开箱即用。**

| 表 | 用途 |
|---|---|
| `ads_ad_daily_report` | 日报，直接喂 BI 和 FastAPI 接口 |
| `ads_ad_anomaly_alert` | 异常检测结果（含告警等级、同比环比） |

特点：

- 字段是**展示态**：有格式化字符串、有同比环比、有告警等级，不再是纯净的数值列。
- 数据量小，可以整体同步到 MySQL / ClickHouse 供接口低延迟查询。
- Agent 侧的 `query_ad_data`、`get_daily_report` 两个工具查的就应该是 ADS 层，而不是回头去扫 DWD。

### 2.5 各层裁剪原则

"裁剪"指每一层只保留自己该保留的数据，多余的列、多余的行、多余的历史都不往下一层带。

| 层 | 行裁剪 | 列裁剪 | 时间范围 |
|---|---|---|---|
| ODS | 不裁剪，全量落地 | 不裁剪，字段与上游一致 | 按业务要求长期保留（可冷归档） |
| DWD | 剔除明确无效数据但打标保留 | 只留分析需要的字段 + 退化维度 | 保留全部历史明细 |
| DWS | 只保留汇总粒度，不再有明细行 | 只留原子度量 + 公共维度 | 保留可支撑回溯的周期（如 2 年） |
| ADS | 只保留应用需要的切片 | 只留展示字段 | 按应用需求，通常 1 年以内 |

## 三、ETL 与 ELT

| | ETL | ELT |
|---|---|---|
| 全称 | Extract-Transform-Load | Extract-Load-Transform |
| 转换发生地 | 独立的转换引擎（如 Spark 作业、Python 脚本） | 目标库内部（用目标库的 SQL 算） |
| 落地顺序 | 先算好再入库 | 先原样入库，用时再算 |
| 适合 | 数据量大、转换逻辑复杂、目标库算力弱 | 目标库是 MPP / 数仓，算力强 |
| 典型形态 | 渠道 API → Python 清洗 → 写 Parquet | 日志 → 落 HDFS/对象存储 → Hive/Spark SQL 加工 |

本项目是**偏 ELT 的混合形态**：抽取后先原样落 ODS（Parquet），转换用 Python / SQL 在仓库内完成，本质是 ELT；但 DWD 的清洗逻辑由调度器里的 Python 任务承担，又带一点 ETL 的味道。

一句话区别：**ETL 是"算完再存"，ELT 是"先存再算"。** 云数仓算力便宜之后，ELT 成为主流，因为原始数据先落地才能支持"当初没想过的新问题"。

## 四、维度建模

### 4.1 事实表 vs 维度表

| | 事实表 | 维度表 |
|---|---|---|
| 存什么 | "发生了什么"，可度量的业务事件 | "从什么角度统计"，描述性属性 |
| 特征 | 行多、列少、数值为主、增长快 | 行少、列多、文本为主、增长慢 |
| 操作 | 追加 + 聚合 | 查询 + 关联，少量更新 |
| 本项目 | `dwd_ad_cost_detail`、变现双轴事实表 | `dim_campaign`、`dim_creative`、`dim_country` |

事实表的外键 + 度量值构成一行；维度表提供切分口径。**事实表回答"多少"，维度表回答"是谁的"。**

### 4.2 星型模型 vs 雪花模型

| | 星型（Star） | 雪花（Snowflake） |
|---|---|---|
| 结构 | 事实表居中，维度表直接环绕，不再向外延伸 | 维度表继续规范化，拆出子维度 |
| join 次数 | 少 | 多 |
| 冗余 | 有冗余，换查询性能 | 冗余少，省存储 |
| 可读性 | 好，业务方容易理解 | 差，需要多跳才看懂 |
| 工业界选择 | **主流** | 少数场景（维度层级深、变更频繁） |

工业界用星型而不是雪花：**join 更少、查询更快，牺牲一点存储换查询性能。** 在列存 + 廉价存储的今天，这个交换几乎总是划算的。

本项目的 5 张维度表构成标准星型：

```
dim_campaign         广告系列（连着投放人）
dim_campaign_country 系列 × 国家（存预算与目标值，供 LLM 读取）
dim_creative         素材
dim_sub_channel      子渠道
dim_country          国家 / 地区
```

`dim_campaign_country` 的粒度是"系列 × 国家"，不是单纯的系列，因为同一系列在不同国家可以设不同的预算和 ROAS 目标。

### 4.3 维度退化（Degenerate Dimension）

把维度属性**直接冗余进事实表**，不再单独建维表。典型是订单号、`campaign_name`、`creative_name`。

好处：少一次 join，查询快，SQL 简单。
代价：维度更新要回刷历史事实表（所以只对"基本不变"或"必须留当时值"的属性做退化）。

判断标准：**这个属性会不会变？** 会变且需要留痕的，走 SCD Type 2 建维表；基本不变又高频查询的，退化进事实表。

### 4.4 双轴事实表

这是本项目数据模型的核心设计：**一张事实表里同时存在 `install_date` 和 `report_date` 两个日期轴。**

| 轴 | 含义 | 切出来的口径 |
|---|---|---|
| `install_date` | 用户安装日，即 cohort 归属 | 同期群口径：这批用户生命周期内贡献了多少收入 |
| `report_date` | 数据回传 / 统计日 | 日历口径：今天实际到账多少收入 |

一行数据的语义是：**"`install_date` 这天安装的用户，在 `report_date` 这天的表现"**。表结构为 2 个日期 + 7 个维度 + 6 个度量，共 15 个字段。

为什么广告投放必须这么建：

1. **IAA 变现有回传延迟**。用户今天安装，收入要在后续 7 天、30 天里逐步回传。只按 `report_date` 存，就看不出"这批用户的长期价值"；只按 `install_date` 存，就看不到"今天账上有多少钱"。
2. **两个口径回答的是不同问题**。日历口径回答"今天赚了多少"（财务对账）；cohort 口径回答"这批量买得值不值"（投放决策）。ROAS 的 D7 目标本质是 cohort 指标。
3. **回传会修正历史**。同一批 `install_date` 的收入会随 `report_date` 推进不断累加，双轴天然支持"重刷历史"，不必改表结构。
4. **避免两套表对不上**。如果拆成"日历收入表"和"cohort 收入表"，两份数据各自加工，迟早口径漂移；双轴是一份明细，两种切法。

红线：**双轴是"一张表两个日期维度"，不是"两个事实表"。** 面试时说错会被直接判定为背概念。

### 4.5 买量与变现为什么拆表

| | 买量 | 变现 |
|---|---|---|
| 业务动作 | 投放当天发生的一次性支出 | 安装之后第 N 天持续产生的收入 |
| 时间轴 | 单轴（`report_date` 当天） | 双轴（`install_date` × `report_date`） |
| 度量 | clicks、buy_impressions、installs、spend | dact / drev / dimp / dview |
| 表 | `acquisition_daily` | 变现双轴事实表 |

时间轴不同，就不能塞进同一张表：买量没有"安装后第 N 天"的概念，变现没有"投放当天花了多少"的概念。硬合并会产生大量 NULL，且粒度语义混乱。拆表后用 `install_date` + 维度关联，是干净的星型结构。

### 4.6 原子度量列：为什么存 dact/drev/dimp/dview 而不是比率

DWS / 事实表只落**原子值**（可加的计数、金额），派生指标（留存率、eCPM、ROI、CPI）一律**用时再算，不落盘**。

| 做法 | 后果 |
|---|---|
| 存比率（如 `retention_rate`） | 无法跨 cohort / 跨渠道汇总，一加就错；口径一变（分母定义改了）历史数据全部作废，只能重跑 |
| 存原子值（`dact`、`drev`） | 任意维度 roll-up 都正确；新增一个比率指标只是改一条 SQL，不动历史数据 |

三个理由：

1. **可加性**：只有原子值满足"部分之和等于整体"，比率不满足。
2. **口径可变**：今天要 D1 留存，明天要 D3 留存，原子值都在，随时重算。
3. **避免精度损失**：比率落盘时的舍入误差会在多层聚合中被放大。

代价是存储变大、查询时要多写除法。在列存压缩下，这个代价很小。

## 五、SCD 缓慢变化维

SCD（Slowly Changing Dimension）解决"维度属性随时间变化，历史事实该按哪个版本归因"的问题。

### 5.1 三种类型

| 类型 | 做法 | 是否留历史 | 适用 |
|---|---|---|---|
| Type 1 | 直接覆盖原值 | 否 | 改错字、补全缺失值，不关心历史 |
| Type 2 | 关旧 + 插新，加 `start_date` / `end_date` / `is_current` | 是，全量留痕 | 需要按历史口径出报表 |
| Type 3 | 加一列 `previous_value`，只留上一版 | 只留一版 | 只关心"变化前是什么"，变化次数少 |

Type 2 的表结构：

| campaign_id | target_roas | start_date | end_date | is_current |
|---|---|---|---|---|
| C001 | 0.70 | 2026-09-01 | 2026-09-20 | false |
| C001 | 0.55 | 2026-09-21 | 9999-12-31 | true |

查询当前值加 `is_current = true`；查询某天的历史状态用 `dt BETWEEN start_date AND end_date`。

### 5.2 投放策略调整为什么必须用 Type 2

优化师会随时调整系列的出价策略和目标 ROAS（D7_ROAS / D0_ROAS / CPI）。如果用 Type 1 覆盖：

- 历史报表会用**新目标**去评价**旧投放**，ROAS 达标率全错。
- Agent 拿不到"这个系列原来的目标值是多少"，无法判断"是策略调整带来的改善，还是市场自然波动"。
- 无法复盘"哪次调价之后效果变差"，因为调价前的基线已经消失。

用 Type 2 留痕后，事实表按 `install_date` 落在哪个版本区间去关联维度，就能做到**当时的事实配当时的目标**。这是"历史不可变"原则在维度上的体现。

Type 2 的工程注意点：

- `end_date` 用 `9999-12-31` 而不是 NULL，避免 join 时 NULL 不相等。
- 同一业务键只能有一行 `is_current = true`，要加约束或用唯一索引保证。
- 关旧和插新必须在**同一事务**里，否则中途失败会出现两行 current 或零行 current。

## 六、操作日志表

SCD Type 2 存的是"状态的历史"，操作日志表存的是"动作的历史"。两者互补，不能互相替代。

| 字段 | 含义 |
|---|---|
| `log_id` | 自增主键 |
| `operator` | 操作人 |
| `action` | 动作类型：`delete_sub_channel` / `adjust_budget` / `adjust_target` |
| `target` | 操作对象（campaign_id、sub_channel_id） |
| `before_value` / `after_value` | 变更前后的值，JSON 存储 |
| `reason` | 变更原因（人工填写） |
| `created_at` | 操作时间 |

作用：

- **审计**：谁在什么时候把预算从 500 调到 2000，有据可查。
- **回滚**：出问题能按 `before_value` 还原。
- **分析**：把操作日志和效果数据按时间对齐，可以评估"人工干预是否有效"，这是 Agent 决策的对照组来源。

在本项目里，所有写操作都经 FastAPI 后端（`/api/delete_sub_channel`、`/adjust_budget`、`/adjust_target`），日志在同一事务内写入，`/api/logs` 提供查询。浏览器端 JS 碰不到投放平台，写操作必须过服务端，这也是日志能完整留存的前提。

## 七、宽表与拉链表

### 7.1 宽表

把多个维度、多个指标平铺到一张大表里，用**冗余换 join**。

| 优点 | 缺点 |
|---|---|
| 查询只需扫一张表，快 | 存储放大 |
| SQL 简单，BI 和 LLM 都好写 | 维度更新要回刷 |
| 列存下压缩率高（同列同质） | 字段多，血缘难维护 |

宽表是 DWS 的默认形态。判断是否该宽：**这张表是否被多个下游按不同维度组合查询**。只服务一个固定报表，没必要宽。

### 7.2 拉链表

记录每条记录的**完整生命周期**，只在属性变化时新增一行，用 `start_date` / `end_date` 圈定有效期。

```
user_id  status   start_date   end_date
U001     active   2026-09-01   2026-09-15
U001     churn    2026-09-16   9999-12-31
```

| | 每日全量快照 | 拉链表 |
|---|---|---|
| 存储 | 每天一份全量，30 天 = 30 份 | 只存变化，一份 |
| 查某天状态 | 直接取当天分区 | `dt BETWEEN start_date AND end_date` |
| 查变化轨迹 | 要跨分区对比 | 直接读全表 |
| 实现复杂度 | 低 | 高（需 merge 逻辑） |

拉链表与 SCD Type 2 是同一思想在不同对象上的应用：**SCD 面向维度表，拉链表面向实体表（用户、订单、设备）**。数据量大、变化率低的实体适合拉链；变化频繁或需要频繁取任意一天快照的，全量快照反而更简单可靠。

## 八、数据质量与幂等

### 8.1 六个质量维度

| 维度 | 检查方式 | 例子 |
|---|---|---|
| 完整性 | 非空率、行数波动 | 当日分区行数较昨日跌 50% 告警 |
| 唯一性 | 主键 / 业务键去重计数 | `channel + campaign_id + dt` 应唯一 |
| 一致性 | 跨表对账 | 数仓消耗合计 vs 渠道后台账单，差异 < 0.5% |
| 及时性 | 分区产出时间 | 8 点前必须产出，超时告警 |
| 有效性 | 枚举、值域、格式 | `country` 必须在国家码表内 |
| 准确性 | 业务规则、同比环比 | ROI 突然翻 10 倍，先怀疑数据而非爆量 |

处理原则：**能打标就不删除**。异常记录写进隔离区并标记原因，主链路继续跑，同时告警。直接删数据会让"为什么少了这些行"变成无法回答的问题。

质量检查要**阻断下游**：DWD 校验不通过时，DWS 任务不应启动。Airflow 里用一个校验 Task 放在依赖链中间，失败即熔断，避免脏数据扩散到 ADS 和 Agent。

### 8.2 幂等

定义：**同一个任务跑一次和跑十次，结果完全一样。**

为什么必须幂等：Airflow 失败会自动重试，补数会重跑历史分区，手动也可能触发一次。不幂等的任务每跑一次就多一份数据。

三种实现：

| 方式 | 做法 | 适用 |
|---|---|---|
| 先删后插 | 按 `dt` 删除分区再写入 | 数仓分区表，最常用 |
| 分区覆盖写 | `INSERT OVERWRITE` / Spark `mode("overwrite")` | Hive / Spark 表 |
| 主键 upsert | `ON DUPLICATE KEY UPDATE` / Delta MERGE | 数据库目标表 |

反例：`INSERT INTO ... SELECT` 追加写，重跑一次数据翻倍。这类写法在 DWD 层是事故高发点。

幂等还要求**可重入**：任务中途失败后重跑，不能依赖"上次已经写了一部分"这种状态。所有中间结果要么落在带版本号的临时目录，要么整分区覆盖。

### 8.3 失败重跑

- 从失败的那个 Task 接着跑，不必从头来（Airflow 的 Task 状态存在元数据库里）。
- 重跑要指定逻辑日期（`ds`），而不是"今天"，否则补历史时会写错分区。
- 补数要评估下游影响：重跑 DWD 某天，DWS / ADS 对应分区必须一起重算。

## 九、全量与增量

| | 全量加载 | 增量加载 |
|---|---|---|
| 做法 | 每次把源数据全部重算重写 | 只处理新增或变化的数据 |
| 优点 | 简单，天然幂等，不会漏 | 快，省资源 |
| 缺点 | 数据量大了跑不动 | 复杂，历史修正不会自动同步 |
| 适用 | 小表、维表、需要强一致的场景 | 大事实表、日志类、每天有新数据 |

增量抽取的四种常见方式：

| 方式 | 原理 | 注意 |
|---|---|---|
| 时间戳 | 只取 `update_time > 上次水位` | 依赖上游时间字段可靠，需处理时钟偏差 |
| 自增 ID | 只取 `id > max(id)` | 只能捕获新增，捕获不到更新 |
| 分区 | 只处理 `dt = 昨天` 的分区 | 数仓最常用，要求上游按分区落地 |
| CDC | 读 binlog / WAL | 最完整，能捕获删除，成本最高 |

**迟到数据**是增量管道必须处理的问题：转化回传可能延迟几天，昨天的分区今天还会变。通用做法是设一个 **lookback 窗口**（如回刷最近 7 天），每次跑批重算 `[T-7, T]` 的所有分区，用幂等覆盖写消化修正。双轴事实表天然适合这个模式：`report_date` 推进时，历史 `install_date` 的行被重新计算并覆盖。

## 面试速查

- **数仓为什么分层？** → 固化口径、消除重复计算、隔离上游变化、缩小排错范围。
- **四层各自一句话？** → ODS 原样落地，DWD 清洗成可信明细，DWS 聚合成可复用宽表，ADS 面向应用出数。
- **为什么不直接从 ODS 出报表？** → 每个分析师重复实现清洗逻辑，同一指标会算出多个版本，口径失控。
- **ODS 为什么不清洗？** → 保留可追溯的原始值，且加工程序写错时能低成本重跑。
- **DWD 做哪五件事？** → 去重、异常值打标、标准化（币种/时区/格式）、维度退化、归因关联。
- **DWD 和 ODS 的本质区别？** → ODS 是原样副本，DWD 是下游可以直接信任的明细事实。
- **ETL 和 ELT 的区别？** → ETL 算完再存，ELT 先存再算；云数仓算力便宜后 ELT 成为主流。
- **事实表和维度表的区别？** → 事实表存可度量的业务事件（行多列少），维度表存切分口径（行少列多）。
- **星型和雪花怎么选？** → 选星型，join 少、查询快，用少量存储冗余换性能。
- **什么是维度退化？** → 把常用维度属性直接冗余进事实表，减少 join；适用于基本不变的属性。
- **双轴事实表是什么？** → 一张表里同时有 `install_date`（cohort 口径）和 `report_date`（日历口径）两个日期维度。
- **为什么广告投放必须双轴？** → 收入按安装后第 N 天延迟回传，日历口径看回款、cohort 口径看买量质量，两者不可互相替代。
- **双轴是不是两张事实表？** → 不是，是一张表里的两个日期维度。
- **为什么只存原子度量不存比率？** → 比率不可加、口径一变历史全废；原子值可任意 roll-up，派生指标随时重算。
- **CTR 为什么不能用 AVG？** → 各渠道曝光量差异大，简单平均会被小样本极端值放大，必须 `SUM(clicks)/SUM(impressions)`。
- **7 天基线为什么用 `1 PRECEDING`？** → 基线不能含当天，否则异常值会抬高基线、自己稀释自己。
- **SCD 三种类型？** → Type 1 覆盖、Type 2 关旧插新留全历史、Type 3 只留上一版。
- **投放策略调整为什么用 Type 2？** → 要用当时的目标评价当时的投放，且 Agent 需要知道历史目标值才能判断策略调整的效果。
- **Type 2 的 `end_date` 为什么用 9999-12-31？** → 避免 NULL 参与比较导致 join 丢行。
- **操作日志表和 SCD Type 2 的区别？** → SCD 存状态历史，操作日志存动作历史（谁、改了什么、改前改后、为什么）。
- **拉链表和全量快照怎么选？** → 变化率低、数据量大选拉链；需要频繁取任意一天快照、实现要简单选全量。
- **幂等是什么？怎么实现？** → 跑一次和跑十次结果一样；先删后插、分区覆盖写、主键 upsert。
- **全量和增量怎么选？** → 小表维表用全量，大事实表用增量；增量必须配 lookback 窗口处理迟到数据。
