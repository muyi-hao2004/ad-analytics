# 数据契约与字段字典

这份文件解决的问题：**同一个字段，两个人理解不一样。**

具体到我这个项目，已经真实发生过三次口径打架：

| 冲突 | 我一开始的理解 | 实测结果 |
|---|---|---|
| `time_since_last_click` 有 53% 负数 | 上游数据脏了 | `-1` 是「没有上一次点击」的哨兵值，不是脏数据 |
| 按 `click_nb >= 1` 当清洗规则 | 它是「累计点击次数」，有点击就该有值 | 它只在**有转化**时才有值，规则一次拦掉 33.65% 的数据 |
| `cat1~cat9` 当 campaign 属性建维表 | 广告计划的类目属性 | 675 个 campaign 全部有多种组合，它们是**事件级**上下文特征 |

三次都是「按列名猜语义」猜错的。所以契约的第一条纪律是：
**字段的含义必须由数据验证，不能由列名推断。**

## 二、`dwd.dwd_ad_event` 字段字典

图例：✅ 可直接用于指标 ｜ ⚠️ 有限制 ｜ ❌ 禁止用于指标

| 字段 | 类型 | 含义 | 可用性 | 说明 |
|---|---|---|---|---|
| `event_ts` | BIGINT | 事件时间（相对秒，从 2026-09-21 00:00:00 起算） | ✅ | 原始值，无损 |
| `event_time` | TIMESTAMP | 同上，可读形式 | ✅ | 由 `event_ts` 换算，已校验 `dt` 一致 |
| `event_hour` | INT | 小时 0–23 | ✅ | 用于分时段分析 |
| `uid` | BIGINT | 用户 ID（脱敏） | ✅ | 6,142,256 个（HLL 近似校验 6,178,418，误差内一致）；平均每 uid 2.7 行 |
| `campaign_id` | BIGINT | 广告计划 ID | ✅ | 675 个，关联 `dim_campaign` |
| `cat1`–`cat9` | BIGINT | 曝光的上下文特征（设备/广告位等，已匿名） | ⚠️ | **不是** campaign 属性；同一 campaign 最多 126,914 种组合。语义未知，只能当特征用 |
| `is_click` | INT | 是否点击（0/1） | ✅ | 36.12% |

| `prev_click_gap_sec` | DOUBLE | 距上次点击的秒数 | ✅ | 原 `time_since_last_click`，`-1` 已转 NULL（占 53.26%） |
| `is_first_click` | INT | 是否首次点击（0/1） | ✅ | `click=1 且 无上次点击`，2,640,891 行 |
| `conversion_ts` | BIGINT | 转化时间（相对秒） | ✅ | 仅转化行有值 |
| `conversion_id` | BIGINT | 转化 ID | ⚠️ | 语义未确认是「转化单号」还是「转化类型」，只做去重键用 |
| `conv_delay_sec` | BIGINT | 转化延迟（秒）= 转化时刻 − 曝光时刻 | ⚠️ | 中位数 3.74 天，最大 **恰好 30.00 天**（= 归因窗口上限），分布见下方专条 |
| `conv_click_nb` | INT | 转化前的累计点击数 | ⚠️ | 原 `click_nb`，仅转化行有值（1–174），其余 `-1` 已转 NULL |
| `conv_click_pos` | INT | 本次点击在转化路径中的位置 | ⚠️ | 原 `click_pos`，仅转化行有值（0–173），其余 `-1` 已转 NULL |
| `cost` | DOUBLE | 本次事件记的花费 | ✅ | 合计 4,829.34（归一化过，不是真实货币）；均值 0.000293，中位数 0.000076，最大 0.06 |
| `cost_per_click` | DOUBLE | **点击事件自身记的花费** | ⚠️ | 仅点击行有值。**它不是 CPC 指标**，见下方专条 |
| `cpo` | DOUBLE | **语义不明** | ❌ | 见下方专条 |

### 转化延迟的真实分布（`conv_delay_sec`）

806,196 条转化行实测（`scripts/probe_dwd_dist.py`）：

| 分位 | 秒 | 换算 |
|---|---|---|
| 10% | 160 | 2.7 分钟 |
| 25% | 7,273 | 2.0 小时 |
| 中位数 | 323,407 | **3.74 天** |
| 75% | 1,034,161 | 12.0 天 |
| 90% | 1,812,390 | 21.0 天 |
| 99% | 2,503,324 | 29.0 天 |
| 最大 | 2,591,997 | **30.00 天** |

按天分桶的形状是**单调衰减**：第 0 天 34.36%，第 1 天 7.09%，第 5 天 3.60%，
第 15 天 1.69%，第 29 天 0.95%。

三个必须能讲出来的判断：

1. **形状是真的。** 如果数据是随机生成的，每个天桶会差不多高。实测是干净的长尾衰减，
   说明这份数据保留了真实的转化行为特征，不是噪声。
2. **30.00 天是硬边界，不是巧合。** 最大延迟恰好 2,591,997 秒（差 3 秒满 30 天），
   99 分位 29.0 天，第 30 天桶直接消失。这说明上游按 **30 天归因窗口**截断——
   超过 30 天的转化被算给了别人，或者干脆没记在这条曝光上。
3. **所以「平均延迟 7.1 天」这个数不能直接用。** 平均值被长尾拉高，中位数只有 3.74 天。
   任何对外口径都应该报中位数，或者报「7 天内转化占比」这种可解释的分段指标。

> ⚠️ **这条推翻了我自己之前写进本文档的一个错误结论。**
> 原文档写「转化延迟实测最大仅 173 秒，说明归因窗口极短」——**这是错的**。
> 173 是 `click_pos` 的最大值（本次点击在转化路径中的位置，0..173），
> 被我（或当时那个探针）张冠李戴当成了延迟。
> 教训和本文档开头那三条一样：**数字必须和产生它的 SQL 一起核对**，
> 一个孤零零的极值看起来最像结论，也最容易错。

### `cost_per_click` 和 CPC 不是一回事（一个容易说错的地方）

| 算法 | 值 | 是什么 |
|---|---|---|
| `avg(cost) WHERE is_click=1`（即本列） | **0.000509** | 点击这一行**自己**记了多少花费 |
| `sum(cost) / sum(is_click)`（真正的 CPC） | **0.000812** | 总花费 ÷ 总点击数 |

两者差 60%，原因很简单：**花费不只记在点击行上，曝光行也记了钱**
（全表 16.47M 行 `cost` 全部 > 0，非点击行合计仍占 1,802.34，即总花费的 37%）。

所以标准 CPC 口径是 `sum(cost)/sum(is_click)`。列名 `cost_per_click` 起得不好，
容易让人以为它就是 CPC。**契约条款：报表里的 CPC 必须用公式算，不许对 `cost_per_click` 取平均。**
（这个名字属于已知的命名债，改列名要重建表，暂时保留 + 用契约约束。）

### `cpo` 为什么被禁用

四个实测证据（`scripts/probe_cost_scale.py`）：

1. **不是 campaign 级常量**：675 个 campaign 共 637,863 个不同取值，平均每个 campaign 945 个。
2. **与 cost 不成固定比例**：全局 `avg(cpo)/avg(cost)` = **669.8 倍**；
   按 campaign 分别算，比值在 **14.8 ~ 5,260.6** 之间，标准差 685。
   如果只是单位换算（比如"分"和"元"），比值应该处处相同。
3. **不等于 campaign 级的 CPA**：实际 CPA（`cost/转化`）平均 0.013084，
   而 `cpo` 平均 0.197161 —— **差 15 倍**，不是同一个口径。
4. 量级本身也奇怪：`sum(cpo)` = 3,234,792，是 `sum(cost)` 的 670 倍。

契约条款：**`cpo` 原样保留以备追溯，但任何指标、报表、模型特征都不得引用。**
要用它，先去问上游要字段定义。

> 这条就是「数据契约」的现实价值：报表要一个指标，源字段给不了，
> 矛盾必须在上线前用契约拦住，而不是等报表算出来被业务方质疑。

> ⚠️ **本节数字修正过一次。** 旧版写的是「cpo 均值 0.110283、差 110 倍、
> campaign 比值 19~55 倍」—— 重算后三个数全部对不上（实测 0.196429 / 669.8 倍 / 14.8~5,260.6）。
> 结论方向没变（仍是"语义不明、禁用"），但**数字必须重算，不能沿用旧结论里的数字**。

## 三、指标口径（唯一定义处）

代码里**不许手写公式**，一律引用这里。

| 指标 | 公式 | 备注 |
|---|---|---|
| CTR | `sum(is_click) / count(*)` | 36.12% |
| CVR | `sum(is_conversion) / sum(is_click)` | 4.90% |
| CPA | `sum(cost) / sum(is_conversion)` | 0.0060 |
| CPC | `sum(cost) / sum(is_click)` | 0.0008 |
| 归因转化率 | `sum(is_attributed) / sum(is_conversion)` | 54.87% |
| **ROI** | **不可计算** | **源数据没有收入字段**，硬编一个收入列面试一问就露 |

> 上面这些数都在 `scripts/probe_cost_scale.py` 的单次扫描里重算过
> （CPA 0.005991、CPC 0.000812），和表里写的一致。
> **改任何一条公式后必须重跑那个脚本** —— 分母口径一变数就变，
> 而报表只会显示"数字变了"，不会告诉你"公式变了"。

### 两条必须主动声明的口径边界

1. **CTR 36.12% 不代表真实点击率。**
   这份数据集只包含「可归因的点击子集」（有转化的曝光才被收录），
   所以分母不是完整曝光量。任何对外表述都要带这个限定。

2. **ROI 算不出来。** 没有收入/成交金额字段。
   如果报表需要 ROI，正确做法是走数据契约向源头提需求，不是自己编一个。

## 三点五、倾斜：这份数据**不倾斜**（实测，重要）

调优练习最大的陷阱是"以为自己在调优，其实数据本来就均匀"。
两个维度都量过了：

| 维度 | 分布 | 结论 |
|---|---|---|
| `campaign_id` | 675 个，最大占 **2.66%** | 不倾斜 |
| `uid` | 6.14M 个，平均 2.7 行，**最活跃的只 880 行（0.005%）** | 不倾斜 |

**所以做 DWS 聚合时不会遇到任何倾斜问题。** 要想练倾斜处理（`salting`、`repartition by range`、
`AQE skew join`），必须**自己制造**：拿 `cat3`（1,584 个取值）人为把 40~50% 的行映射到同一个键上。

> 我一开始在探针脚本里写的是「按 uid 分组一定会倾斜」，实测**反了**。
> 这类"凭经验下的判断"必须被数字推翻一次，才算真的学过。

## 四、`dwd.dim_campaign` 的时间边界（point-in-time 问题）

`dim_campaign` 的统计量（`impressions`、`ctr`、`cpa` 等）是**全量 31 天的期末快照**。

- ✅ 用于 BI 报表：没问题，报表本来就是月底跑。
- ❌ 用于训练模型：会泄露未来信息。`dt=2026-09-21` 的行会带上 10-21 才发生的统计量。

要做训练集，必须按天滚出版本（只用当天及之前的数据算），
这个要求叫 **point-in-time correctness**。当前版本**没有实现**，属于已知缺口。

## 五、契约条款（对上游的要求）

| 条款 | 触发后果 |
|---|---|
| 字段改名 / 类型变更 / 单位变更（如秒改毫秒）必须提前一个周期通知 | 未通知导致任务失败，责任在上游 |
| `-1` 之类的哨兵值必须书面登记 | 否则会像这次一样被误判为脏数据，一次拦掉 33% 的数据 |
| 新增字段可以随意加，删除或改语义必须走变更 | 下游按列名读取，删列会静默变成 NULL |
| 数据延迟超过 2 小时要打标 | 否则「今日数据变少」会被误判成业务下滑 |
