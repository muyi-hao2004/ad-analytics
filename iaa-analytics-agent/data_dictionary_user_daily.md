# 数据字典：用户级明细事实表 `dwd_user_daily`

> 本表是 IAA 中台「数据身体」的核心。原项目的 `demo_dirty.csv` 只有 6 行日汇总，
> 无法计算真实的 cohort 留存与 ROI 曲线；本表把粒度下沉到「用户 × 天」，
> 让 `metrics.yaml` 里 12 个指标全部有真实数据支撑。

---

## 1. 基本信息

| 项 | 值 |
|---|---|
| Hive 表名 | `lab.dwd_user_daily` |
| 中文名 | 用户日活明细事实表 |
| **粒度** | **一个用户在某一天的活跃记录（一行）** |
| 唯一键 | `(uid, dt)` |

## 2. 字段定义

### 2.1 维度字段（6 个）

| 字段 | 类型 | 基数 | 说明 |
|---|---|---|---|
| `uid` | STRING | 1,240 万 | 用户唯一 ID，格式 `u{install_date}_{seq}`，如 `u20261001_000381` |
| `app` | STRING | 1 | 游戏包，当前仅 `money_clicker` |
| `country` | STRING | 4 | 国家：US / JP / CA / GB |
| `campaign` | STRING | 5 | 投放系列，与 `dim.db` 的 `dim_campaign` 对齐 |
| `sub_channel` | STRING | 4 | 归因子渠道 `ch_001` ~ `ch_004`，与 `dim_sub_channel` 对齐 |
| `creative_id` | STRING | ~200 | 素材 ID，格式 `crt_{campaign}_{n}`；自然流量为 NULL |
| `device_os` | STRING | 2 | `iOS` / `Android` |

### 2.2 时间字段（1 个）

| 字段 | 类型 | 说明 |
|---|---|---|
| `days_since_install` | INT | 当前行日期距装机日的天数，0 = 装机当天（D0）。cohort 序号 |

> `install_date` 不单独存：`install_date = dt - days_since_install`，信息等价，
> 但存 INT 比存 DATE 省 3 字节，且 cohort 分析直接 `GROUP BY days_since_install`。

### 2.3 度量字段（5 个，全部为原子值）

| 字段 | 类型 | 说明 | 何时为 NULL |
|---|---|---|---|
| `session_cnt` | INT | 当天打开 App 的次数 | 永不为 NULL（最少 1） |
| `ad_impr` | BIGINT | 当天广告展示总次数（全广告位合计） | 永不为 NULL（可为 0） |
| `rewarded_views` | INT | 当天激励视频观看次数 | 永不为 NULL（可为 0） |
| `ad_revenue` | DECIMAL(12,6) | 当天广告收入（美元） | 永不为 NULL（可为 0） |
| `install_cost` | DECIMAL(12,6) | 该用户的获客成本（美元） | **仅 D0 有值，D>0 为 NULL** |

**不存任何派生指标**：`ctr` / `roi` / `ecpm` / `arpu` / `retention` 一律不落库，
查询时按 `metrics.yaml` 的公式现算（见该文件第 148 行规则）。

## 3. 五个关键设计决策

### 决策 1：为什么粒度必须带「天」，不能只到「用户」

因为**留存这个指标本身要求有「天」这一维**。

- 纯用户表（一行一个用户）：只能算「这个人来过没有」，算不了「第 7 天还剩几个」
- 用户 × 天表：`COUNT(DISTINCT uid) WHERE days_since_install = 7` 直接得出 D7 留存人数

这是「指标倒推粒度」：**先看要算什么，再定一行代表什么。**

反过来也一样成立——如果业务只关心「总花费」，一行一个渠道就够了，
根本不需要用户级。粒度不是越细越好，是**刚好够算你要的指标**。

### 决策 2：为什么不做到「事件级」（每次广告展示一行）

事件级行数估算：5,000 万活跃日 × 平均 7 次展示 = **3.5 亿行**。

放弃理由：
1. 本机 `local[2]` + 2 GB driver 跑不动，属于为演而演
2. 展示级别的分析价值有限——真正的问题是「这个素材的用户一周赚回多少钱」，
   聚合到「天」就足够回答，再细只是噪音

这是一个真实的工程权衡：**粒度细到够用就停，不是越细越好。**

### 决策 3：为什么 `install_cost` 只在 D0 有值，其余为 NULL

买量花费是「投放当天花一笔钱，买来 N 个人」——**成本只发生一次**，在装机那一刻。

三种处理方式对比：

| 做法 | 问题 |
|---|---|
| 每天重复填同一个值 | D>0 的行全是冗余，5,000 万行里 4,000 万行是重复数据 |
| 每天填 0 | 严重错误：`SUM(install_cost)` 变成 0，ROI 分母消失 |
| **D0 有值，D>0 为 NULL** | ✅ 正确：语义是「不适用」，不是「未知」也不是「0」 |

查询时取成本必须用 `SUM(install_cost)`（自动跳过 NULL），不能用 `AVG`。

### 决策 4：为什么冗余 6 个维度到事实表里（反正规化）

严格按星型模型，`country` / `campaign` / `creative_id` 应该放在 `dim_user` 维表里，
事实表只存 `uid`。但这里选择冗余进事实表。

理由：
- 这 6 个维度是**用户装机时就固定、一辈子不变**的（不会出现「上个月是美国人，这个月变日本人」）
- 基数都很小（1 ~ 200），存储代价可忽略
- 省掉一次 1,240 万行的维表 join —— 在 `local[2]` 上这个 join 要 broadcast 约 600 MB，容易 OOM

**这是一次明确的权衡：牺牲一点规范性，换查询简单和本机可跑通。**
真实场景里，如果维表会变（比如用户等级、付费状态），就必须留维表做 SCD2，不能冗余。

### 决策 5：为什么分区键用 `dt` 而不是 `install_date`

| 分区依据 | 效果 |
|---|---|
| 按 `install_date` 分区 | 一个分区 = 某天装机的人的全部生命周期数据。**问题：新数据要往老分区追加**（10-01 装的人，10-20 还在产生数据），分区不可独立重算 |
| **按 `dt` 分区** | 一个分区 = 某天发生的所有活跃。**每天的数据独立完整，可单独重跑** |

这是「能否只重跑某一天」的直接体现：按 `dt` 分区，补 10-15 号就只覆盖
`dt=2026-10-15` 这一个目录，其余 30 天纹丝不动。

## 4. 空值语义（三种含义必须区分）

| 字段 | NULL 的含义 | 正确用法 |
|---|---|---|
| `install_cost`（D>0 行） | **不适用**：成本只在装机日产生 | `SUM()` 自动跳过；不要 `COALESCE(..., 0)` 后求平均 |
| `creative_id`（自然流量） | **不适用**：没有素材来源 | 分析素材时 `WHERE creative_id IS NOT NULL` |
| `ad_revenue = 0` | **真实观测到的 0**：用户活跃了但没看广告 | 不是 NULL！用 0 参与平均才对 |

**红线**：把「未知」填成 0 会拉低平均值；把「不适用」填成 0 会造出假指标。

## 5. 数据生成规则（`gen_iaa_users.py` 依据）

### 5.1 规模

| 参数 | 值 |
|---|---|
| 日期范围 | 2026-10-01 ~ 2026-10-31（31 天） |
| 每天新增用户 | 400,000 |
| 总用户数 | 12,400,000 |
| 留存曲线 | 幂律 `R(d) = 0.35 × d^-0.55` |
| 理论平均活跃天数 | 3.99 天（`Σ R(d)`，无限窗口） |
| **实际平均活跃天数** | **2.88 天** |
| 实测行数 | **3,568 万**（ODS 3,596.9 万） |

**为什么实际 3,568 万而不是理论的 4,948 万 —— 这是一个必须讲清的口径问题：**

理论值 `1240 万 × 3.99 天 = 4,948 万` 假设每个用户都能被观察满 30 天。
但 10 月只有 31 天，**10-31 装机的用户只能观察到 D0，10-25 装机的只能观察到 D6**。
31 个 cohort 里，只有 10-01 那批能看到完整的 D30。

于是「寿命」被窗口截断：`L_实际 = min(L_理论, 31 - 装机日序)`。
被截断后平均只剩 2.88 天。

这不是 bug，而是**所有真实 cohort 分析都会遇到的现象**：
> 任何按装机日分组的报表，越靠近今天的数据看起来越差 —— 不是业务变差，是观察窗口变短。

所以算 D7 ROAS / 平均留存时，必须显式排除不完整的 cohort（`WHERE install_date <= 结束日 - 7`），
否则「平均 D7 留存」会被大量「还没来得及过完 7 天」的用户稀释掉。

### 5.2 campaign 流量分布（含倾斜，美国 T0 占大头）

| campaign | country | channel | 策略 | 流量占比 | CPI | eCPM | 预期 D7 ROAS | **实测 D7 ROAS** |
|---|---|---|---|---|---|---|---|---|
| `US_A_01` | US | unity | D7_ROAS | 40% | $0.32 | $11.5 | 0.78 | **0.752** |
| `US_B_01` | US | unity | CPI | 18% | $0.38 | $10.0 | 0.55 | **0.529** |
| `JP_A_01` | JP | mtg | D0_ROAS | 15% | $0.42 | $14.1 | 0.65 | **0.626** |
| `CA_A_01` | CA | admob | D7_ROAS | 12% | $0.26 | $11.6 | 0.85 | **0.819** |
| `GB_A_01` | GB | mtg | CPI | 15% | $0.34 | $9.2 | 0.48 | **0.464** |

> 美国合计 58%，这是**刻意的倾斜**：为了让 join 倾斜、热点分区这些真实问题
> 自然浮现，而不是靠人为造。
>
> 实测值普遍比设计值低 3~4%，原因是留存从打点表改成了幂律拟合（累计活跃天数 4.18 → 3.99），
> 收入随之下调。这是**已知且已解释的系统性偏差**，不是随机误差。
>
> D7 ROAS 目标线是 0.70（`config.D7_ROAS_TARGET`）：
> **达标 2 个**（CA 0.819、US_A 0.752），**不达标 3 个**（JP 0.626、US_B 0.529、GB 0.464）。
> 这个分布是刻意设计的 —— 如果全部达标或全部不达标，Agent 就没有判断可做。

### 5.3 留存曲线（幂律，不是打点表）

```
R(d) = 0.35 × d^(-0.55)     （d >= 1，D0 固定 100%）
```

三个锚点拟合得出：D1 = 35%、D7 = 12%、D30 = 5.4%，符合网赚类 IAA 休闲游戏的行业基准。

| 天 | D1 | D3 | D7 | D14 | D30 |
|---|---|---|---|---|---|
| 设计 | 35.0% | 19.2% | 12.0% | 8.1% | 5.3% |
| **实测** | **34.04%** | **18.66%** | **11.72%** | **7.96%** | **5.23%** |

**为什么用幂律公式而不是打点表：**
打点表只能正向判断「第 d 天活不活跃」，要对每个用户展开满 31 天才知道结果 ——
中间结果 `1240 万 × 31 = 3.84 亿行`，跑半小时以上，其中 87% 的行刚生成就被丢掉。
幂律可以**反解**：给定随机数 `u`，直接算出这个用户能活到第几天
（`L = floor((A/u)^(1/|B|))`），只展开到寿命那天，中间结果降到 5,000 万行，快 70 倍。

**这个模型的已知简化：** 假设「流失后不再回来」，活跃天是 D0..L 连续的一段，
没有「D2 断了 D3 又回来」。对卸载率高的 IAA 休闲游戏，这个简化是可接受的。

### 5.4 日行为分布（仅活跃日）

| 指标 | 分布 |
|---|---|
| 日展示次数 `ad_impr` | 泊松分布，均值 7；美国 +15% |
| 激励视频占比 | 展示的 25%，四舍五入 |
| 打开次数 `session_cnt` | 泊松分布，均值 2.5，最少 1 |
| 单次展示收入 | `eCPM / 1000`，加 ±10% 随机波动 |
| 收入 | `ad_impr × 单次展示收入` |

### 5.5 故意植入的脏数据（供 DWD 清洗规则测试）

沿用原项目 `demo_dirty.csv` 的思路，在 ODS 层植入脏数据，
用于验证 DWD 的过滤规则**精确命中、零误伤**。

| 规则 | 类型 | 占比 | 日实际条数 | 期望处理 |
|---|---|---|---|---|
| R1 | `uid` 为空 | 0.1% | ~1,190 | 拦截（无主键无法归因） |
| R2 | `days_since_install` 为负 | 0.1% | ~1,204 | 拦截（活跃日早于装机日 = 时钟错乱） |
| R3 | `ad_revenue` 为负 | 0.1% | ~1,187 | 拦截（负数收入 = 上游扣款错误） |
| R4 | 展示为负 / 零次打开 | — | **0（生成器不产出）** | 拦截 |
| R5 | 观次超过总展示 | — | **0（生成器不产出）** | 拦截 |
| — | 完全重复行 | 0.5% | ~5,867 | 按 `(uid, dt)` 去重 |

> **R4 / R5 在生产数据里命中 0，不能拿来说明「规则没问题」——**
> 「0 命中」有两种相反的解释：数据里真的没有，或者规则写错了永远为 false。
> 从输出上区分不出来。
>
> 唯一能区分的办法是**故障注入**：主动塞一条必然违规的数据，看它会不会被拦。
> 见 `scripts/test_dwd_rules_iaa.py`，注入 12 行（3 干净 + 7 脏 + 1 重复），
> 断言四条：干净样本零误伤、7 类脏数据零漏网、去重精确、行数精确。
> 实测结果：12 行进 → 4 行出，四项全过。

## 6. 验收断言与实测结果

DWD 建完后逐条跑过，**全部通过**：

| 断言 | 内容 | 实测 |
|---|---|---|
| A1 | 主键 `(uid, dt)` 唯一 | 重复组数 **0** ✅ |
| A2 | `dt` 与 `days_since_install` 自洽（`install_date` 不得晚于 `dt`） | **0 行**违规 ✅ |
| A3 | 每个 uid 的 D0 行存在且唯一 | **0 个**用户违规 ✅ |
| A4 | `install_cost` 只在 D0 有值 | **0 行**违规 ✅ |
| A5 | 脏数据全部清零 | **0 行**残留 ✅ |
| A6 | 留存曲线吻合设计 | D1 34.04% / D7 11.72% / D30 5.23% ✅ |
| A7 | 输入输出对账 | 3,596.9 万 − 28.6 万 = **3,568.3 万** ✅ |

对应 SQL：

```sql
-- A1 主键唯一：应为 0 行
SELECT uid, dt, COUNT(*) AS c FROM lab.dwd_user_daily
GROUP BY uid, dt HAVING c > 1 LIMIT 10;

-- A2 dt 与 days_since_install 自洽：install_date 不得晚于 dt
SELECT COUNT(*) FROM lab.dwd_user_daily
WHERE date_sub(dt, days_since_install) > dt;

-- A3 每个 uid 的 D0 行必须存在且唯一（装机日必须留痕）
SELECT COUNT(*) FROM (
  SELECT uid FROM lab.dwd_user_daily WHERE days_since_install = 0
  GROUP BY uid HAVING COUNT(*) <> 1
) t;

-- A4 install_cost 只在 D0 有值
SELECT COUNT(*) FROM lab.dwd_user_daily
WHERE days_since_install > 0 AND install_cost IS NOT NULL;

-- A5 分区行数
SHOW PARTITIONS lab.dwd_user_daily;

-- A6 留存曲线（分母限定 10-01 装机、窗口完整的那批人）
SELECT
  COUNT(DISTINCT CASE WHEN days_since_install = 1 THEN uid END) /
  COUNT(DISTINCT CASE WHEN days_since_install = 0 THEN uid END) AS d1_ret
FROM lab.dwd_user_daily
WHERE date_sub(dt, days_since_install) <= DATE '2026-10-01';
```

## 7. 已知的口径陷阱

1. **`install_cost` 不能 `AVG`**：D>0 全是 NULL，`AVG` 只看 D0 行，结果碰巧对；
   但一旦有人 `COALESCE(install_cost, 0)` 就会算出接近 0 的假 CPI。**必须 `SUM`。**

2. **D7 ROAS 的分母是「D0 装机那批人的总成本」，不是「D7 当天活跃的人的成本」**
   —— cohort 口径，两边必须都限定在同一批用户上。

3. **留存率的分子分母不能跨 cohort**：
   `D7 留存 = (10-01 装机的人中，10-08 还活跃的) / (10-01 装机的总人数)`，
   不是「10-08 的活跃人数 / 10-01 的装机人数」。

4. **尾部 cohort 不完整**：10-25 之后装机的用户拿不到 D7，
   算平均 D7 ROAS 时要么 `WHERE install_date <= 2026-10-24`，要么按 cohort 分别报。
   **这个必须写进报表口径，否则越新的数据看起来越差。**

## 9. 五个必须解释清楚的设计决定

### ① cohort 表按 `dt`（变现日）分区，不按 `install_date`

按 `install_date` 分区看着更「cohort 友好」，但它是**只读一次的假分区**：
10-01 装的那批用户，D0 到 D30 的数据会陆续产生在 10-02 到 10-31。
也就是说「`install_date=2026-10-01`」这个分区每天都要往里追加新行 ——
分区不再是「算完就不动」的单元，而是个持续变脏的容器。

按 `dt` 分区则完全对齐：
```
DWD dt=2026-10-15  ──→  DWS dt=2026-10-15
```
一个分区进、一个分区出，重跑 10-15 只读 DWD 的 10-15。
**每层的分区边界要能一一对上**，否则「单天重跑」在第 2 层就断了。

### ② `installs` / `spend` 只在 `day_offset = 0` 上有值

这是本表最大的坑。同一批用户的 `installs` 会出现在 31 行上（D0~D30 各一行）。
如果每行都填 1000，`SUM(installs)` 会得到 31000 —— **放大 31 倍，且不报错**。

处理方式：只在 D0 填真值，其余填 0。这样 `SUM(installs)` 天然正确，
不需要调用方记住任何附加条件。这叫「**可加性设计**」：
让每个度量在任何维度上卷都得到正确答案，而不是要求下游「只能按某种特定方式查」。

### ③ 三张全量表不分区

341 行 / 6,231 行 / 31 行，都是几十 KB 级别。
分区表的最小粒度是「一个目录 + 一个文件」，每个文件还有几百字节 footer，
31 个分区就是 31 个文件管 341 行，典型的**小文件问题**——读的时候要开 31 个句柄，比不分区还慢。

不分区意味着「重跑某天要全量重算」，但整表只有几百行，全量也就几秒。
这是**用规模换简单**的正当权衡。判断标准始终是：单分区是否落在 128 MB ~ 1 GB。

### ④ 买量侧必须是独立一张表

IAA 是双轨业务，两条轨的**粒度不同**：

| | 粒度 | 时间轴 | 表 |
|---|---|---|---|
| 买量侧 | 渠道 × 天 | 单轴（投放日） | `ods_iaa_acquisition_daily` |
| 变现侧 | 用户 × 天 | 双轴（装机日 + 变现日） | `dwd_user_daily` |

从用户明细**算不出**买量数据：「我买了 10 万次曝光，进来 500 个安装」——
你不知道这 10 万次曝光对应的是这 500 个安装，还是同样 500 个安装背后其实花了 30 万次曝光。
归因是单向的（曝光 → 点击 → 安装），逆向不可推导。

所以 `buy_ctr` / `buy_cvr` / `buy_ecpm` 三个指标**只能**从买量表算。
这张表是从 DWD **反算**的（`installs`/`spend` 直接取 DWD 的 D0 口径，
`clicks`/`buy_impressions` 按稳定转化率反推），保证两轨 100% 对得上。

### ⑤ `dws_creative_daily` 算不出 D7 ROI

因为它的粒度是「素材 × 投放日」，没有 `day_offset`，任何 Dn 类指标都算不了。
要按素材看 D7 ROI，必须回到 `dws_cohort_daily`（那里有 `creative_id` 维度）。

**同一维度在不同表里有不同口径**，这是分层的正常代价，不是设计缺陷。
记住一条：**要 cohort 指标就回 cohort 表**。

## 12. 素材质量因子（已修）

**问题（第一版）**：200 个素材的 D7 ROI 集中在 0.46~0.83，同一 campaign 内几乎无差别
（GB 的 5 个最差素材：0.4614 / 0.4618 / 0.4627 / 0.4630 / 0.4630，CV 只有 0.5%）。

根因：造数时 `creative_id` 用 `hash(uid) % 40` 分配，**与留存、eCPM 完全无关**，
素材之间只有随机噪声。后果是「这个素材该不该砍」这个场景是空的。

**修法**：在 `gen_iaa_users.py` 里给每个 `creative_id` 一个质量因子
`_q = abs(hash(creative_id)) % 1000 / 1000`，分三段映射：

| 分位 | 区间 | 质量因子 | 含义 |
|---|---|---|---|
| 20% | `_q < 0.20` | 0.62 ~ 0.75 | 差素材（早就疲劳的） |
| 60% | `0.20 ~ 0.80` | 0.92 ~ 1.05 | 一般 |
| 20% | `_q >= 0.80` | 1.20 ~ 1.45 | 好素材（爆款） |

加权均值 **0.987**，所以整体渠道 ROI 几乎不变（不会把渠道结论打乱），
但素材之间的排序被拉开了 2 倍。

用 `hash` 而不是 `rand()` 的原因：同一个素材的所有行必须乘同一个因子，
否则「素材质量」就成了随机噪声；而且 hash 是确定性的，重跑 100 次结果一样（幂等）。

**修复后实测**：

| campaign | 最差素材 | 最好素材 | 极差 | CV |
|---|---|---|---|---|
| GB_A_01 | 0.298 | 0.606 | **2.04x** | 16.4% |
| CA_A_01 | 0.514 | 1.179 | **2.29x** | 22.6% |

全站素材 Top/Bottom（D7 ROI，成本 > $5,000）：

```
最该砍：  crt_gb_a_01_026 0.3013 / _030 0.3168 / _037 0.3191 / us_b_01_001 0.3269
最该加：  crt_ca_a_01_002 1.1910 / _021 1.1890 / _010 1.1823 / _006 1.1173
```

**这一条在面试里能讲的不是「我调了参数」，而是「我发现自己的数据没有决策信号，并且知道怎么补」。**

## 13. 一个关于「部分重跑」的血泪教训

修完质量因子后，我先用 `--days 1` 跑了造数做冒烟测试。脚本正常退出、日志显示
「31 个分区 / 522 MB」，我查 `dt='2026-10-01'` 的素材 eCPM，看到 5.93~12.02（2.03 倍），
确认「因子生效了」，然后往下游跑。

**实际上 `--days 1` 只重写了 10-01 一个分区，其余 30 天还是旧数据。**
那个「31 个分区」是统计整个表目录，不是本次写入量。

结果：DWS/ADS 里素材 ROI 仍然几乎没差别（CV 0.5%），因为 30/31 的数据没有因子。
我花了 5 轮查询才定位——D0 有差异 → 全量无差异 → 单个 uid 逐天看 → 算 `_q` 分布
→ 最后才想到「是不是只有一天被重写了」。

**规律：验证分区表时必须跨多个分区抽样。只看一个分区，会得出与事实相反的结论。**
（我当时查的正好是唯一被更新的那天。）

全量重跑（不用 `--days`）之后一切正常。

## 14. ADS 层与中台接入

### 14.1 为什么不用 OLAP

标准架构是 `Hive 算 → 同步 → OLAP 查`（ClickHouse / Doris），但本项目不该上：

1. **规模差 3 个数量级**：ADS 最大 1.4 万行，Spark 查 341 行要 2 秒，
   其中 1.8 秒是查询规划开销，跟数据量无关。上 Doris 也不会更快，还得先启动它。
2. **机器跑不动**：16 GB 内存，Docker 吃 5 GB，Spark 只能 `driver 2g`。
   再塞一个 ClickHouse 容器，系统开始交换页，比现在慢。
3. **多一条一致性链路**：数据同步到 OLAP 后，「Hive 已更新、OLAP 还是旧数」
   这个窗口就是新故障源。面试被问「怎么保证两边一致」答不上来会减分。

**原项目的 ADS 层本来就是 OLAP 的轻量替代**：`daily_detail` / `creative_table` /
`sub_channel_table` 就是「算好、直接显示」的小结果集。改造只是把它换成了真数据。

### 14.2 三张 ADS 表

| 表 | 行数 | 大小 | 说明 |
|---|---|---|---|
| `ads_daily_detail` | 13,981 | 4.4 MB | cohort D0~D7 横铺（75 列） |
| `ads_creative_table` | 6,231 | 397 KB | 素材 × 装机日 |
| `ads_sub_channel_table` | 341 | 26 KB | 子渠道 × 装机日 |

同时导出到 `iaa-analytics-agent/data/warehouse/ads/*.parquet`（单文件，供中台读）。

**ADS 可以存比率，DWD/DWS 不行。** 因为 ADS 是终点，输出直接进图表和 LLM 上下文，
不会再被 `SUM` / `AVG` 上卷。前提是**永不从 ADS 表 sum(ctr)** —— 这条边界必须写死。

### 14.3 取数层 `warehouse_api.py`

| 模式 | 数据源 | 延迟 |
|---|---|---|
| `ADS_MODE=parquet`（默认） | `data/warehouse/ads/*.parquet` | **~5 ms** |
| `ADS_MODE=hive` | `lab.ads_*`（Spark 直连） | ~2 s |

默认 parquet 不是妥协，是**快 400 倍**。真实公司做在线服务也不会让 API 直连批处理集群，
标准做法就是「数仓算完 → 导出小结果 → 在线服务读小结果」。所谓「接 OLAP」，
只是把「导出 parquet」换成「同步进 ClickHouse」。

`agent.py` 里 6 处 `pd.read_parquet(config.ADS_DIR / ...)` 全部替换为
`warehouse_api.read_xxx()`，**业务逻辑 1,300 行未动**。将来数据涨到千万级、QPS 几百，
只改 `warehouse_api.py` 一个文件。

### 14.4 顺手修掉的原项目缺陷

`_tool_get_top_history` 和 `_tool_get_trend_with_ops` 读的是 `daily_detail`，
但那张表只有 `roi_0..roi_7`，**没有 `d7_roi` 列**，所以这两个工具传
`metric="d7_roi"` 时永远返回「指标不存在」。
而 `_load_top` 读的是 `creative_table`（有 `d7_roi`），所以从外面看一切正常 ——
典型的「两个工具读不同的表，却共用一套指标命名」。

已在 ADS 表补上 `d7_roi` 和 `cpi` 两列。

### 14.5 接入验收（`check_warehouse_integration.py`）

```

[PASS] _load_top('sub_channel_table.parquet', 3)       3 条
```

### 14.6 成熟度标记 `is_mature_d7`（最重要的一个数据质量措施）

接上中台后立刻发现一个**会误导决策**的问题：

```
ch_001 的 D7 ROI 趋势
  2026-10-24   spend 25,633   d7_roi 0.7325
  2026-10-31   spend 25,403   d7_roi 0.3644   ← 掉了一半
```

看起来像「渠道急剧恶化」，但真相是：10-31 装机的用户只活了 D0，
D7 收入根本还没产生，而分母（成本）是全额的，所以 d7_roi 天然偏低。

**任何按装机日分组的 D7 类指标，越靠近今天看起来越差 —— 这不是业务问题，是观察窗口问题。**

处理方法：ADS 表加 `is_mature_d7` 列

```sql
date_add(install_date, 7) <= to_date('2026-10-31') AS is_mature_d7
```

`warehouse_api.read_daily_detail(mature_only=True)` 会过滤掉不完整的 cohort。
实测：13,981 行中 10,824 行成熟，剔除 3,157 行（10-25 ~ 10-31 共 7 天）。

**过滤后的趋势（与之前对比）**：

| 日期 | 过滤前 | 过滤后 |
|---|---|---|
| 10-24 | 0.7325 | 0.7325 |
| 10-31 | **0.3644** | —（已剔除）|
| 10-17~10-24 全程 | — | **0.726 ~ 0.735（平稳）** |

工具分工（这个分工是有意的）：

| 工具 | 不完整 cohort | 用途 |
|---|---|---|
| `_tool_get_metric` | **保留**，但每行标 `is_mature` + 顶层 `mature_hint` | 看最新的逐日明细（删掉最近 7 天等于没回答） |
| `_tool_get_trend_with_ops` | **剔除** | 判断趋势与因果（用不完整数据判因果必错） |
| `_load_top`（快照排行） | **剔除** | 排行要做决策，必须用完整口径 |

这里的设计区别值得讲清楚：**「过滤」和「标记」解决的是两个不同问题。**

`get_trend_with_ops` 要回答「这个渠道是在变好还是变差」，混进窗口未走完的
数据必然得出「急剧恶化」的错误结论 —— 所以直接剔除，不给它犯错的机会。

`get_metric` 要回答「最近几天发生了什么」，如果把最近 7 天删掉，等于拒答。
更好的做法是**保留真实数字 + 明确标注这段不可信**，让它自己判断。
一刀切过滤不是谨慎，是回避。

**这条是整个改造里最有价值的一个细节**：数仓不只是把数字算出来，
还要保证数字在什么条件下才有意义。面试时被问「你遇到过什么数据陷阱」，
这个案例比任何理论都更有说服力。

## 15. 给 LLM 的数据快照（2026-10-23 重构）

快照是 `agent.py` 里 `build_snapshot()` 产出的那个 JSON，作为第一条 user message
发给模型。它决定了 LLM 对数据的第一印象 —— 所以它的口径必须和工具调用完全一致，
否则会出现「快照说 0.28，调工具查出来 0.31」这种自相矛盾。

重构前这里有两个真问题，都会直接改变决策。

### 15.1 口径打架：快照读的是没过滤的表

`_load_top` 原先读 `creative_table.parquet` / `sub_channel_table.parquet`。
这两张是 DWS 全量表，聚合了全部 31 天，**没有 `is_mature_d7` 列**，
于是最后 7 天窗口未走完的 cohort 被全额计入分母。

实测（31 天 / 200 个花费 > 5000 的素材）：

| 口径 | D7 ROI 区间 | 与成熟口径的偏差 |
|---|---|---|
| 全量（快照用的） | 0.2885 ~ 1.1401 | 平均 **-0.0529** |
| 成熟（工具用的） | 0.3131 ~ 1.2413 | — |

**100% 的素材都被低估**。这不是小数误差，因为它跨过了决策阈值：

| 判断 | 全量口径 | 成熟口径 | 差异 |
|---|---|---|---|
| 低于关停线 0.50（该砍） | 65 个 | 47 个 | **18 个素材会被误砍** |
| 高于加预算线 0.90（该加） | 13 个 | 17 个 | **4 个被漏掉** |

改用 `read_daily_detail(mature_only=True)` 后，快照与工具口径统一。
顺带把明细层补全成自包含的：加了 `d7_retention` / `d7_ecpm`
（原先只有 `d7_roi` / `cpi`），现在所有工具都能统一走一张表，
不用再按指标去挑表。

### 15.2 呈现偏差：只给尾部会被读成「全线崩」

`_load_top` 只返回**最差的 20 个**素材。LLM 单独看这 20 行，
ROI 全在 0.31~0.45，很容易得出「所有素材都不达标，建议全部关停」。

新增 `素材总览`，把分布和各档位个数一起给它：

```json
{"纳入统计": 200, "样本不足未纳入": 0, "P10": 0.45, "P50": 0.62, "P90": 0.88,
 "最低": 0.31, "最高": 1.24,
 "低于关停线（0.5）的个数": 47, "高于加预算线（0.9）的个数": 17,
 "说明": "素材表现只列出最差的 20 个，不代表全部…"}
```

这样它才能区分「换 3 个素材」和「停一个 campaign」—— 量级完全不同的决策。

### 15.3 精度与 NaN

新增 `sanitize_for_llm()` / `_to_llm_content()` 统一处理：

| 问题 | 修法 |
|---|---|
| `0.28853533219904687` 这种 17 位浮点尾巴 | ROI 类 4 位、金额 2 位、计数还原整数 |
| `json.dumps(NaN)` 产出非法 JSON token | `allow_nan=False` + 递归 NaN/inf → `null` |
| numpy 标量走 `default=str` 变成 `"44993"` 字符串 | 统一转原生类型 |

反直觉的收益：精度截断后快照从 **8,639 字符降到 7,497 字符**，
但信息量反而增加了（多了数据口径、素材总览）。省下的 token 就是精度尾巴。

### 15.4 `d7_retention` 的 NULL 不能变成 0

修 15.1 时踩到一个语义坑。`_tool_get_metric` 从明细层聚合时用了
`(metric * spend).sum() / spend.sum()`，而 pandas 的 `sum()` **跳过 NaN**。
于是「一整天所有行都是 NULL」（窗口未走完）被算成 `0.0 / 总花费 = 0.0`。

LLM 看到 `d7_retention: 0.0` 会说「用户全流失了」，而真相是「还没到能看的时候」。

这和建表时特意区分的三种 NULL 语义是同一件事：

| 情况 | 正确值 | 错误值 |
|---|---|---|
| 观察窗口没走完 | `null`（不知道） | `0.0`（误导） |
| 窗口走完但 D7 无记录 | `0.0`（真流失） | — |
| 正常 | `dact7 / installs` | — |

修法：聚合时先判 `g[metric].notna().sum() == 0`，整天无有效值就保持 `null`；
加权时也只用有效行，否则 NULL 行的花费会稀释分子。

## 16. 判定层与决策日志（2026-10-23 新增）

### 16.1 为什么要加一层「判定」

原来的结构是：快照给 LLM 一堆数字 + 一堆阈值，LLM 自己判「该砍 / 该观察」。

问题不在于 LLM 判得不准，而在于**它每次都是独立推理**。同一份数据，
今天说「观察」、明天说「关停」，你没法用 prompt 要求它保持一致 ——
它没有昨天的记忆，而「一致性」恰恰是决策系统最基本的可信度要求。

所以把「判定」和「解释」拆开：

```
判定层（decision.py）  确定性纯函数，同输入必同输出，可单测
解释层（LLM）          拿到已判好的结论，负责讲原因、排优先级、出动作
```

好处是抖在被规则吃掉，而不是指望模型稳定。

### 16.2 两个机制：死区 + 连续确认

| 机制 | 解决什么 | 参数（`metrics.yaml` → `decision_thresholds.hysteresis`） |
|---|---|---|
| 死区 band | 值在阈值上下来回跳 | `band_width: 0.04`（素材 0.48~0.52 不动） |
| 连续确认 | 单日事故导致一夜改判 | `min_consecutive_days: 3` |

死区的原理跟空调恒温器一样：设 26℃ 但 25℃ 才启动、27℃ 才停，
否则在 26℃ 上下会疯狂开关。用一条「带子」代替一个「点」，抖动自然消失。

**两个方向都要加，不能只对变坏设门槛。** 否则一次侥幸反弹就会让你加预算。

### 16.3 实测证据（`check_decision_layer.py`，10 项全过）

```
A. 6 天在 0.49~0.53 抖动      结论始终 hold
   （反证）关掉死区同序列     hold/cut/hold/cut/hold/cut   ← 真的会跳
B. 单日掉到 0.28 后恢复       仍维持 strong，不改判
C. 连续 3 天 <0.50           从 watch 改判到 critical（不能稳定到盖住真问题）
D. 同输入跑 20 次             结果集合只有一个元素
```

C 这条是反向校验：**只证明「不乱改」不够，还要证明「该改的时候改得动」**，
否则死区会把真问题一起盖住，那比抖动更糟。

### 16.4 决策日志 `decision_log`

和维度表同库（SQLite `data/dim.db`），表结构：

```
decided_at     判定时间
data_as_of     当时指标截止到哪天   ← 注意不是判定时间
obj_type/id    对象
metric         指标
value          判定时的值
verdict        结论
reason         一句话理由
days_sustained 已连续多少天
snapshot_hash  当时的快照指纹
config_version 当时配置的生效日
UNIQUE(obj_type, obj_id, metric, data_as_of)
```

**`UNIQUE` 是这张表的核心。** 它让「写日志」本身变成幂等的：
agent 一天跑三次（重试 / 手动 / 定时）也只会留一行最终结论，
不需要调用方去重。实测：写 3 次 → 1 行，`log_id` 三次相同。

**必须写全量，不能只写快照里展示的那几条。** 这是个容易出错的实现细节：
素材有 160 个，快照只展示「改判的 + 最差 10 个」，但如果日志也只记这 20 条，
其余 140 个下次跑的时候「上次结论」是空的，永远判不出「改判」——
滞回机制直接失效，而且**不会报错**，只是悄悄没用。
所以：**展示可以裁剪，状态必须完整。**

### 16.5 指纹：只对指标敏感

`snapshot_hash()` 只哈希「数据口径截止日 + 素材总览 + 素材表现 + 子渠道表现」，
**不含当前配置、最近操作、上次结论**。

这个边界是刻意的：如果改一次预算就让指纹变，系统会以为「数据更新了，
可以重新判断」，于是 LLM 又改一次口 —— 跟防抖动的目标正好相反。

一个踩过的坑：指纹原本在 `sanitize_for_llm()` **之前**算，
导致「快照里存的指纹」和「拿快照重算的指纹」不相等（前者受 `np.float64`
被 `default=str` 写成字符串的影响）。而指纹的全部意义就是**可重算校验**，
算完不可复算等于没算。现在改成先清洗再算，`sanitize` 幂等，两边必然一致。

### 16.6 两个独立问题，别混

| 想干什么 | 靠什么 |
|---|---|
| 三天后知道「当时为什么这么判」 | `decision_log` 的 value / reason / data_as_of |
| 知道「这份数据我判过了，别重复判」 | `snapshot_hash` |
| 完整复原当时那 7KB 快照 | 都不行，得按 `data_as_of` 重跑 |

**决策日志是病历本，管回溯；指纹是标签，管别改口。** 两个都需要，
但指纹不含任何内容，它替代不了存快照。

### 16.7 代价

快照从 7,713 字符涨到 12,322 字符（约 7,700 token），多出来的是
「判定建议」和「上次结论」两块。这是知情成本：判定层替 LLM 做了判断，
就得把结论和依据一起给它，否则它会自己再算一遍、然后算得不一样。

## 17. 已知未修的问题

### 17.1 已修：NaN 会污染 JSON（2026-10-23）

原先 `d7_retention` 对尾部 cohort 返回 `NaN`，`json.dumps(NaN)` 输出裸 `NaN` token，
不是合法 JSON。已在 `agent.py` 加 `sanitize_for_llm()` 统一处理（见 15.3），
所有回传 LLM 的结构都递归清洗。

### 17.2 已修：空值语义（2026-10-23）

三层改动，缺一不可：

1. **落盘的 NULL 不动。** 窗口没走完就是「不知道」，写成 0 是把
   「不知道」说成「零」，会导致砍错素材。
2. **读取端换 dtype。** `warehouse_api._harden_dtypes()` 把
   `d7_roi / d7_retention / d7_ecpm / cpi` 转成 pandas 的 `Float64`（nullable）。
   `float64` 的 NaN 在 `sum()` 里被静默跳过，一整列 NULL 会变成 0.0；
   `Float64` 的 `pd.NA` 会向上传播，逼着调用方显式区分「没有值」和「值为零」。
3. **门禁用断言钉住来源。** `null_only_when`：
   `d7_retention` 的空值必须伴随 `is_mature_d7 = false`。
   这条比在出口把 NaN 洗成 null 强一个量级 —— 前者是「我猜 LLM 会误读」，
   后者是「我证明这个空值的来源合法」。

实测：`d7_retention` / `d7_ecpm` 各 3,157 行为空，全部符合成熟度规则；
`d7_roi` 0 行为空。

这条断言第一次跑就抓到了我自己写错的规则（条件里引用了 `cum_rev7`，
而那是建表 SQL 的中间别名，不是表里的列），直接 `UNRESOLVED_COLUMN`。
**门禁能抓出「规则本身写错」，这是它最有价值的时刻** —— 如果它只会报 PASS，
那它就是个装饰。

### 17.3 仍然存在的问题

**① 已修（2026-10-23）：配置与指标的时间轴没有事务约束。**

「当前配置」「最近操作」原先只来自 SQLite，指标来自 parquet，两个数据源各读一半。
现在日志（决策日志 + 操作日志）已入仓，中台统一走 `warehouse_api` 读，
两源用 `max(decided_at)` 当水位对账（详见第 18 章）。
**跨源事务仍然不存在**，但「不一致」已经能被门禁当场发现。

剩下的窄口子是 `dim_campaign`（SCD2 配置维表）仍在 SQLite，
快照里的「配置生效日」还是查 `dim.db`。它的读频率低、变更少，
暂不迁；迁的时候同样要补一条对账断言。

**② 判定的值口径是「当日 D7 ROI」。**
素材单日花费可能只有几百块，ROI 波动主要是噪声。目前靠
`min_spend: 5000`（14 天累计）+ 连续 3 天确认来压噪声。
更稳的做法是判 7 天滚动加权 ROI，但那样「连续天数」要按滚动序列重算，
两个口径混用更容易出错，暂不做。

**③ `daily_report.parquet` 是 10-15 的旧文件，已经不再更新。**
保留是因为 `build_report.py` 还在读它，但它反映的是改造前的口径。
要清理得先改报表链路。

**④ 判定只覆盖 D7 ROI 一个指标。**
`cpi` 的 `guard_band` 已经在 YAML 里定义，但还没接进判定层。
接的时候要注意：CPI 是「越低越好」，方向与 ROI 相反，阶梯不能直接复用。

**⑤ 已知未修：快照指纹与展示条数 `top_n` 耦合。**
`snapshot_hash()` 算的是整份快照（含 `素材表现` / `子渠道表现` 这两个被
`top_n` 截断的块）。所以同一个数据、不同的 `top_n`，指纹不同 ——
而「数据已变」这个字段就是拿指纹比的。
线上 `persist` 路径固定用默认 `top_n=20`，所以不影响；
但用 `top_n=5` 调试一次之后再看快照，所有对象的「数据已变」都会变成 `true`，
LLM 会以为数据真的变了，从而允许自己改判。
正解是把 `top_n` 一起写进决策日志，条数不一致时把「数据已变」标成「不可比」
而不是 `true`；这要动 `decision_log` 的表结构，暂不做，先记在这里。

# 第三部分：日志入仓（2026-10-23）

## 18. 决策日志进数仓：SQLite → ODS → DWD → ADS

### 18.1 之前的问题

判定结论写在 SQLite（`data/dim.db`），指标在 Hive / parquet。
两个数据源，除了「读起来别扭」，真正的代价是**问不出问题**：

- 判了 `cut` 的那 44 个素材，砍完之后 D7 ROI 有没有回升？
  → 日志在 SQLite、ROI 在 Hive，跨源只能在内存里手工拼
- 上周一共改判了几次？是滞回在起作用，还是规则在漂？
  → 需要 `data_as_of × verdict` 的聚合，SQLite 上没有这张汇总
- 三个月前的定论，当时指纹和配置版本是什么？
  → `dim.db` 是本地文件，换台机器就没了

### 18.2 分工：写在 SQLite，读去数仓

| 维度 | SQLite（写入端 / OLTP） | 数仓（台账 / OLAP） |
|---|---|---|
| 写入方式 | 行级 UPSERT（`UNIQUE` 约束） | 分区整块覆盖 |
| 延迟 | 毫秒，agent 一天跑多次 | 秒级，按调度跑 |
| 保存范围 | 只存当前最新结论 | 存历史上每一次改口 |
| 能做什么 | 事务边界清晰 | join / 聚合 / 进门禁 / 跨机器回溯 |

两边都不是多余的。让数仓当唯一写入端，就得在 parquet 上做 UPSERT ——
列式不可变文件做这件事只能「读全表 → 改一行 → 重写全表」，
agent 每跑一轮重写一遍，代价荒谬。
反过来只读 SQLite，就回到「两个源没法 join」。

**同步是全量镜像，不是增量。** 增量（`WHERE decided_at > 水位`）会漏掉改写：
补数时某天的行被 UPSERT（`data_as_of` 相同、`decided_at` 变新），
按 `data_as_of` 增量会整个跳过它，数仓永久停在旧结论上且不报错。
源表只有几百行，全量镜像换来「不可能漏」。

### 18.3 产出

| 表 | 行数 | 粒度 | 用途 |
|---|---|---|---|
| `lab.ods_decision_log` | 171 | obj × metric × `data_as_of`（按它分区） | 原样落地 |
| `lab.ods_operation_log` | 14 | `log_id`（按操作日分区） | 原样落地 |
| `lab.dwd_decision_event` | 171 | 同 ODS + `prev_verdict` / `changed` | 判定事件流 |
| `lab.ads_decision_latest` | 171 | obj × metric（每对象一行） | 中台读「上次结论」 |
| `lab.ads_decision_stats` | 7 | 日期 × 类型 × 结论 | 判定分布 / 复盘 |

导出到 `data/warehouse/ads/`：`decision_log.parquet` / `decision_latest.parquet` /
`decision_stats.parquet` / `operation_log.parquet`。

两个新增字段值得单独说：

- **`changed`**：`LAG(verdict)` 算「相对上一次改没改口」。
  第一行的 `verdict <> NULL` 在 Spark 里是 `NULL` 不是 `false`，
  直接拿去 `sum(CASE WHEN changed THEN 1 END)` 会被静默跳过，
  所以显式写成「没有上一次 → `false`」。
- **`verdict_streak`**：当前结论连续稳定了几天（gaps-and-islands）。
  **和 `days_sustained` 不是一回事**：后者是「裸阈值分类连续几天」（改判门槛），
  前者是「最终结论连续几天」（结论有多稳）。
  一个对象可以 `days_sustained=5` 而 `verdict_streak=1` —— 那正是滞回刚放行一次改判的样子。
  这两个数不能互相比对，`metrics.yaml` 里写了这句提醒。

### 18.4 一致性：用对账代替事务

跨 SQLite 和 Hive 不可能有分布式事务。这里承认它，然后做三件事：

1. **水位（watermark）**：两边 `max(decided_at)` 一比就知道谁更新。
   数仓新 → 用数仓；SQLite 新（agent 刚跑完）→ 用 SQLite。没有第三种情况。
2. **整块替换而非逐行 merge**：SQLite 新时从源重算一遍最新结论（171 行，1 毫秒）。
   逐行 patch 一旦有 bug，产出的是**半新半旧**的结论表 ——
   看起来完全正常，只是某几个对象的「上次」是旧的，报表上永远发现不了。
3. **门禁断言 `source_parity`**：同步完逐行比对两源（key + verdict + value）。
   不一致就 fail 掉流水线。**做不到原子，就做到可发现。**

### 18.5 幂等：两层，缺一层都不完整

| 层 | 机制 | 回答的问题 |
|---|---|---|
| 源 | `UNIQUE(obj_type, obj_id, metric, data_as_of)` | 同一天跑十次 agent，只留一条最终结论 |
| 仓 | `INSERT OVERWRITE` + dynamic partition overwrite | 同一份源同步十次，分区内容相同 |

只做第二层没用（源在变，仓只是忠实复制了变化）；
只做第一层也不够（源稳定，但同步逻辑有随机残留，重跑结果仍可能不同）。

### 18.6 门禁新增 13 条断言（`--scope log`）

| 表 | 断言 |
|---|---|
| `ods_decision_log` | `row_count_between` / `no_duplicate_grain` / `non_null` / `verdict_in_enum` / `source_parity` / `watermark_lag_days` |
| `ads_decision_latest` | `no_duplicate_grain` / `latest_covers_all` / `non_null` |
| `ads_decision_stats` | `no_duplicate_grain` / `sum_equals_table_count` |
| `ods_operation_log` | `no_duplicate_grain` / `non_null` |

其中三条是这次新增的实现：

- `source_parity`：逐行对账，只比到数仓已有的最后一天
  （源里更新的日期交给 `watermark_lag_days` 管 —— 一个查「抄错没有」，一个查「跟没跟上」）
- `watermark_lag_days`：专门抓「一致地过期」。
  同步任务整体没跑时，两边在旧范围上完全一致，`source_parity` 会过，
  但中台读到的是三天前的结论，而且它不知道自己读到的是旧的。
- `latest_covers_all`：`LEFT ANTI JOIN`。少一个对象不报错，
  只是那个对象永远走「首次判定」，滞回对它静默失效。

### 18.7 验收（`check_decision_log_sync.py`，27 条全过）

| 组 | 验的是什么 |
|---|---|
| 0~1 | 三重指纹：**源 = ODS = 导出 parquet**（顺序无关指纹，不是文件 md5） |
| 2 | 门禁 13 条正向全过 |
| 3 | **负向**：篡改一行 verdict → `source_parity` 必须变红 |
| 4 | 幂等：同一份源再同步一次，指纹不变 |
| 5 | 增量水印：模拟 agent 刚写一条，中台必须切到 `sqlite(delta)` 并读到新结论 |
| 6 | 快照：日志来源标注正确、「上次结论」覆盖所有展示对象 |

第 3 组是整份验收里最重要的：**一个从来没红过的断言，不能算断言。**

### 18.8 踩到的两个坑

**① parquet 导出「内容相同、字节不同」。**
同一份数据导两次，md5 不一致。逐字节 diff 后定位：只有 24 个字节不同，
且**全部落在数据页之后**的列统计索引区（数据页 0~5499 完全一致）。
根因是 Spark 写入列级 min/max 统计时字节序不确定。
→ 结论：判幂等只能用**顺序无关的内容指纹**，不能用文件 md5。
   （顺手给 `export_parquet()` 加了 `order_by`，行序稳定了，但统计区那 24 字节仍在。）

**② 常驻 Spark 会话的 `InMemoryFileIndex` 缓存过期。**
同步是另一个进程把分区文件整个换掉的，当前会话还以为旧文件名有效，
报 `file does not exist` 而文件明明在。
→ 外部改完 Hive 数据后必须 `spark.catalog.clearCache()` + `REFRESH TABLE`。
