# 能力边界与已知限制

> 这份文件回答一个问题：**这个项目哪些是真的，哪些是壳。**
>
> 写在最前面是因为它决定别人怎么读这个仓库。一个项目声称什么都做了，比明确说
> 「这三块是模拟的、原因是 X、替代方案是 Y」更容易崩。后者反而是工程成熟度的证据
> ——知道系统边界在哪，是设计者能力和使用者的区别。

---

## 一句话定位

这不是一个生产投放系统，是：

> **一个 Agent 系统的工程化参考实现（reference implementation）+ 一套决策评测方法论。**

业务数据是合成的，策略知识是通用知识，采集对象是本地假页面。
**但代码结构、护栏、评测框架、成本计量是真的**，且每一块都有可执行的验证。

---

## 一、三个数据资产缺口

共同点是同一个问题的三个面：**没有生产环境的数据权限**。这在个人项目里是结构性的，
不是执行不到位。

| 缺口 | 现状（实测） | 可以救吗 |
|---|---|---|
| 策略知识库（RAG） | `data/knowledge/` 两个 md，共 2.5 KB | **可以直接删，而且应该删** |
| 历史决策数据 | `operation_log` 14 条，全部由本项目测试产生 | 可转成规则库，值一半 |
| 线上真实数据（Playwright） | `mock_pages/` 两个本地 HTML | 不是缺口，做法本来就该这样 |

### 1.1 策略知识库：这是 RAG 反模式，不是"数据不够"

实测检索返回的内容：

```
query: 低ROI渠道怎么处理
命中:  "eCPM = 广告收入 / 广告展示次数 × 1000"
       "D7 ROAS 高于目标 → 可以保持甚至加预算"
       "下钻优先级：先看素材，再看子渠道，最后看国家"
```

**这些是教科书常识，模型本来就知道。**

RAG 只在三个条件**同时成立**时才有价值：

1. 模型不知道（私有事实、内部口径、最新变化）
2. 必须准确（不能靠猜，错了有代价）
3. 内容会变（硬编码进 prompt 会过期）

通用广告知识三条全不满足。所以这套 RAG 的实际作用是：

- 不提升准确率 —— 模型本来就会
- 增加延迟 —— 多一次向量检索 + 一次 embedding
- **引入不确定性** —— 检索错了会污染上下文，且错得没有规律

行业里管这个叫 **RAG anti-pattern**：把"模型已知的常识"放进检索，
用不确定性换一个本来就不存在的问题。

**三个处置选项，按推荐排序：**

| 方案 | 做法 | 代价 |
|---|---|---|
| **B（推荐）** | 改成「口径检索」：`metrics.yaml` 已有 16 个指标的结构化定义，`get_metric_definition` 精确查询即可，删掉 `search_knowledge` 和整个向量库 | 删 ~500 行，依赖少两个（chromadb、sentence-transformers） |
| A | 直接删除 RAG 能力，不替代 | 最简单，但少一个演示点 |
| C | 保留，但如实标注为 placeholder（占位） | 保留风险：被追问「为什么用向量库存 eCPM 定义」时不好答 |

推荐 B 的理由：**口径是"模型不知道 + 必须准确 + 会变"的内容**，这才是 RAG 的正当用途。
但它已经有结构化存储（YAML），**精确查询严格优于向量相似度** —— 不需要"大概相似的口径"。

> 面试可以说的一句话：「我做过一次 RAG 的判断，结论是这个场景不该用 RAG。
> 用向量检索存指标口径，不如 YAML 精确查询准，还多一次网络往返。」

### 1.2 历史决策数据：可以做"规则化降级"

现状：`operation_log` 14 条，全部由本项目测试产生。

**行业里"用历史日志评估策略"有正规方法：OPE（off-policy evaluation）**，
包括 IPS（逆倾向加权）、Doubly Robust。但它有一个硬前提：

> 每条历史记录必须带 **propensity**（该动作当时被选中的概率），
> 且 logging policy 必须有**探索性**（不是次次都选最优动作）。

自测产生的日志 propensity ≡ 1，没有方差 → **IPS 会除零 / 方差爆炸，做不了严格 OPE**。
这一点必须承认，不能含糊过去。

**可验证替代物：把"历史怎么做"转成"什么条件下做什么"（Playbook）**

```
历史数据的样子：  3 月 12 日，优化师删了 ch_007，因为它 ROI 0.3
规则化的样子：    IF d7_roi < 0.5 AND installs >= 1000 AND 连续天数 >= 8
                  THEN delete_sub_channel
```

规则化的三个好处：

1. **可执行** —— 能直接写成护栏和评测用例，不需要"回忆当时怎么想"
2. **可反驳** —— 每条规则都能问"反例是什么"，这是评估的起点
3. **不依赖后台权限** —— 实习期间见过的处理方式是**个人经验**，写下来就是你的

具体做法：20 条正例（该动）+ 20 条反例（不该动），直接变成 eval 场景。
第 1.2 节的缺口就变成了第 1.2 节的资产。

### 1.3 Playwright：这不是缺口，做法本来就该这样

现状：`mock_pages/` 下两个本地 HTML，但 Playwright 走的是**真实操作链路**——
启动浏览器、按 CSS 选择器定位、列表页→详情页跳转、逐字段提取。

**IAA 后台数据是商业隐私，任何公开仓库都不可能有。** 想拿到只有一条路：
在该公司任职。这不是技术问题。

所以「Playwright 抓不到真实数据」不构成缺陷，**但叙述必须改**：

| 错误的说法 | 正确的说法 |
|---|---|
| 「用 Playwright 抓取真实投放数据」 | 「用 Playwright 模拟后台操作链路，数据源用 fixture 替代」 |
| 「实现了多平台采集」 | 「实现了采集器的抽象层（`ConfigFetcher` 基类 + 工厂），接一个平台只需实现三个方法」 |

**Playwright 在这个项目里的真实价值，不是"抓到数据"，是证明你能处理：**

- 登录态（cookie / localStorage 注入）
- 动态渲染（等元素出现，不是 `sleep(3)`）
- 多级页面跳转（列表 → 详情 → 回列表）
- 选择器脆弱性（用 `data-*` 属性而不是位置 nth-child）
- 失败重试与部分成功（某一页挂掉不能整批丢）

行业里对应的做法叫 **fixture / recorded response**（录制一次真实响应，之后回放），
`vcrpy` 就是这个思路的通用实现。这是标准工程实践，不是妥协。

**升级路径（如果想补强）**：接一个公开站点做真实采集，比如应用商店榜单 / 公开广告情报站，
证明反爬绕过与增量同步。这比"假装有后台权限"有价值得多。

## 二、架构限制（评测中已标记为 known_gap）

这些是**代码结构问题，不是数据问题**，已修或已记录：

| # | 限制 | 后果 | 状态 |
|---|---|---|---|
| 1 | `adjust_budget` / `adjust_target` 作用于「系列+国家」，快照只有「素材/子渠道」维度，无映射字段 | Agent 唯一的对象级动作只有 `delete_sub_channel`；「看到子渠道该降预算」这条路走不通 | 已记录，修法明确：快照带 `campaign_id`（数据本来有，`_load_top()` 聚合时丢了） |
| 2 | 快照不直接暴露趋势（只能通过 `get_trend_with_ops` 二次查询） | Agent 可能只看当前值就下判断（S07 失败的直接原因） | 已记录，修法：快照加 `trend_7d` 字段 |

评测里的 `known_gap` 分类**不计入任何指标**。理由：把架构欠账算成模型能力问题，
优化方向会被彻底带偏。

## 三、评测本身的边界（这套 eval 能证明什么、不能证明什么）

| 能证明 | 不能证明 |
|---|---|
| 在 8 个设计好的场景上，Agent 的行为符合预期 | 在真实业务分布上也能符合预期 |
| LLM 会**稳定**犯某一类错（S02: 0/3） | 这类错在真实数据里的发生频率 |
| 护栏能拦住不合规动作（54 个单测 + 6 条冒烟） | 护栏阈值（100 次安装、3 倍幅度）在真实业务里是否合理 |
| 成本可计量（单次 $0.0016，缓存命中 93.3%） | 规模化后的成本（没有真实并发） |

**五条具体的方法论限制：**

1. **样本量不足** —— 13 条场景（9 dev + 4 holdout）做不了统计推断。
   行业 benchmark 通常 100–500 例。现在的 13 条是「能不能发现已知问题」，
   不是「通过率是多少」。holdout 只有 4 条，一条翻转就是 25 个百分点，
   所以 holdout 的分数只能当**信号**看，不能当**指标**报。
2. **动作级判定测不出「动作对但理由错」** —— 如果 Agent 删对了渠道但理由是瞎猜的，
   现在会判 PASS。要测这个得加 reasoning 审核（LLM-as-judge），但那会引入
   模型自身的偏好偏差（position bias / verbosity bias），不可靠。
3. **场景分布是人选的** —— 我挑的 13 条反映**我对风险的理解**，
   可能过拟合我的假设。真实业务的 corner case 比我能想到的多。
4. **必须 `--repeat`** —— temperature ≠ 0，单次结果会翻转。实测 S04 三次里有一次
   误删，单跑会显示 PASS。已默认 `--repeat 1`，但正式流程应该是 3。
5. **holdout 是一次性消耗品** —— 看过结果再改代码，它就已经退化成 dev。
   所以每轮修完必须把暴露问题的场景移进 dev、再补新的 holdout。
   这条限制没法消除，只能靠纪律：**holdout 的分数只写进报告，不回灌到调参。**

## 四、术语对照（这套东西的正式名字）

如果被问「你做的这个检测叫什么」，按这个顺序答：

### 整体

| 中文 | 英文 | 说明 |
|---|---|---|
| Agent 评测 | **Agent Evaluation / Evals** | 总称 |
| 离线评测 | **offline eval / static eval** | 不接真实流量，用固定输入跑 |
| 在线评测 | online eval / A-B test / shadow mode | 接真实流量，我只做了离线 |

### 数据集与场景

| 中文 | 英文 | 说明 |
|---|---|---|
| 黄金测试集 | **golden set / eval set / benchmark suite** | 答案确定的评测用例集 |
| 场景化评测 | **scenario-based evaluation** | 每个 case 是完整状态快照 + 预期行为 |
| 反事实对偶用例 | **counterfactual paired cases** | 表面现象相同、正确答案相反（本项目 S01/S03） |
| 对抗用例 | **adversarial cases** | 刻意设计让模型出错的输入 |

### 判定方式

| 中文 | 英文 | 说明 |
|---|---|---|
| 确定性判定 | **programmatic / rule-based scorer** | 代码精确匹配，可复现。**本项目用的就是这个** |
| 模型判分 | **LLM-as-judge / model-graded** | 有 position bias / verbosity bias / self-preference bias |
| 动作级匹配 | **action-level / exact match** | 比的是"做了什么"，不是"说了什么" |
| 副作用正确性 | **side-effect correctness** | Agent 特有维度：该不该写库、写对没有 |

### 核心指标

| 指标 | 含义 | 本项目对应 |
|---|---|---|
| **pass@k** | k 次里**有一次**成功即算过 → 衡量**能力上界** | 不适用（我不用这个） |
| **pass^k** | k 次**全部**成功才算过 → 衡量**可靠性** | `--repeat 3` 取最严重那次 ≈ pass^3 |
| false positive rate | 不该动却动了 | safety 指标，代价最高 |
| false negative rate | 该动没动 | recall 指标 |
| **unsafe action rate** | 产生有害写操作的比例 | 安全侧行业叫法 |

**`pass^k` 这个术语值得重点记**，出自 τ-bench（Sierra，2024）：

```
pass^k ≈ p^k        （p = 单次通过率）
S04 实测：p = 2/3 → pass^3 ≈ 0.296
```

也就是说：**单次通过率 66.7% 的 Agent，连续 3 次都做对的概率只有 29.6%。**
这就是"为什么不取多数、取最严重那次"的数学依据。

### 历史日志评估

| 中文 | 英文 | 前提 |
|---|---|---|
| 离线策略评估 | **off-policy evaluation (OPE)** | 日志需带 propensity，且 logging policy 有探索 |
| 逆倾向加权 | **IPS (inverse propensity scoring)** | propensity ≡ 1 时方差爆炸 |
| 双重稳健 | **doubly robust** | 需要 reward model，我没有 |

### 相关 benchmark（能被追问时引用）

| 名称 | 测什么 |
|---|---|
| **τ-bench** | tool-agent-user 交互，提出 pass^k |
| SWE-bench | 修真实 GitHub issue |
| WebArena | 网页操作任务 |
| AgentBench | 多环境 Agent 综合 |
| RAGAS | RAG 的 faithfulness / context precision |

## 五、被问到时怎么答（三段式，不辩解）

**问：「你这个数据是真的吗？」**

> 「业务数据是合成的，因为 IAA 后台是商业隐私，离职后没有权限，任何公开项目都拿不到。
> 但评测场景的正确答案是我按业务逻辑设计的——真实投放数据本来就没有 label，
> 连资深优化师对'这个渠道该不该删'也只能凭经验判断，历史上没人标注过。
> 所以评测的关键不是数据真不真实，是陷阱设计得对不对。」

**问：「那你的 RAG 和采集是不是也是壳？」**

> 「采集是 fixture，但 Playwright 走的是真实操作链路——登录态、动态渲染、多级跳转、
> 选择器都按真实后台写，接一个平台只要实现基类的三个方法。
> RAG 是真跑了：9 篇行业知识（68 块），ChromaDB + bge-m3，向量与 TF-IDF 关键词
> 混合检索（RRF 融合），20 条检索用例 recall@3 100%。
> 但我不会说它是'行业经验库'——语料是我从公开资料整理的基准和口径，
> 不是我在职期间的内部经验。它的价值在检索链路本身（分块策略、嵌入、融合排序），
> 不在语料规模。」

**问：「你怎么证明 Agent 的判断是对的？」**

> 「13 条场景，分 9 条 dev 和 4 条 holdout，三层指标：safety 看假阳性（代价最高）、
> recall 看漏检、precision 看对象和方向。
> 故意做成对设计——S01 和 S03 表面都是低 ROI，但一个该不动一个是真该动，
> 只会'ROI 低就删'的必然在其中一个上失败。
> 而且判断层和生效层分开报：`--repeat 3` 取最坏情况，safety 判断层 4/8、生效层 7/8，
> 说明护栏补上了三个漏洞，但 Agent 的判断力一点没变——护栏买到的是'不出事'，
> 不是'变聪明'。
> 跑 3 次取最严重那次而不是取多数，因为单次通过率 66.7% 的 Agent，
> pass^3 只有 29.6%，在业务上仍然不能上线。
> 同一份代码单次跑 safety 判断是 7/8，跑 3 次只剩 4/8——所以单次数字只能用来
> 发现问题，不能用来报分数。」

## 六、这份文件本身的作用

多个项目在 GitHub 上都会写 README，但很少有 **LIMITATIONS**。

它的作用不是自我批评，是**降低沟通成本**：

- 面试官不用花时间试出边界，直接看到边界在哪
- 你自己不会被"这个数据是真的吗"这种问题问崩
- 后来者（包括三个月后的你）不会误以为这是生产系统

**能被指出的限制，不构成风险；不能指出的限制，才是风险。**
