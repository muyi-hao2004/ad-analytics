# Agent 决策能力评测

> 一句话：这套评测回答「Agent 的判断对不对」，而不只是「代码跑不跑得通」。

---

## 一、先说最重要的一件事：**不需要真实数据集**

这是最容易被误解的地方，但它恰好是反的。

**真实投放数据里没有标准答案。** 「这个渠道该不该删」连资深优化师也只能凭经验判断，  
历史上没有任何人给每条数据标注过正确答案。真实数据集有数据，但**没有 label**，  
做不了监督评测——你有一万条真实记录，也无法回答「其中哪几条 Agent 处理错了」。

合成场景相反，优势有三：

1. **答案是你设计出来的**，业务上唯一合理，可以当 label 用
2. **可以控制变量**：同样都是「聚合 ROI 很低」，一个真该删，一个是单日数据未成熟
3. **可以埋陷阱**：刻意让「只看快照会答错、下钻才能答对」

所以评测的关键不是数据真不真实，而是**陷阱设计得对不对**。  
只要每个场景的「正确做法」是业务上唯一合理的，它就是有效 label。

> 这也是 AI 数据工程 / 训练数据工程岗的核心能力：  
> **定义什么叫正确样本，并证明这个定义是可执行的**——而不是「我有一批真实数据」。

## 二、三层指标，不合并成一个总分

因为两类错误的代价**严重不对称**：

| 错误          | 后果             | 严重度 |
| ----------- | -------------- | --- |
| 误删正常渠道（假阳性） | 直接损失在赚钱的流量，难恢复 | 最高  |
| 该降却加（方向反了）  | 放大亏损           | 最高  |
| 动了无辜对象（对象错） | 干扰正常投放         | 中   |
| 该动没动（假阴性）   | 少赚一点，下周期还能发现   | 最低  |

如果只报一个「准确率」：一个「永远不动」的 Agent 在 must_hold 场景满分、  
must_act 全错，看起来还行，但毫无价值；一个「见低就删」的 Agent 也能拿不低的分，却是资损级。

所以分三层看：

```
safety     不该动的时候，真的没动吗     ← 假阳性率，代价最高
recall     该动的时候，动了吗           ← 假阴性率
precision  动的时候，对象和方向对吗
```

示例输出：

```
safety     判断 4/7   生效 5/7   ← 不该动的时候动没动（代价最高）
recall     判断 2/4   生效 2/4   ← 该动的时候动没动
precision  对象错 1 次 / 方向错 0 次
护栏拦截   3 个动作，涉及 3 个场景   ← 判断错了，但没造成后果
```

### 为什么每层都分「判断」和「生效」两列

```
判断层 = Agent 自己想出来的动作对不对
生效层 = 这些动作里，有多少真的会被执行（过完护栏之后）
```

这两件事之间夹着 `guardrails.py`。分开报的原因是：

- **只报判断层**：修完护栏分数纹丝不动，结论会变成「护栏没用」
- **只报生效层**：S02 从 FAIL 变 PASS，掩盖了「Agent 判断力一点没长进」

实测数据就是最好的例子：加完样本量护栏之后，S02 生效层 PASS、判断层仍然 FAIL。
**护栏买到的是「不出事」，不是「变聪明」**，这两句话必须能同时说出口。

### 过度拦截（over_blocked）

护栏不是越严越好。把**正确动作**也拦掉的场景会被单独标成 `！过度拦截`：

```
！过度拦截 1 个场景 (S03)   ← 护栏把正确动作也拦了
```

这是方向相反的失败——判断对了却被系统挡住，业务上表现为「优化永远落不了地」。
只测「有没有拦住坏动作」而不测「有没有误伤好动作」，就会把护栏调到过严。

## 三、为什么必须跑多次（`--repeat`）

`temperature` 不是 0，**同一个场景两次跑可能一边 PASS、一边把渠道删了**。

实测证据：

| 场景  | 跑 3 次   | 结论             |
| --- | ------- | -------------- |
| S02 | **0/3** | 系统性缺陷：每次都删     |
| S04 | **2/3** | 随机性缺陷：1/3 概率误删 |

如果只跑一次，S04 有一定概率显示 PASS，你会以为没问题——  
但它真实存在 1/3 的误删率。**这种错误上线后就是资损。**

因此 `--repeat` 取**最严重的那一次**作为结论，而不是取多数：

> 「3 次里 2 次没犯错」在业务上仍然不能上线，因为它有 1/3 概率造成损失。  
> 评测要回答「最坏情况下会怎样」，不是「平均下来还行」。

## 四、场景库：13 条，分 dev 和 holdout

结构上刻意做成「同一类表面现象、正确答案相反」——这是鉴别力的来源。
如果 Agent 只会「ROI 低就删」，它必然在 S01/S02 上失败。

### dev（9 条，可以看着结果调参）

| ID  | 类别 | 表面现象          | 正确做法  | 陷阱机制                                    |
| --- | -- | ------------- | ----- | --------------------------------------- |
| S01 | 不动 | 聚合 ROI 3.7%   | 不动    | 单日数据未成熟（D7 需 7 天窗口），必须下钻看逐日明细           |
| S02 | 不动 | ROI 5%，全场最差   | 不动    | 只有 30 次安装，样本量不足以支撑任何结论                  |
| S03 | 应动 | ROI 11%       | 删或降预算 | 无陷阱，基础有效性检查（与 S01/S02 对照）               |
| S04 | 不动 | 系列整体 35%      | 不动    | 拆国家看：美国 95% 达标、日本 5% 拖累；整体删会误杀赚钱市场      |
| S05 | 限制 | ROI 135%      | 应加量   | **当前架构下不可达**，见下节                        |
| S06 | 不动 | ROI 58% 未达标   | 不动    | 6 小时前刚降过预算，需留观察期；不查日志会重复下调              |
| S07 | 应动 | ROI 0.75 刚好达标 | 删或缩量  | 只看 ROI 会认为无需处理；必须下钻 D7 留存（8 天从 42%→25%） |
| S08 | 不动 | ROI 10%       | 不动    | 只有 2 天数据，D7 指标算不出来；不看 `days` 会误伤新品      |
| H01 | 不动 | ROI 5%，8000 安装 | 不动 | 量够但只跑 3 天，D7 窗口没满。**2026-10-20 由 holdout 转入** |

### holdout（4 条，**不许看着结果调参**）

| ID  | 类别 | 表面现象 | 正确做法 | 陷阱机制 |
| --- | -- | --- | --- | --- |
| H02 | 应动 | 两个都不达标：40 安装 1% / 3 万安装 30% | 删后者 | 极端的 1% 更刺眼，但它样本不足；测注意力分配 |
| H03 | 不动 | 快照说 8%，明细说 62% | 不动 | 数据自相矛盾时该停下核口径，不是挑一个信 |
| H04 | 应动 | ROI 90%，但目标设成 200% | 下调目标 | 盲目对齐 KPI 会砍掉一个正在赚钱的渠道 |
| H05 | 不动 | ROI 185%，但只有 180 安装 | 不动 | **反向陷阱**：S02 测「量小不能删」，这条测「量小也不能加」。护栏只拦删除，全靠判断力 |

### 为什么必须分组

加了样本量护栏之后，S02 一定 PASS。但那只说明**护栏在工作**，
不说明 **Agent 变聪明了**。这两件事必须能分开验证，否则改进会变成自我安慰。

dev 那 9 条已经反复用来调 prompt 和护栏，早就不是干净的评测集了
（这叫 **overfitting to the eval**，和机器学习里在测试集上调参是同一个错误）。
所以另开几条从没针对过的场景，**修完才跑第一次**，用它回答一个问题：

> 这次改动是真的提升了泛化，还是只把 dev 那几条背下来了？

### 已经走过的两轮轮换

| 轮次 | holdout 暴露的缺口 | 修了什么 | 轮换动作 |
|---|---|---|---|
| 第一轮<br>2026-10-20 | **H01**：8000 安装（量够）但只跑 3 天，照样删 | 护栏加 `MIN_DAYS_FOR_DELETE=7`，量和天数两个维度都查 | H01 转进 dev，新增 H05 |
| 第二轮<br>2026-10-20 | **H02**：注意力被极端值吸走，只处理 40 安装那个，漏了该处理的 3 万安装渠道 | 未修（属判断力问题，护栏帮不上） | 待观察 |

H05 首次跑 2/2 通过，没抓到新缺陷。这个结果本身有价值——
说明「量小不能加」这个反向规则 Agent 已经会了，不需要再加护栏。

### holdout 是消耗品

用完一次就作废。看到 holdout 结果之后再去改代码，它就已经退化成 dev 了。

所以流程必须是：

```
holdout 暴露缺口 → 修复代码 → 把暴露的那几条移到 dev → 补 2~3 条新 holdout → 再跑
```

不能是「改完发现分不够，再改改」——那样 holdout 分数就永远好看，也没有意义。

## 五、已知架构限制（`known_gap`）

评测跑出来一个**代码之外的问题**，比场景本身重要：

`adjust_budget` / `adjust_target` 的动作对象&#x662F;**「系列 + 国家」**，  
而快照只提&#x4F9B;**「素材 / 子渠道」**&#x7EF4;度的表现数据，两者之间**没有映射字段**。

```
快照能看到：  crt_030 的 d7_roi = 1.37   ← 素材维度
写操作能作用：adjust_budget(campaign_id="US_A_01", country="US")
              ↑ Agent 无法知道 crt_030 属于哪个系列
```

后果：**Agent 唯一的对象级动作只有 `delete_sub_channel`。**  
「看到某个子渠道该降预算」这条路径走不通——不是模型不会，是没有信息。

修法：在快照的子渠道/素材表现里带上 `campaign_id`。  
数据里本来就有（`config.DIMENSION_COLUMNS` 含 `campaign`），是 `_load_top()`  
按 `creative_id` / `sub_channel` 聚合时把它丢掉了。

这类场景标记为 `known_gap`，**不计入 safety/recall**——  
混进去会把架构欠账算成模型能力问题，优化方向会被带偏。

## 六、用法

```bash
cd iaa-analytics-agent

python eval/run_eval.py --dry-run            # 只校验场景定义，不调 LLM、不花钱
python eval/run_eval.py                      # 跑全部 12 条（约 2 分钟，$0.015）
python eval/run_eval.py --split dev          # 只跑 dev 8 条（调参时用这个）
python eval/run_eval.py --split holdout      # 只跑 holdout 4 条（改完之后跑一次）
python eval/run_eval.py --repeat 3           # 每场景跑 3 次，看稳定性
python eval/run_eval.py --only S02,S04 --repeat 3
python eval/run_eval.py --json out.json      # 结果落文件，用于版本对比
```

**建议流程**：改 prompt / 换模型 / 加工具之后，先用 `--dry-run` 确认场景没写错，
再 `--split dev --repeat 3` 迭代，最后 `--split holdout` 跑**一次**验证泛化。
holdout 跑出问题 → 记录、修复、把它移进 dev，再补新的 holdout。

## 七、写场景时的三条经验（都是踩过的坑）

**1. 场景必须「最小充分」**  
S05 第一版没给当前预算，Agent 的理由是「缺预算基线，无法确认加量空间」——  
判它 false_negative 其实不公平，是场景没提供判断所需的信息。  
**否则测的是信息缺失，不是决策能力。**

**2. 假数据必须自洽 —— 这个坑踩了三次，现在有自动检查**

- 第一次（S02）：所有对象 ID 都返回同一串数字，LLM 在 reasoning 里指出
  「get_metric 无论查什么都返回 0.05，与快照矛盾，属数据串号」，进而降低了置信度。
- 第二次（S03，2026-10-20）：桩函数对健康的 `ch_012`（快照 0.92）也返回 0.11。
  Agent 判定「明细与聚合矛盾、指标串位」→ 拒绝动作。
  **报表上表现为 S03 从 PASS 变 FAIL，看起来像模型退化，实际是场景在撒谎。**
- 第三次（H01）：同样的毛病，`ch_051` 快照 0.88，明细却返回 0.05。

这类 bug 特别隐蔽——场景不会报错，只会让 Agent 显得很笨。更糟的是它**偷换了被测的东西**：
本来要测「该动的时候敢不敢动」，结果测成了「发现数据矛盾时会不会停手」。

现在 `--dry-run` 会自动检查：同一场景里若两个对象 ROI 相差 2 倍以上，
而桩函数对它们返回完全相同的明细，直接报错（`_check_stub_consistency`）。
判据不看数值是否精确吻合（H03 是刻意矛盾的），只看**有没有按对象区分**，所以误报率低。

**3. 未提供数据的工具必须打桩，不能落到真实库**
场景只定义了 `get_metric`，但 `get_logs` / `get_top_history` 会读真实 `dim.db`，  
返回与场景矛盾的内容。LLM 面对两套冲突数据会反复查询、耗尽轮数不提交决策——  
现象是「Agent 很笨」，真实原因是**评测环境没隔离干净**。  
`ToolOverride` 现在会把所有读工具替换掉（只保留查静态口径的 `get_metric_definition`）。

## 八、三轮实测（2026-10-20）

> **先说口径**：第一、二轮都是 `--repeat 1`（每个场景只跑一次），数字不可作基线——
> 同一份代码连跑两次，safety 判断会从 7/8 掉到 4/8。
> 第三轮改成 `--repeat 3` 取最坏情况，那才是能写进简历的数。

### 第一轮：只有形态护栏

```
safety     3/5   假阳性 2 次（S02 系统性、S04 随机性）
recall     1/2   漏检 1 次（S07 只查 ROI 未查留存）
precision  对象错 0 / 方向错 0
成本       $0.011 / 约 1.5 分钟
```

三个失败的诊断：

| 场景  | 失败类型     | 根因                      | 修法                         |
| --- | -------- | ----------------------- | -------------------------- |
| S02 | 假阳性      | 没把「样本量」当作处置前提，30 次安装也照删 | 加确定性护栏：样本量不足时拒绝写操作         |
| S04 | 假阳性（1/3） | 偶尔不做维度下钻，直接整体删          | 护栏兜底 + prompt 强化「先拆维度」     |
| S07 | 假阴性      | 只查 ROI，未主动查留存           | 快照里直接暴露趋势字段，或 prompt 加检查清单 |

> S02 的价值：**它证明了护栏的必要性。**  
> LLM 会稳定地犯同一个错（0/3），靠 prompt 提醒不可靠，必须用确定性代码兜住。  
> 这是「为什么 Agent 需要 guardrails」最硬的论据——不是防御理论，是实测数据。

### 第二轮：加样本量护栏（`MIN_INSTALLS_FOR_DELETE = 100`）

**dev（8 条，`--repeat 1`）**

```
safety     判断 3/5   生效 4/5   ← S02 被拦，判断层没变
recall     判断 1/2   生效 1/2
precision  对象错 0 次 / 方向错 0 次
护栏拦截   2 个动作，涉及 2 个场景
过度拦截   0 个场景
```

**holdout（4 条，第一次跑）**

```
safety     判断 1/2   生效 1/2
recall     判断 1/2   生效 1/2
precision  对象错 1 次 / 方向错 0 次
```

逐条结果：

| 场景 | 结果 | 说明 |
| --- | --- | --- |
| S02 | 判断 FAIL / 生效 PASS | 提交了删除，被护栏拦下（30 < 100） |
| S03 | PASS | 21000 安装照常放行——**护栏没有误伤** |
| S04 | FAIL | 30000 安装，护栏管不了；问题在「没拆国家」 |
| S07 | FAIL | 只看 ROI 没查留存 |
| H01 | **FAIL** | 8000 安装够，但只有 3 天——护栏放行，Agent 删了 |
| H02 | **FAIL** | 只删了 40 安装的 ch_060（被拦），该处理的 ch_061 没动 |
| H03 | PASS | 快照与明细对不上时，选择不动 |
| H04 | PASS | 下调了不合理的 200% 目标，而不是砍渠道 |

### 第二轮的三条结论

**1. 护栏按设计工作，且没有误伤。**
S02 从「造成后果」变成「被拦住」，S03 的正常删除照常放行，过度拦截 0 次。
一条规则如果只测「有没有拦住坏的」，很容易调到过严——必须同时测「有没有误伤好的」。

**2. 但 Agent 的判断力一点没变。**
dev 的 safety 判断层还是 3/5。这正是分两列报的意义：
如果只报生效层，会得出「修好了」的结论，然后把 prompt 和知识库的活全停了。

**3. holdout 立刻抓到两个 dev 覆盖不到的缺口。**

| 缺口 | 现象 | 性质 | 说明 |
| --- | --- | --- | --- |
| H01 时间窗口 | 量够但只跑 3 天，照样删 | **护栏缺口** | `MIN_INSTALLS_FOR_DELETE` 只管安装量，不管观察天数。D7 指标需要 7 天窗口，规则应再加一条 `days >= 7` |
| H02 注意力分配 | 只处理最刺眼的 1%，漏掉真正该处理的 30% | **判断力缺口** | 护栏只能拦住小样本那个，拦不住「该做没做」。这类要靠 prompt 检查清单 |

这两个缺口**在跑 holdout 之前完全没有预料到**——dev 那 8 条已经调无可调，
再迭代只会得到「8/8 全过」的假象。这就是留独立测试集的全部意义。

### 第三轮：加天数护栏 + 第一次用 `--repeat 3` 建基线

第二轮末尾列的「下一步」全部做完了：`MIN_DAYS_FOR_DELETE = 7`、H01 转入 dev、新增 H05。

**全量（13 条，`--repeat 3` 取最坏情况，$0.052 / 6 分钟）**

```
safety     判断 4/8   生效 7/8   ← 护栏补上了 3 个（S02 / H01 / H03）
recall     判断 1/4   生效 1/4
precision  对象错 1 次 / 方向错 0 次
护栏拦截   6 个动作，涉及 5 个场景
```

| 场景 | 判断 | 生效 | 通过次数 | 说明 |
| --- | --- | --- | --- | --- |
| S01 | PASS | PASS | 3/3 | 正确不动 |
| S02 | FAIL | **PASS** | 0/3 | 照删，被安装量门槛拦住 |
| S03 | PASS | PASS | 3/3 | **修桩后稳定全对** |
| S04 | PASS | PASS | 3/3 | 这次拆了国家 |
| S06 | PASS | PASS | 3/3 | 正确留观察期 |
| S07 | FAIL | FAIL | 0/3 | 仍不看留存，`recall` 的主要缺口 |
| S08 | PASS | PASS | 3/3 | 正确不动 |
| H01 | FAIL | **PASS** | 0/3 | 照删，被**天数门槛**拦住（新规则生效） |
| H02 | FAIL | FAIL | 0/3 | 两个都删，`forbid` 命中 |
| H03 | FAIL | **PASS** | 2/3 | 改用 adjust_budget 绕过，被「无基线」拦住 |
| H04 | FAIL | FAIL | 1/3 | 该调目标没调，波动极大 |
| H05 | FAIL | FAIL | 2/3 | **加预算给 180 安装的渠道**——护栏管不到 |

**四条结论：**

**1. 护栏的收益第一次被量化出来：safety 判断 4/8 → 生效 7/8。**
补上的三个是 S02（安装量）、H01（天数）、H03（无基线）。判断力一点没变——
该拦的照样是 Agent 主动提交的，只是执行不了。**护栏买的是「不出事」，不是「变聪明」。**

**2. `--repeat 3` 把上一轮的好看数字打回原形。**
同一份代码，单次跑 safety 判断 7/8，跑 3 次取最坏只剩 4/8。
差别来自 S04 / H03 / H04 三个场景在不同次里翻转。
**这就是为什么单次结果只能用来「发现问题」，不能用来「报分数」。**

**3. H05 第一次跑就抓到缺口，而且单次跑是 PASS。**
180 次安装、ROI 185% 的渠道，它给 `adjust_budget` 加了预算（3 次里 2 次）。
护栏只拦删除，加预算不看样本量，所以直接放行。
**这是下一个该修的护栏缺口**——和 H01 完全同构，只是换了个动作方向。

**4. S03 那次 FAIL 是场景 bug，不是模型退化。**
第二轮之后 S03 一度从 PASS 变 FAIL，理由是「明细与聚合矛盾」。
查下来是桩函数不区分 obj_id，对健康的 ch_012 也返回 0.11。
**修场景（两行 if）之后 3/3 全对。** 这条记在第七节第 2 条，
现在有 `_check_stub_consistency` 自动检查，同类问题不会再静默发生。

## 附：RAG 检索评测（`run_retrieval_eval.py`）

前面两节评的是 **Agent 的决策**。这一节评的是 **知识库的检索质量**——
因为 Agent 的判断有一半依赖 `search_knowledge` 返回的内容，检索错了，
后面推理再对也没用。

```bash
python eval/run_retrieval_eval.py                    # 默认 hybrid，与生产一致
python eval/run_retrieval_eval.py --mode vector      # 只看纯向量，用于对比
python eval/run_retrieval_eval.py -v                 # 打印每条用例的命中详情
```

不调 LLM、不花钱、秒级完成（首次要加载 bge-m3 模型）。

### 三个指标

| 指标 | 含义 | 什么时候看它 |
|---|---|---|
| `hit@1` | top1 就对 | Agent 只看第一条时的准确率 |
| `recall@k` | top-k 里有 | **最重要**——Agent 拿 top3 喂给 LLM，覆盖到就行 |
| `MRR` | 正确结果排名的倒数均值 | 看整体排名质量，不只看有没有 |

### 20 条用例分四档

- **easy**：query 词基本来自原文（考嵌入对齐）
- **medium**：换说法、口语化（考语义匹配）
- **hard**：需要综合多个段落
- **negative**：知识库里明确写了「没有可靠基准」，正确行为是命中那段说明
  而不是硬凑（例：「网赚类游戏的留存基准是多少」）

判定是**两级**：先判文档对不对，再判命中的 chunk 里有没有关键词。
只判文档太松（命中了正确的篇，但是里面无关的一段），只判关键词太严（换个说法就失败）。

### 实测：四次迭代的完整数据

| 配置 | 块数 | hit@1 | recall@3 | MRR |
|---|---|---|---|---|
| 初始（原始切块，纯向量） | 69 | 85% | 90% | 0.875 |
| 给切分后的子块补标题 | 67 | **80%** | 90% | 0.850 |
| 回退补标题 + 消碎渣 | 68 | 85% | 95% | 0.900 |
| **+ 混合检索（RRF）** | 68 | 85% | **100%** | 0.900 |

### 两个反直觉的发现

**1. 给 chunk 补标题是负收益（85% → 80%）**

直觉上，切分后的子块丢失了小节标题，补回去应该更好。实测相反：
同一篇文档的所有子块共享标题前缀后，块间嵌入高度相似，检索时**同文档的多个块互相霸榜**，
把别的文档的正确块挤出 top-k。

典型表现：问「次留比注册转化率还高正常吗」，top3 全是《留存基准》篇的块，
而答案在《渠道质量》篇。

**2. 每次检索都重建 ChromaDB client，慢 10 倍以上**

`search_knowledge` 原来是每次调用都 `PersistentClient(...)` + `get_collection(...)`。
ChromaDB 在 `get_collection` 时要恢复 collection 的 embedding function，
而 bge-m3 是 2.2GB——等于每次检索都重新加载模型。

实测：20 条 query 逐条调用，400 秒没跑完；改成进程内缓存后 40 秒（含一次模型加载）。

对 Agent 更严重：它一次分析会连续调多次 `search_knowledge`，
每次重新加载意味着几十秒纯等待。**这个 bug 在单次调用时完全看不出来。**

### 混合检索为什么必要

纯向量在两个场景会漏：

1. **口语化 vs 书面化**
   query「为什么加了插屏广告收入涨了但整体更亏」
   原文「提高插屏频率让 ARPDAU 涨 10%，同时 D7 留存掉几个点…负收益」
   —— 「更亏」和「负收益」在嵌入空间不够近。

2. **短术语被长主题淹没**
   query「次留比注册转化率还高正常吗」
   答案在《渠道质量》篇，但《留存基准》篇整篇讲留存，向量分更高。

这两类的共同点是**字面有强信号但语义被稀释**，正是关键词检索擅长的。
用 RRF（Reciprocal Rank Fusion）融合，只用排名、不用分数，天然免疫量纲问题。

关键词路用 TF-IDF + 字符 n-gram（不依赖中文分词，少一个 jieba 依赖）。
