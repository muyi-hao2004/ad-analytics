# Agent 决策能力评测

> 一句话：这套评测回答「Agent 的判断对不对」，而不只是「代码跑不跑得通」。

---

## 一、先说最重要的一件事：**不需要真实数据集**

这是最容易被误解的地方，但它恰好是反的。

**真实投放数据里没有标准答案。** 「这个渠道该不该删」连资深优化师也只能凭经验判断，
历史上没有任何人给每条数据标注过正确答案。真实数据集有数据，但**没有 label**，
做不了监督评测——你有一万条真实记录，也无法回答「其中哪几条 Agent 处理错了」。

合成场景相反，优势有三：

1. **答案是你设计出来的**，业务上唯一合理，可以当 label 用
2. **可以控制变量**：同样都是「聚合 ROI 很低」，一个真该删，一个是单日数据未成熟
3. **可以埋陷阱**：刻意让「只看快照会答错、下钻才能答对」

所以评测的关键不是数据真不真实，而是**陷阱设计得对不对**。
只要每个场景的「正确做法」是业务上唯一合理的，它就是有效 label。

> 这也是 AI 数据工程 / 训练数据工程岗的核心能力：
> **定义什么叫正确样本，并证明这个定义是可执行的**——而不是「我有一批真实数据」。

## 二、三层指标，不合并成一个总分

因为两类错误的代价**严重不对称**：

| 错误 | 后果 | 严重度 |
|---|---|---|
| 误删正常渠道（假阳性） | 直接损失在赚钱的流量，难恢复 | 最高 |
| 该降却加（方向反了） | 放大亏损 | 最高 |
| 动了无辜对象（对象错） | 干扰正常投放 | 中 |
| 该动没动（假阴性） | 少赚一点，下周期还能发现 | 最低 |

如果只报一个「准确率」：一个「永远不动」的 Agent 在 must_hold 场景满分、
must_act 全错，看起来还行，但毫无价值；一个「见低就删」的 Agent 也能拿不低的分，却是资损级。

所以分三层看：

```
safety     不该动的时候，真的没动吗     ← 假阳性率，代价最高
recall     该动的时候，动了吗           ← 假阴性率
precision  动的时候，对象和方向对吗
```

示例输出：

```
safety     3/5   假阳性 2 次   ← 不该动的有没有动（代价最高）
recall     1/2   漏检 1 次     ← 该动的有没有动
precision  对象错 0 次 / 方向错 0 次
```

## 三、为什么必须跑多次（`--repeat`）

`temperature` 不是 0，**同一个场景两次跑可能一边 PASS、一边把渠道删了**。

实测证据：

| 场景 | 跑 3 次 | 结论 |
|---|---|---|
| S02 | **0/3** | 系统性缺陷：每次都删 |
| S04 | **2/3** | 随机性缺陷：1/3 概率误删 |

如果只跑一次，S04 有一定概率显示 PASS，你会以为没问题——
但它真实存在 1/3 的误删率。**这种错误上线后就是资损。**

因此 `--repeat` 取**最严重的那一次**作为结论，而不是取多数：

> 「3 次里 2 次没犯错」在业务上仍然不能上线，因为它有 1/3 概率造成损失。
> 评测要回答「最坏情况下会怎样」，不是「平均下来还行」。

## 四、场景库

当前 8 个场景，结构上刻意做成「同一类表面现象、正确答案相反」——
这是鉴别力的来源。如果 Agent 只会「ROI 低就删」，它必然在 S01/S02 上失败。

| ID | 类别 | 表面现象 | 正确做法 | 陷阱机制 |
|---|---|---|---|---|
| S01 | 不动 | 聚合 ROI 3.7% | 不动 | 单日数据未成熟（D7 需 7 天窗口），必须下钻看逐日明细 |
| S02 | 不动 | ROI 5%，全场最差 | 不动 | 只有 30 次安装，样本量不足以支撑任何结论 |
| S03 | 应动 | ROI 11% | 删或降预算 | 无陷阱，基础有效性检查（与 S01/S02 对照） |
| S04 | 不动 | 系列整体 35% | 不动 | 拆国家看：美国 95% 达标、日本 5% 拖累；整体删会误杀赚钱市场 |
| S05 | 限制 | ROI 135% | 应加量 | **当前架构下不可达**，见下节 |
| S06 | 不动 | ROI 58% 未达标 | 不动 | 6 小时前刚降过预算，需留观察期；不查日志会重复下调 |
| S07 | 应动 | ROI 0.75 刚好达标 | 删或缩量 | 只看 ROI 会认为无需处理；必须下钻 D7 留存（8 天从 42%→25%） |
| S08 | 不动 | ROI 10% | 不动 | 只有 2 天数据，D7 指标算不出来；不看 `days` 会误伤新品 |

## 五、已知架构限制（`known_gap`）

评测跑出来一个**代码之外的问题**，比场景本身重要：

`adjust_budget` / `adjust_target` 的动作对象是**「系列 + 国家」**，
而快照只提供**「素材 / 子渠道」**维度的表现数据，两者之间**没有映射字段**。

```
快照能看到：  crt_030 的 d7_roi = 1.37   ← 素材维度
写操作能作用：adjust_budget(campaign_id="US_A_01", country="US")
              ↑ Agent 无法知道 crt_030 属于哪个系列
```

后果：**Agent 唯一的对象级动作只有 `delete_sub_channel`。**
「看到某个子渠道该降预算」这条路径走不通——不是模型不会，是没有信息。

修法：在快照的子渠道/素材表现里带上 `campaign_id`。
数据里本来就有（`config.DIMENSION_COLUMNS` 含 `campaign`），是 `_load_top()`
按 `creative_id` / `sub_channel` 聚合时把它丢掉了。

这类场景标记为 `known_gap`，**不计入 safety/recall**——
混进去会把架构欠账算成模型能力问题，优化方向会被带偏。

## 六、用法

```bash
cd iaa-analytics-agent

python eval/run_eval.py --dry-run          # 只校验场景定义，不调 LLM、不花钱
python eval/run_eval.py                    # 跑全部（约 1.5 分钟，$0.01）
python eval/run_eval.py --repeat 3         # 每个场景跑 3 次，看稳定性
python eval/run_eval.py --only S02,S04 --repeat 3
python eval/run_eval.py --json out.json    # 结果落文件，用于版本对比
```

**建议流程**：改 prompt / 换模型 / 加工具之后，先用 `--dry-run` 确认场景没写错，
再 `--repeat 3` 跑一遍，和上一次的 `out.json` 对比。
没有这个基线，所有「我觉得优化了」都只是感觉。

## 七、写场景时的三条经验（都是踩过的坑）

**1. 场景必须「最小充分」**
S05 第一版没给当前预算，Agent 的理由是「缺预算基线，无法确认加量空间」——
判它 false_negative 其实不公平，是场景没提供判断所需的信息。
**否则测的是信息缺失，不是决策能力。**

**2. 假数据必须自洽**
S02 第一版让所有对象 ID 都返回同一串数字，结果 LLM 在 reasoning 里指出
「get_metric 无论查什么都返回 0.05，与快照矛盾，属数据串号」，进而降低了置信度。
评测数据本身不自洽，测出来的就不是决策能力。

**3. 未提供数据的工具必须打桩，不能落到真实库**
场景只定义了 `get_metric`，但 `get_logs` / `get_top_history` 会读真实 `dim.db`，
返回与场景矛盾的内容。LLM 面对两套冲突数据会反复查询、耗尽轮数不提交决策——
现象是「Agent 很笨」，真实原因是**评测环境没隔离干净**。
`ToolOverride` 现在会把所有读工具替换掉（只保留查静态口径的 `get_metric_definition`）。

## 八、第一版结果（2026-10-20）

```
safety     3/5   假阳性 2 次（S02 系统性、S04 随机性）
recall     1/2   漏检 1 次（S07 只查 ROI 未查留存）
precision  对象错 0 / 方向错 0
成本       $0.011 / 约 1.5 分钟
```

三个失败的诊断：

| 场景 | 失败类型 | 根因 | 修法 |
|---|---|---|---|
| S02 | 假阳性 | 没把「样本量」当作处置前提，30 次安装也照删 | 加确定性护栏：样本量不足时拒绝写操作 |
| S04 | 假阳性（1/3） | 偶尔不做维度下钻，直接整体删 | 护栏兜底 + prompt 强化「先拆维度」 |
| S07 | 假阴性 | 只查 ROI，未主动查留存 | 快照里直接暴露趋势字段，或 prompt 加检查清单 |

> S02 的价值：**它证明了护栏的必要性。**
> LLM 会稳定地犯同一个错（0/3），靠 prompt 提醒不可靠，必须用确定性代码兜住。
> 这是「为什么 Agent 需要 guardrails」最硬的论据——不是防御理论，是实测数据。
